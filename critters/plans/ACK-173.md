# ACK-173: Add `critters list-types` command

## Summary

Add a `critters list-types` CLI command that displays all configured critter types with their key settings. This is a read-only, config-inspection command — it loads the config YAML (without requiring provider credentials) and prints a structured summary of each critter type.

## Files to Create

### `src/cli-list-types.ts`

New file implementing `runListTypes()`. Follows the pattern of `src/status.ts` and `src/cli-kickoff.ts` — standalone CLI command module with a named export.

**Behavior:**
1. Find and parse the config YAML (reusing the config path resolution logic from `src/config.ts`). Since `loadConfig()` validates provider credentials (which may not be set for a pure config inspection command), we need a lighter approach: use the same `resolveConfigPath()` logic inline (check `./critters.config.yaml`, then `~/.critters/config.yaml`, then `--config` flag) and parse the YAML directly, then use `parseCritterTypes` from `src/critter-type.ts` to build the type configs. Alternatively, we can accept that credentials are needed and use `loadConfig()` — but this would make `list-types` fail without env vars, which is undesirable for a config inspection tool.

   **Decision:** Parse YAML directly and use `parseCritterTypes`/`synthesizeDefaultTypes` to build type configs without full validation. This mirrors how `getStatusConfig()` in `src/status.ts` does lightweight config reads.

2. For each `CritterTypeConfig`, print:
   - **Name** — `ct.name`
   - **Provider** — `ct.provider ?? defaultProvider` (from top-level `provider` field)
   - **Trigger** — `label`, `status`, `statusType` (if set), `assignee` (if set)
   - **Phases** — count and names (e.g., "2 phases: planning → execution")
   - **Concurrency** — `ct.concurrency`
   - **Timeout** — `ct.timeoutMinutes` minutes
   - **Outcomes** — each outcome key with its status (e.g., "success→In Review, failure→Critter Failed")

3. Output format: structured text, one block per type, with clear labels. Example:

```
Critter Types (2 configured)

  create
    Provider:    linear
    Trigger:     label="Critter", status="Todo", statusType="unstarted"
    Phases:      planning → execution (2 phases)
    Concurrency: 2
    Timeout:     30 min
    Outcomes:    success → In Review, failure → Critter Failed

  review
    Provider:    linear
    Trigger:     label="Critter Review", status="In Review"
    Phases:      review (1 phase)
    Concurrency: 2
    Timeout:     15 min
    Outcomes:    merged → Done, needsChanges → Human Review, failure → Critter Failed
    Enrichment:  extractPrUrl
```

**Config loading approach:**
- Read config YAML path using same candidate logic as other CLI commands
- Parse YAML with the `yaml` package
- Build critter types using the existing parsing functions from `src/critter-type.ts`
- Build a minimal `Config`-like object with just the fields needed by `synthesizeDefaultTypes` (for the case where `critterTypes` is not in the YAML)
- Accept an optional `--config PATH` flag (consistent with daemon flags)

## Files to Modify

### `src/index.ts`

Add a new subcommand block for `list-types` in the CLI routing section (between existing commands, alphabetically near `logs`):

```typescript
if (subcommand === "list-types") {
  const { runListTypes } = await import("./cli-list-types.js");
  const configIdx = Bun.argv.indexOf("--config");
  const configPath = configIdx !== -1 && Bun.argv[configIdx + 1] ? Bun.argv[configIdx + 1] : undefined;
  await runListTypes(configPath);
  process.exit(0);
}
```

## Dependencies

No new dependencies. Uses existing:
- `yaml` (already a dependency) for YAML parsing
- `src/critter-type.ts` exports (`parseCritterTypes`, `synthesizeDefaultTypes`) for type parsing

## Edge Cases

1. **No config file found** — Print an error message and exit with code 1 (same pattern as other CLI commands)
2. **No `critterTypes` in YAML** — Use `synthesizeDefaultTypes()` to show the default create + review types. Need to build a partial Config object with the flat fields that `synthesizeDefaultTypes` reads.
3. **Multi-provider types** — These expand into multiple entries (e.g., `create:linear`, `create:jira`). Display each expanded entry separately, which is what the user actually gets at runtime.
4. **Custom config path** — Support `--config PATH` flag, same as the daemon.

## Testing Approach

1. **Manual testing** with `bun run src/index.ts list-types` against the project's own `critters.config.yaml`
2. **Manual testing** with `--config test-configs/custom-types.yaml` to verify custom types display correctly
3. **Manual testing** with `--config test-configs/multi-provider.yaml` to verify multi-provider expansion
4. **Verify** `critters help` output includes `list-types`
5. **Verify** the command works without `LINEAR_API_KEY` or other provider env vars set (since it's config-only)

No automated tests are added — this follows the pattern of other CLI commands in the codebase (`status.ts`, `cli-kickoff.ts`, `cli-retry.ts`, `logs.ts`) which do not have unit tests.
