# ACK-121: Add `critters status` CLI Command

## Summary

Add a `status` subcommand to the critters CLI that fetches data from the running daemon's health API and displays a formatted terminal overview. This is a thin CLI wrapper — it reads from `GET /healthz` and `GET /metrics`, formats the data, and prints to stdout.

## Files to Create

### 1. `src/status.ts` — Status command implementation

Create a new module exporting `runStatus()`:

#### `getStatusConfig(): { healthPort: number; concurrency: number; reviewConcurrency: number }`

A lightweight config reader that extracts only the fields needed by the status command — avoids requiring `LINEAR_API_KEY` or full config validation (since the status command is a one-shot CLI tool, not the daemon):

1. Check for config files in order: `./critters.config.yaml`, then `~/.critters/config.yaml`
2. If found, parse YAML and extract:
   - `healthPort` (default: `3847`)
   - `concurrency` (default: `2`)
   - `reviewConcurrency` (default: `2`)
3. If no config file found, use defaults for all fields

This intentionally does NOT call `loadConfig()` because that function requires `LINEAR_API_KEY` and validates the full config, which is unnecessary for the status command. The config file search order matches `resolveConfigPath()` in `src/config.ts`.

#### `runStatus(): Promise<void>`

Main logic:

1. Call `getStatusConfig()` to determine the port and capacity values
2. Fetch `http://localhost:<port>/healthz` — if the fetch fails (connection refused, timeout, etc.), print `"Critters daemon is not running (or health endpoint is disabled)"` to stderr and `process.exit(1)`
3. Fetch `http://localhost:<port>/metrics` — if this fails, proceed with empty metrics (non-fatal)
4. Parse the `/healthz` JSON response (shape matches the existing `HealthStatus` + extras returned by `health.ts`)
5. Filter `/metrics` entries to today (compare `timestamp` date portion to current date in local time)
6. Aggregate today's metrics: count `task_completed` (success), `task_failed` (failure), sum `costUsd`
7. Format and print the output using `console.log()` (not `log()` from logger, since this is a one-shot CLI command)

#### Output format

```
Critters v0.3.1 — running for 2h 15m

Active critters: 2/5
Active reviews:  0/2
Queued: 3 critters, 1 review

Last poll: 45s ago
Today: 5 completed, 1 failed, $2.34 total cost
```

Design notes on the output format:
- The task spec's example shows per-critter detail rows (identifier, title, repo, phase, elapsed). However, the current `/healthz` endpoint (from ACK-119) only returns **counts** (`activeCritters`, `queuedCritters`, `activeReviews`, `queuedReviews`), not per-task details. The status command can only display what the API provides.
- If per-task detail is desired in the future, the `/healthz` endpoint would need to be extended first (separate ticket). This plan implements the command with the data currently available.
- The "running for" duration is computed from the `uptime` field (seconds) returned by `/healthz`.
- "Last poll" is computed from `lastPollAt` ISO timestamp vs now.
- The capacity denominators (`2/5`, `0/2`) come from `concurrency` and `reviewConcurrency` read from the YAML config by `getStatusConfig()`.

#### `formatLastPoll(isoTimestamp: string | null): string`

- If `null`, return `"never"`
- Otherwise, compute delta from now and use `formatDuration(delta_ms)` to format, append `" ago"`

#### `filterTodayMetrics(metrics: MetricEvent[]): MetricEvent[]`

Filter metrics where the date portion of `timestamp` matches today's date (local timezone). Uses `new Date(m.timestamp).toDateString() === new Date().toDateString()`.

#### `aggregateTodayStats(metrics: MetricEvent[]): { completed: number; failed: number; cost: number }`

Loop through today's metrics:
- Count events where `event === "task_completed"` → `completed`
- Count events where `event === "task_failed"` → `failed`
- Sum `costUsd` from all `task_completed` and `task_failed` events → `cost`

However, for verification during development:
- Manual test: start the daemon, run `critters status` in another terminal
- Manual test: stop the daemon, run `critters status` — should show error message and exit 1
- Verify output formatting looks correct with various states (no metrics, many metrics, null lastPollAt)

## Edge Cases

- **Daemon not running**: `fetch()` throws on connection refused → print error message, exit 1
- **Health endpoint disabled** (`healthPort: 0`): Same behavior as daemon not running — fetch fails, error message shown
- **No config file found**: Fall back to defaults (port 3847, concurrency 2, reviewConcurrency 2)
- **No metrics available**: `/metrics` returns `[]` → "Today: 0 completed, 0 failed, $0.00 total cost"
- **`lastPollAt` is null**: Display "Last poll: never" (daemon just started, no poll yet)
- **Metrics without `costUsd`**: Treat undefined as 0 when summing
- **`LINEAR_API_KEY` not set**: Status command does NOT require it — uses lightweight config reader
- **Metrics fetch fails**: Non-fatal — show "Today: (metrics unavailable)" or similar, still show health data
- **Queued counts are zero**: Show "Queued: 0 critters, 0 reviews" or omit the line
