# ACK-202: Dashboard logs — fix live streaming so logs update in real-time

## Summary

The dashboard log page (`/logs/<identifier>`) has three issues with its live streaming implementation:

1. **Content gap between initial fetch and SSE** — The client fetches logs via `/api/logs/<id>?tail=500`, then connects to the SSE stream at `/api/logs/<id>/stream`. The SSE endpoint starts tracking the file from its current size (`fileOffset = statSync(logFile).size`) at connection time. If new log content arrives between the initial fetch response and the SSE connection being established, that content is missed. Additionally, the SSE `start()` handler also sends existing tail content, causing **duplication** with the initial fetch.

2. **SSE error handler kills reconnection** — The `onerror` handler at `src/dashboard.ts:1245` closes the EventSource and sets it to null. Browsers natively auto-reconnect SSE on transient errors, but this handler prevents that behavior entirely.

3. **No auto-scroll indicator** — When the user scrolls up to read earlier logs, new content is silently appended below. There's no visual indication that new content has arrived.

## Files to modify

### `src/dashboard.ts` — Client-side JS in `renderLogPage()` (lines 1163–1267)

#### Change 1: Remove double-fetch pattern, use SSE as sole data source

**Current:** `loadPhase()` fetches via `/api/logs/<id>?tail=500`, then calls `startSSE()` which opens a second connection. The SSE endpoint also sends existing tail content in its `start()` handler (health.ts:164-169), creating duplication.

**New:** Remove the initial `fetch()` call. Connect to SSE directly with `?tail=500` in the SSE URL. The SSE endpoint already accepts a `tail` query parameter (health.ts:124) and sends existing tail content on connection. The client should:
- Set `logEl.textContent = 'Loading...'`
- Open EventSource directly with `?tail=500`
- On first `onmessage`, clear the "Loading..." text and start appending
- This eliminates both the gap and the duplication

Specifically in `loadPhase()` (lines 1174–1215):
- Remove the `fetch()` call and its `.then()` chain
- Call `startSSE(phase)` directly (or inline the SSE logic)
- When `isActive` is false, still do a single fetch for the static content (no SSE needed for completed critters)

#### Change 2: Fix SSE reconnection (lines 1245–1251)

**Current:**
```js
eventSource.onerror = function() {
  if (eventSource) {
    eventSource.close();
    eventSource = null;
  }
};
```

**New:** Replace with a reconnection strategy with exponential backoff:
```js
var retryCount = 0;
var maxRetries = 5;

eventSource.onerror = function() {
  if (eventSource) {
    eventSource.close();
    eventSource = null;
  }
  if (retryCount < maxRetries && isActive) {
    retryCount++;
    var delay = Math.min(2000 * Math.pow(2, retryCount - 1), 30000);
    setTimeout(function() {
      startSSE(phase);
    }, delay);
  }
};
```

Reset `retryCount` to 0 on successful message receipt (inside `onmessage`).

Note: This retry mechanism also handles the startup race condition where a critter has just started but the log file doesn't exist yet. In that case, the SSE endpoint returns a 404 (because `resolveLogFile()` returns null at health.ts:140-143), EventSource fires `onerror`, and the client retries with backoff. The first few retries (2s, 4s, 8s) give the critter time to start producing output.

#### Change 3: Add auto-scroll UX

Add scroll tracking and a "New logs" indicator:

1. **Track scroll position:** Add a `userScrolledUp` flag. On the `scroll` event for `logEl`, check if the user is at the bottom (within a small threshold, e.g. 50px). Set `userScrolledUp = true` when not at bottom.

2. **Conditional auto-scroll:** In `onmessage`, only auto-scroll (`logEl.scrollTop = logEl.scrollHeight`) if `!userScrolledUp`.

3. **"New logs" indicator:** Add a small fixed-position div (initially hidden). When `userScrolledUp` is true and new content arrives, show the indicator (e.g., "↓ New logs"). On click, scroll to bottom and hide the indicator. When the user manually scrolls to the bottom, hide the indicator too.

JS logic:
```js
var userScrolledUp = false;
var indicator = document.getElementById('new-logs-indicator');

logEl.addEventListener('scroll', function() {
  var atBottom = logEl.scrollHeight - logEl.scrollTop - logEl.clientHeight < 50;
  userScrolledUp = !atBottom;
  if (atBottom && indicator) {
    indicator.style.display = 'none';

});

if (indicator) {
  indicator.addEventListener('click', function() {
    logEl.scrollTop = logEl.scrollHeight;
    indicator.style.display = 'none';
    userScrolledUp = false;
  });
}
```

In `onmessage`, replace `logEl.scrollTop = logEl.scrollHeight;` with:
```js
if (!userScrolledUp) {
  logEl.scrollTop = logEl.scrollHeight;
} else if (indicator) {
  indicator.style.display = 'block';
}
```

## Edge cases

- **Completed critters**: When `isActive` is false, the client still uses a simple `fetch()` for the static log content (no SSE needed). The auto-scroll indicator is not relevant since content is static.
- **Phase switching**: When switching tabs, `loadPhase()` closes any existing SSE, resets `userScrolledUp` to false, resets `firstMessage` to true, hides the indicator, and starts fresh.
- **SSE sends existing content**: The SSE endpoint sends the last N lines on connection (controlled by `?tail=500`). For active critters, this is sufficient — no separate fetch needed. The `firstMessage` flag ensures "Loading..." is cleared on first data.
- **Log file doesn't exist yet (startup race)**: If a critter was just picked up but hasn't started producing output, the log file doesn't exist. `resolveLogFile()` returns null, and the SSE endpoint returns a 404. The EventSource fires `onerror`, and the client retries with exponential backoff (2s, 4s, 8s, 16s, 30s). This gives the critter time to start. If after 5 retries (~62s total) the file still doesn't exist, retries stop and the "Loading..." text remains visible.
- **Browser tab backgrounding**: Browsers may throttle timers for background tabs, but SSE connections remain active. The server-side 500ms poll timer and heartbeat handle this correctly.
- **Tail count consistency**: The SSE URL includes `?tail=500`, matching the previous fetch behavior. The SSE endpoint's `tailCount` parameter (health.ts:124) is used for the initial content send, ensuring users see the same amount of history as before.

## Testing approach

1. **Manual testing with active critter**: Start a critter, navigate to `/logs/<id>`, verify logs stream in real-time without gaps or duplication.
2. **Scroll behavior**: Scroll up while logs are streaming, verify the "New logs" indicator appears. Click it to scroll down. Verify auto-scroll resumes.
3. **SSE reconnection**: Open browser DevTools → Network, find the SSE connection, and cancel it. Verify the client reconnects with exponential backoff and continues streaming.
4. **Phase switching**: Click between phase tabs, verify content loads correctly, SSE reconnects for the new phase, and scroll state is reset.
5. **Completed critter**: Navigate to a completed critter's logs, verify static content loads correctly without SSE.
6. **No duplication**: Verify that log lines are not duplicated (the initial SSE send and ongoing polls should not overlap).
7. **Startup race**: Navigate to a critter's logs immediately after it's picked up (before log file exists). Verify the client retries and eventually connects once logs start appearing.
