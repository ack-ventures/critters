# ACK-236: Structured Logging Improvements

## Summary

Make structured JSON logging easier to enable via config and ensure task-scoped logs consistently include the `identifier` field. Currently `--json-logs` is a CLI-only flag. We need to add a `jsonLogs` config field and audit all log call sites to ensure task-scoped logs pass the identifier through to the JSON output.

## Changes

### 1. Add `jsonLogs` config field

**File: `src/types.ts`**
- Add `jsonLogs?: boolean` to the `Config` interface (after `noTmux`)

**File: `src/config.ts`**
- Parse `jsonLogs` from YAML: `jsonLogs: (yaml.jsonLogs as boolean) ?? undefined`
- Set it on the config object

**File: `src/index.ts`**
- After loading config, apply `jsonLogs` from config when the CLI flag isn't set:
  ```typescript
  const jsonLogs = Bun.argv.includes("--json-logs");
  // ... after config load:
  if (jsonLogs || config.jsonLogs) {
    enableJsonLogs();
  }
  ```
- The CLI flag takes precedence because it's checked first and `enableJsonLogs()` is idempotent

**File: `src/config-watcher.ts`**
- In the hot-reload callback in `src/index.ts`, detect when `jsonLogs` changes and call `enableJsonLogs()` or `disableJsonLogs()` accordingly. This makes `jsonLogs` hot-reloadable.
- Add `jsonLogs` to the `diffConfigs()` function so changes are logged

### 2. Add `logWarn` function to logger

**File: `src/logger.ts`**
- Add a new exported `logWarn` function for non-task-scoped warnings (currently some code uses `log("WARN: ...")` which doesn't produce `"level": "warn"` in JSON mode):
  ```typescript
  export function logWarn(message: string, ...args: unknown[]): void {
    writeLog("WARN: ", message, args);
  }
  ```

### 3. Audit and fix log calls missing identifiers

The current logger already supports task-scoped logging via `logTask`, `logTaskWarn`, and `logTaskError`. The issue is that some call sites use `log`/`logError` when they have access to an identifier. Here's the audit:

#### `src/slack.ts` (4 fixes)
- **Line 34**: `logError("Slack notification failed: ...")` → Change `SlackNotifier.notify()` to accept an optional `identifier` param, then use `logTaskError(identifier, ...)` when available
- **Lines 77, 101**: `logError("Slack notification failed, retrying...")` in `onRetry` callbacks → Similarly thread identifier through
- **Line 136**: `logError("Slack notification failed: ...")` in the standalone `sendSlackNotification` function → This is a legacy function; it doesn't have task context, so leave as-is (it's only used with webhook URLs without task context)

Approach: Add an optional `identifier?: string` param to `SlackNotifier.notify()`. Store it and pass it to `sendViaWebApi` and `sendViaWebhook`. Use `logTaskError` when identifier is present, `logError` otherwise.

#### `src/hooks.ts` (already correct)
- `runHook` and `triggerHook` already accept an optional `identifier` parameter and use `logTask`/`logTaskWarn` when available. No changes needed.

#### `src/tracker/linear.ts` (2 fixes)
- **Line 127**: `log("findIssues failed, retrying...")` in the `onRetry` callback → This is a polling-level log, not task-scoped. However, it would be useful to include the trigger label for context. Leave as `log` since there's no single task identifier during polling.
- **Line 136**: `logError("Status not found for group...")` in `updateStatus()` → This is called with a `taskId` but no `identifier`. The method signature needs an optional `identifier` param added, or callers should pre-log. Since the tracker interface doesn't carry identifier, and this is called from `applyOutcome` which has access to `task.identifier`, the cleaner approach is to log at the call site. However, the tracker interface is used generically. Best approach: add optional `identifier` param to `updateStatus` in the interface and implementations.

Actually, looking more carefully: the tracker methods (`updateStatus`, `comment`, etc.) take `taskId` (the internal ID) not `identifier`. The identifier is available at the spawner level. The cleanest fix is:
- For `logError` in `updateStatus` (linear.ts:136): Add optional `identifier` param to the tracker interface's `updateStatus`. Pass it through from `applyOutcome`.
- For `logError` in Jira `updateStatus` (jira.ts:129, 141): Same treatment.

This is a larger interface change. A simpler approach: wrap the calls in `unified-spawner.ts` where `applyOutcome` is called, catching errors and logging with identifier. But `updateStatus` already silently returns on error in both trackers. The `logError` calls inside the trackers are the only logging — so the most practical fix is to add the optional identifier param.

**Updated approach**: Add optional `identifier?: string` as the last parameter to `updateStatus()` in the `IssueTracker` interface and both implementations. Use `logTaskError` when identifier is present.

#### `src/tracker/jira.ts` (2 fixes)
- **Line 129**: `logError("Jira: No transition to ...")` in `updateStatus()` → Use `logTaskError` when identifier available
- **Line 141**: `logError("Jira: Failed to transition...")` in `updateStatus()` → Same

#### `src/git.ts` (already correct)
- All git functions already take `identifier` and use `logTask`/`logTaskWarn`/`logTaskError`. No changes needed.

#### `src/runner/*.ts` (already correct)
- All runner files use `logTask`/`logTaskWarn`/`logTaskError` with the task identifier. No changes needed.

#### `src/unified-spawner.ts` (1 fix)
- **Line 563**: `logTaskError(task.identifier, "Failed to apply failure outcome")` — already correct, uses identifier.
- The file is well-instrumented. No changes needed.

#### `src/unified-watcher.ts` (check needed)
- Need to verify — likely uses `log` for polling-level messages (correct) and `logTask` for task-scoped (correct).

## Testing approach

1. **Unit tests**: Extend logger tests to verify `logWarn` produces warn-level JSON output, and `isJsonMode()` reflects state
2. **Config tests**: Verify `jsonLogs: true` is parsed and available on the Config object
3. **Config-watcher tests**: Verify `diffConfigs` detects `jsonLogs` changes
4. **Manual verification**: Run with `jsonLogs: true` in config and verify JSON output; toggle via config hot-reload and verify mode switches
5. **Slack tests**: Verify that when identifier is passed, error logs include it in JSON mode

## Risks and considerations

- The `updateStatus` interface change touches both tracker implementations but is additive (optional param) — no breaking changes
- The `notify()` signature change on SlackNotifier is also additive
- Hot-reload of jsonLogs is safe because `enableJsonLogs`/`disableJsonLogs` just flip a boolean — no state to migrate
- The CLI `--json-logs` flag must always take precedence; if the flag was passed, disabling via config reload should be a no-op
