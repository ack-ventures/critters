# ACK-273: Add `critters kill` command to stop a running critter

## Summary

Add a `critters kill` CLI command that can stop individual running critters, all running critters, or critters of a specific type. The command communicates with the daemon via the health HTTP API (same pattern as `critters stop`, `critters restart`, etc.). The daemon exposes a new `/kill` POST endpoint that looks up active critters and aborts them via their `AbortController`. Killed critters go through the existing failure outcome path (status update, cleanup, logging).

## Architecture

The implementation follows the established CLI-to-daemon communication pattern:

```
CLI (cli-kill.ts)
  │  GET /healthz → find matching critters
  │  POST /kill   → { identifiers: [...] }
  ▼
Health Server (health.ts)
  │  new /kill endpoint, calls trigger
  ▼
UnifiedSpawner (unified-spawner.ts)
  │  killByIdentifier() / killByType() / killAll()
  │  looks up activeCritterMap → finds AbortController → abort()
  ▼
Existing failure path
  │  applyOutcome(failure), cleanup, metrics, slack
```

### 1. `src/cli-kill.ts` (NEW)

New CLI command handler, following the pattern of `cli-stop.ts` and `cli-retry.ts`.

- `getKillConfig()`: Read `healthPort` and `dashboardToken` from config YAML (same helper pattern as `cli-stop.ts`).
- `runKill(args: string[])`: Main command function.
  - Parse arguments:
    - `critters kill <identifier>` — kill by identifier
    - `critters kill --all` — kill all running critters
    - `critters kill --type <name>` — kill all critters of a type
  - Validate: must have exactly one of `<identifier>`, `--all`, or `--type <name>`.
  - Query `GET /healthz` to fetch `activeCritterDetails`.
  - Determine which critters to kill:
    - By identifier: filter `activeCritterDetails` where `d.identifier === identifier`. Error if none found.
    - By type: filter where `d.critterType === typeName`. Error if none found.
    - All: use all `activeCritterDetails`. Error if none found.
  - Send `POST /kill` with body `{ identifiers: string[] }` (the list of issue identifiers to kill).
  - Print confirmation for each killed critter: `Killed <IDENTIFIER> (type: <type>, ran for <elapsed>)`.
  - On error (no match, daemon not running), print error and `process.exit(1)`.

## Detailed behavior

### Kill flow

1. CLI queries `/healthz` to get active critter details with elapsed times and types.
2. CLI filters to find matching critters (by identifier, type, or all).
3. If no matches: print error, exit 1.
4. CLI sends `POST /kill` with `{ identifiers: ["GAMES-65", ...] }`.
5. Daemon's spawner finds the task IDs for those identifiers, calls `abort()` on their AbortControllers.
6. The existing `runTask()` catch block handles the abort:
   - `timedOut` stays `false` (it's an abort, not a timeout — the abort happens via the AbortController but the timeout flag is only set by the timeout handler).
   - The error will be caught as an `AbortError` or similar — we need to check for `abortController.signal.aborted` to produce a clear error message like `"Killed via CLI"`.
7. The failure outcome is applied (`applyOutcome(failure)` sets issue status).
8. The critter is removed from `activeCritterMap` in the `finally` block.
9. `critters status` immediately reflects the removal.

### Abort vs Timeout distinction

Currently, `abortController.abort()` is called both on timeout and (with the new code) on kill. To distinguish:
- The timeout handler sets `timedOut = true` before aborting.
- For kills, `timedOut` remains `false`.
- In the catch block, when `!timedOut && abortController.signal.aborted`, the error message should be `"Killed via CLI"` instead of a generic error. This is a small addition to the existing catch block logic (around line 624-628).

### Graceful shutdown (SIGTERM → SIGKILL)

The `AbortController.abort()` mechanism already handles this. When a phase runner receives the abort signal:
- In `src/cli/spawn.ts`, the `spawnForPhase()` function checks `signal?.aborted` and kills the tmux pane.
- The subprocess (Claude CLI) receives SIGTERM when the pane is killed.
- If the process doesn't exit, tmux's `kill-pane` forcefully terminates it.

The 5-second SIGTERM→SIGKILL grace period is not currently implemented in the spawn layer. To add it:
- In `src/cli/spawn.ts`, where the abort signal handler kills the pane, add logic to first send SIGTERM to the process, wait 5 seconds, then SIGKILL/kill-pane if still running.
- However, since critters run in tmux panes (not direct child processes), `tmux kill-pane` is the mechanism. Tmux sends SIGHUP to the pane's shell process, which cascades. This is effectively a graceful kill already.
- **Decision**: The existing `tmux kill-pane` behavior is sufficient for graceful shutdown. No additional SIGTERM→SIGKILL logic needed — tmux handles process teardown.

### Error messages

- No running critter with identifier: `Error: No running critter with identifier "GAMES-99".`
- No running critters of type: `Error: No running critters of type "timber-create".`
- No running critters at all (for --all): `Error: No critters are currently running.`
- Daemon not running: `Critters daemon is not running (or health endpoint is disabled)` (same as `critters stop`).
