# ACK-238: Add Circuit Breaker for Tracker API Failures

## Summary

Implement a circuit breaker pattern that tracks consecutive poll failures per provider (Linear/Jira), backs off exponentially on repeated failures, sends Slack alerts on state changes, and exposes state via `/healthz`. This prevents the daemon from hammering a down API every poll cycle.

## Design

### Circuit Breaker States

- **CLOSED** — Normal operation. Polls proceed as usual. Consecutive failures are counted.
- **OPEN** — Backing off. Polls are skipped. A probe is attempted at each backoff interval.
- **HALF_OPEN** — A single probe poll is in flight. If it succeeds → CLOSED. If it fails → OPEN (with increased backoff).

### State Transitions

```
CLOSED --[N consecutive failures]--> OPEN
OPEN   --[backoff elapsed]---------> HALF_OPEN (single probe)
HALF_OPEN --[probe succeeds]-------> CLOSED
HALF_OPEN --[probe fails]----------> OPEN (backoff increases)
```

### Backoff Strategy

Reuse the exponential backoff math from `src/retry.ts` (line 37): `delay = min(baseDelay * 2^attempt, maxDelay)` with jitter. Applied at the circuit level:

- Base delay: `pollIntervalSeconds * 2` (default: 2 minutes with 60s poll interval, or 4 minutes with 120s)
- Max delay: 30 minutes (configurable)
- Each consecutive failure while OPEN doubles the backoff (capped at max)
- On recovery (HALF_OPEN → CLOSED), failure count resets to 0

**Concrete backoff example** (threshold=3, baseDelay=2min, maxDelay=30min):
- Failures 1-2: CLOSED, normal polling continues
- Failure 3: OPEN, exponent = 3-3 = 0, backoff = 2min * 2^0 = 2min
- Probe fails (failure 4): OPEN, exponent = 4-3 = 1, backoff = 2min * 2^1 = 4min
- Probe fails (failure 5): OPEN, exponent = 5-3 = 2, backoff = 2min * 2^2 = 8min
- Probe fails (failure 6): OPEN, exponent = 6-3 = 3, backoff = 2min * 2^3 = 16min
- Probe fails (failure 7): OPEN, exponent = 7-3 = 4, backoff = 2min * 2^4 = 30min (capped)
- Probe succeeds: CLOSED, failures reset to 0

## Files to Create

### `src/circuit-breaker.ts` — CircuitBreaker class

```typescript
export type CircuitState = "closed" | "open" | "half_open";

export interface CircuitBreakerOptions {
  failureThreshold: number;    // consecutive failures before opening (default: 3)
  baseDelayMs: number;         // base backoff delay in ms
  maxDelayMs: number;          // max backoff delay (default: 30 min)
  jitter?: boolean;            // add jitter to backoff (default: true)
  onStateChange?: (provider: string, from: CircuitState, to: CircuitState) => void;
}

export class CircuitBreaker {
  private state: CircuitState = "closed";
  private consecutiveFailures = 0;
  private lastFailureAt = 0;
  private nextRetryAt = 0;
  private provider: string;
  private options: CircuitBreakerOptions;

  constructor(provider: string, options: CircuitBreakerOptions);

  /** Update options (e.g., after config hot-reload) */
  updateOptions(options: Partial<CircuitBreakerOptions>): void;

  /** Returns true if the call should proceed, false if circuit is open and backoff hasn't elapsed */
  canProceed(): boolean;

  /** Record a successful call — resets failures, closes circuit */
  recordSuccess(): void;

  /** Record a failed call — increments failures, may open circuit */
  recordFailure(): void;

  /** Get current state for healthz */
  getStatus(): {
    state: CircuitState;
    consecutiveFailures: number;
    lastFailureAt: string | null;
    nextRetryAt: string | null;
  };
}
```

**Key implementation details:**

- `canProceed()`:
  - If CLOSED → return `true`
  - If OPEN and `Date.now() >= nextRetryAt` → transition to HALF_OPEN, return `true` (probe)
  - If OPEN and backoff not elapsed → return `false`
  - If HALF_OPEN → return `false` (probe already in flight)

- `recordSuccess()`:
  - If HALF_OPEN → transition to CLOSED, reset `consecutiveFailures` to 0, call `onStateChange`
  - If CLOSED → reset `consecutiveFailures` to 0 (no state change callback)
  - Note: When multiple types share a provider, after a HALF_OPEN probe succeeds and closes the circuit, subsequent types call `recordSuccess()` on an already-CLOSED breaker. This is benign — it just resets the already-zero failure count.

- `recordFailure()`:
  - Increment `consecutiveFailures`, set `lastFailureAt`
  - If CLOSED and `consecutiveFailures >= failureThreshold` → transition to OPEN, compute `nextRetryAt`
  - If HALF_OPEN → transition to OPEN with increased backoff
  - Backoff calculation: `min(baseDelayMs * 2^(consecutiveFailures - failureThreshold), maxDelayMs)` with optional jitter

- `getStatus()`: Returns a serializable snapshot for healthz

### `src/unified-watcher.ts` — Integrate circuit breaker into poll loop

**Constructor changes:**
- Accept circuit breakers as a parameter: `circuitBreakers: Map<string, CircuitBreaker>`
- Store as `this.circuitBreakers`

**`poll()` method changes (line 157-233):**

The current loop iterates over `config.critterTypes` and calls `tracker.findIssues()` for each type. Multiple types can share the same provider/tracker. The circuit breaker should be per-provider, not per-type.

Restructure the inner loop to check the circuit breaker before calling `findIssues()`:

```typescript
private async poll(): Promise<number> {
  let totalIssues = 0;

  for (const critterType of this.config.critterTypes) {
    const providerName = critterType.provider ?? this.config.provider;
    const breaker = this.circuitBreakers.get(providerName);

    // Check circuit breaker
    if (breaker && !breaker.canProceed()) {
      log(`[${critterType.name}] Skipping poll — ${providerName} circuit breaker is open`);
      continue;
    }

    const tracker = this.getTracker(critterType);
    try {
      const issues = await tracker.findIssues(critterType.trigger);
      breaker?.recordSuccess();
      totalIssues += issues.length;

      // ... existing issue processing logic unchanged ...
    } catch (err) {
      breaker?.recordFailure();
      logError(`[${critterType.name}] Poll failed for ${providerName}: ${err}`);
      // Don't rethrow — continue polling other types/providers
    }
  }

  return totalIssues;
}
```

**Important behavioral changes:**
1. The current `poll()` doesn't try/catch around `findIssues()` — if one type fails, the entire poll throws. The circuit breaker integration wraps each type's `findIssues()` in a try/catch so one provider's failure doesn't prevent polling other providers. This is a behavior improvement that aligns with the per-provider circuit breaker design.
2. When circuit is open, a log message is emitted for each skipped type so operators can distinguish "zero issues found" from "poll was skipped."
3. The `totalIssues` count only reflects types that were actually polled. The metric recorded in `start()` (`poll_completed`) will show the reduced count, which accurately reflects actual work done.

**Per-provider success/failure tracking note:** Multiple types may share a provider. When type A (linear) succeeds, `recordSuccess()` is called, which is correct — it confirms the provider is reachable. If type B (linear) then fails, `recordFailure()` increments the counter. The circuit breaker tracks provider health, not type-specific issues. A single type consistently failing while others succeed (e.g., due to a bad query) won't trip the breaker because successes reset the counter. This is intentional — the breaker is for provider-level outages, not type-specific query issues.

**`dryRunPoll()` changes:** No changes needed — dry run is a one-shot operation, circuit breaker doesn't apply.

**`updateConfig()` changes:** No changes needed — circuit breakers are per-provider and persist across config reloads.

### `src/index.ts` — Create and wire circuit breakers

**After tracker creation (line 268), before watcher creation (line 343):**

1. Import `CircuitBreaker` from `./circuit-breaker.js`
2. Create a `Map<string, CircuitBreaker>` with one breaker per provider
3. Configure the `onStateChange` callback to log and send Slack notifications
4. Pass the map to `UnifiedWatcher` constructor

```typescript
import { CircuitBreaker } from "./circuit-breaker.js";

// Create circuit breakers (one per provider)
const circuitBreakers = new Map<string, CircuitBreaker>();
for (const provider of trackers.keys()) {
  const breaker = new CircuitBreaker(provider, {
    failureThreshold: config.circuitBreaker?.failureThreshold ?? 3,
    baseDelayMs: config.pollIntervalSeconds * 2 * 1000,
    maxDelayMs: (config.circuitBreaker?.maxBackoffMinutes ?? 30) * 60 * 1000,
    onStateChange: (providerName, from, to) => {
      if (to === "open") {
        const msg = `⚠️ Circuit breaker OPEN for ${providerName} — backing off after ${breaker.getStatus().consecutiveFailures} consecutive failures`;
        logError(msg);
        // Use spawner's slack notifier if available (supports bot token + threading),
        // fall back to webhook-only sendSlackNotification
        if (slackNotifier?.isConfigured) {
          slackNotifier.notify(`__circuit_breaker_${providerName}__`, msg);
        } else {
          sendSlackNotification(config.slackWebhookUrl, msg);
        }
      } else if (to === "closed" && from !== "closed") {
        const msg = `✅ Circuit breaker CLOSED for ${providerName} — API recovered, resuming normal polling`;
        log(msg);
        if (slackNotifier?.isConfigured) {
          slackNotifier.notify(`__circuit_breaker_${providerName}__`, msg);
        } else {
          sendSlackNotification(config.slackWebhookUrl, msg);
        }
      }
    },
  });
  circuitBreakers.set(provider, breaker);
}
```

**Slack notification approach:** The `onStateChange` callback uses the `SlackNotifier` instance (if configured) for threaded bot-token notifications, with `sendSlackNotification()` (webhook-only) as fallback. This ensures circuit breaker alerts work regardless of which Slack integration is configured. The issue ID `__circuit_breaker_<provider>__` groups all circuit breaker messages for a provider into a single Slack thread.

**Note on config hot-reload and closures:** The `onStateChange` callback references `config.slackWebhookUrl` and `slackNotifier`. Since `config` is a `let` variable that gets reassigned during hot-reload, the closure captures the variable binding (not the value), so it will always read the current config. The `slackNotifier` reference should similarly be a `let` variable or the callback should read from a stable reference that gets updated on reload. The existing spawner already creates a `SlackNotifier` — we should either reuse that instance or create a module-level `let slackNotifier` that gets updated on config reload.

**Health server `getStatus` callback:** Include circuit breaker status:
```typescript
circuitBreakers: Object.fromEntries(
  [...circuitBreakers.entries()].map(([k, v]) => [k, v.getStatus()])
),
```

**Config hot-reload (line 446):** When config reloads:
1. Update existing breakers' options via `breaker.updateOptions()` if threshold/backoff changed
2. Create new breakers for any new providers added during reload
3. The `onStateChange` closure naturally picks up the new `config` value since it captures the `let` binding

**Manual poll trigger (`triggerPoll()`):** Manual polls via `/poll` endpoint go through the same `poll()` method and respect the circuit breaker. This is intentional — if the API is genuinely down, a manual trigger shouldn't spam it either. If operators need to force a check, they can observe the circuit state in `/healthz` and wait for the next probe window.

  maxBackoffMinutes: 30     # max backoff duration (default: 30)

Both fields are optional with sensible defaults. The circuit breaker is always enabled (no `enabled` flag) — with the default threshold of 3, it only activates after genuine repeated failures, so there's no reason to disable it.

## Edge Cases

- **Multiple types sharing a provider**: If types `create:linear` and `review:linear` share the Linear tracker, a single circuit breaker covers both. When the breaker opens, all Linear types are skipped. When it closes, all resume. This is correct — if the API is down, it's down for all types. During HALF_OPEN, only the first type to call `canProceed()` gets the probe; subsequent types for the same provider are skipped until the probe completes.

- **Mixed providers**: If Linear is down but Jira is up, only the Linear circuit opens. Jira types continue polling normally.

- **Config hot-reload**: If `circuitBreaker.failureThreshold` changes at runtime, existing breakers update via `updateOptions()`. New providers get new breakers.

- **Probe concurrency**: If multiple types share a provider and the backoff elapses, `canProceed()` transitions to HALF_OPEN on the first call and returns `false` for subsequent calls in the same poll cycle. This ensures only one probe per provider per poll cycle.

- **Slack notification failure**: Circuit breaker Slack alerts use `sendSlackNotification()` / `SlackNotifier.notify()` which already have retry logic and swallow errors. A Slack failure won't affect circuit breaker behavior.

- **Per-type vs per-provider failures**: A single type consistently failing (e.g., bad JQL query) while other types for the same provider succeed won't trip the breaker, because successes reset the counter. The breaker only trips on provider-level outages where all calls fail.
