# ACK-133: Add rollback backup before applying updates

## Summary

The updater in `src/updater.ts` performs an atomic rename (`renameSync`) to replace the current binary with the downloaded update, but creates no backup first. If the new binary is corrupted or broken, there's no way to recover. This plan adds a backup step before the rename and a restore step in the catch block.

## Files to modify

### 1. `src/updater.ts` — Add backup and restore logic

**Import changes** (line 1):
- Add `copyFileSync` to the existing `node:fs` import
- Add `import { dirname } from "node:path"` (new import)

**Backup before rename** — Insert between lines 148 and 149 (after `chmodSync`, before `renameSync`):

```ts
const backupPath = `${dirname(process.execPath)}/critters-v${currentVersion}.bak`;
copyFileSync(process.execPath, backupPath);
print(`Backup saved to ${backupPath}`);
```

Key details:
- Uses `copyFileSync` (not rename) so the original stays in place for the subsequent atomic `renameSync`
- The backup filename follows the pattern `critters-v{currentVersion}.bak` in the same directory as the executable
- Only the single most recent backup is kept — `copyFileSync` overwrites any existing file at that path
- Logs the backup path so the user knows where to find it

**Restore on failure** — In the catch block (lines 151–159), after the existing temp file cleanup and before the error log, add restoration logic:

```ts
try {
  if (existsSync(tempPath)) {
    unlinkSync(tempPath);
  }
} catch {
  // best-effort cleanup
}

// Attempt to restore from backup
const backupPath = `${dirname(process.execPath)}/critters-v${currentVersion}.bak`;
try {
  if (existsSync(backupPath)) {
    copyFileSync(backupPath, process.execPath);
    printError(`Restored previous binary from ${backupPath}`);
  }
} catch {
  // best-effort restore — if this fails too, the error message below still prints
}

printError(`Update failed: ${err instanceof Error ? err.message : String(err)}`);
```

Key details:
- The `backupPath` variable is re-derived in the catch block (rather than hoisting it) because we don't want to declare it outside the try — the catch block needs to work even if the error occurred before the backup was created
- The restore uses `copyFileSync` (not rename) so the backup file remains available for manual recovery if needed
- The restore is wrapped in its own try/catch — if restore also fails, we still log the original error
- `existsSync` check prevents attempting restore when no backup was created (e.g., error occurred during download, before the backup step)
