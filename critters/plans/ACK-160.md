# ACK-160: Fix shallow clone branch checkout in spawner resume path

## Summary

When a critter resumes work on an existing remote branch, the `git checkout -b <branch> origin/<branch>` command fails because the preceding `git fetch origin <branch>` in a shallow clone fetches into `FETCH_HEAD` but does NOT create the remote tracking ref `origin/<branch>`. The fix is a one-line change to the fetch command to explicitly create the remote tracking ref.

## Root Cause

In `src/spawner.ts:163`, the fetch command is:
```ts
await runCommand("git", ["fetch", "origin", branch], { cwd: workDir });
```

In a shallow clone (`git clone --depth 1`), `git fetch origin <branch>` puts the result in `FETCH_HEAD` only — it does not create `refs/remotes/origin/<branch>`. The subsequent checkout on line 167 then fails:
```ts
await runCommand("git", ["checkout", "-b", branch, `origin/${branch}`], { cwd: workDir });
```

## Fix

### File: `src/spawner.ts`

**Line 163** — Change the fetch args from:
```ts
const fetchResult = await runCommand("git", ["fetch", "origin", branch], { cwd: workDir });
```
to:
```ts
const fetchResult = await runCommand("git", ["fetch", "origin", `${branch}:refs/remotes/origin/${branch}`], { cwd: workDir });
```

This uses git's refspec syntax `<src>:<dst>` to explicitly map the remote branch into the expected remote tracking ref location. After this fetch, `origin/<branch>` will exist as a valid ref, and the `checkout -b` on line 167 will work correctly.

**No other lines change.** The checkout on line 167 remains:
```ts
const checkoutResult = await runCommand("git", ["checkout", "-b", branch, `origin/${branch}`], { cwd: workDir });
```

### Consistency with review-spawner

The `review-spawner.ts` (lines 200-216) already handles this correctly but uses a different approach — it fetches directly into a local branch:
```ts
["fetch", "origin", `${task.prBranch}:${task.prBranch}`]
```
then does `checkout` (without `-b`) on the local branch.

For the spawner, the `origin/<branch>` refspec approach is more appropriate because the spawner uses `checkout -b <branch> origin/<branch>` to create a new local tracking branch from the remote — the standard git workflow for starting local work from a remote branch.

## Files to Modify

| File | Change |
|---|---|

3. **Manual verification** — the fix can be verified by:
   - Creating a shallow clone of any repo
   - Running `git fetch origin <existing-branch>:refs/remotes/origin/<existing-branch>`
   - Confirming `git checkout -b <existing-branch> origin/<existing-branch>` succeeds

No new tests are needed — this is a one-line fix to a git command argument. The bug is in git CLI argument construction, not in application logic that can be meaningfully unit tested beyond what already exists.
