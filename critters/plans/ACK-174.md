# ACK-174: Include plan summary in PR description

## Summary

After the execution phase creates a PR via `gh pr create`, the PR body is generic. This change reads the plan file from `critters/plans/<identifier>.md` and updates the PR body to include the plan content under a `## Plan` section, giving reviewers immediate context.

## Approach

The change happens in **`src/runner/execution.ts`** — after `detectPr()` finds the PR URL, we read the plan file and update the PR body using `gh pr edit`. This keeps all PR-related logic in the execution runner and avoids modifying the spawner.

## Files to modify

### `src/runner/execution.ts`

1. **Add import**: `import { existsSync, readFileSync } from "node:fs"` at the top.

2. **Add a new function `updatePrWithPlan()`**:
   ```typescript
   async function updatePrWithPlan(
     workDir: string,
     prUrl: string,
     identifier: string,
   ): Promise<void> {
     const planFile = `${workDir}/critters/plans/${identifier}.md`;
     if (!existsSync(planFile)) {
       logTask(identifier, "No plan file found, skipping PR body update");
       return;
     }

     let planContent = readFileSync(planFile, "utf-8").trim();
     if (!planContent) return;

     // Truncate very long plans to keep PR body manageable
     const MAX_PLAN_LENGTH = 10000;
     if (planContent.length > MAX_PLAN_LENGTH) {
       planContent = planContent.slice(0, MAX_PLAN_LENGTH) + "\n\n*(plan truncated)*";
     }

     // Get current PR body
     const { code: viewCode, stdout: viewOut } = await runCommand(
       "gh",
       ["pr", "view", prUrl, "--json", "body"],
       { cwd: workDir },
     );
     if (viewCode !== 0) {
       logTask(identifier, "Could not read current PR body, skipping plan injection");
       return;
     }

     let currentBody = "";
     try {
       currentBody = JSON.parse(viewOut).body ?? "";
     } catch {
       // Best effort
     }

     const newBody = currentBody + "\n\n## Plan\n\n" + planContent;

     const { code } = await runCommand(
       "gh",
       ["pr", "edit", prUrl, "--body", newBody],
       { cwd: workDir },
     );
     if (code !== 0) {
       logTask(identifier, "Failed to update PR body with plan (non-fatal)");
     } else {
       logTask(identifier, "Updated PR body with implementation plan");
     }
   }
   ```

3. **Call `updatePrWithPlan()` in the `run()` method** after `detectPr()` returns a non-null URL (around line 68-70):
   ```typescript
   const prUrl = await detectPr(workDir, branch, task.identifier);

   // Include plan in PR body
   if (prUrl) {
     await updatePrWithPlan(workDir, prUrl, task.identifier);
   }

   return { spawn, data: { prUrl } };
   ```

## Design decisions

- **`gh pr edit` over modifying the prompt**: The execution prompt already tells Claude to create the PR with a specific body. Rather than modifying the prompt (which Claude might not follow reliably), we update the PR body programmatically after detection. This is deterministic and reliable.
- **`gh pr view` to get current body**: We preserve whatever body Claude wrote (including the Linear issue link and "Automated by Critters" text) and append the plan section.
- **Truncation at 10,000 chars**: Consistent with the `MAX_COMMENT_LENGTH` used elsewhere in the codebase (e.g., `unified-spawner.ts:406`). Plans are typically much shorter but this guards against edge cases.
- **Non-fatal failures**: If `gh pr edit` fails, we log and continue. The PR still exists; it just won't have the plan in the body. This matches the pattern used elsewhere (e.g., Slack notifications failing don't block the task).
- **No changes to planning phase**: The planning runner already writes and commits the plan file. We just read it.

## Edge cases

- **Plan file doesn't exist**: Skipped gracefully with a log message (e.g., custom types that don't use `builtin:planning`).
- **Empty plan file**: Skipped (no point adding an empty section).
- **Very long plan**: Truncated at 10,000 characters with a note.
- **PR not detected**: `updatePrWithPlan` is only called when `prUrl` is non-null, so this is already handled.
- **`gh pr edit` fails**: Logged as non-fatal; task still succeeds.

## Testing approach

1. **Manual/integration test**: Run a critter on a test issue and verify the PR body contains a `## Plan` section with the plan content.
2. **Unit test considerations**: The `updatePrWithPlan` function relies on filesystem (`existsSync`, `readFileSync`) and shell (`gh pr view`, `gh pr edit`), making it best suited for integration testing rather than unit tests. The function is small and straightforward enough that integration testing is sufficient.
3. **Verify truncation**: Create a plan file larger than 10,000 characters and confirm the PR body contains the truncated version with the `*(plan truncated)*` marker.
