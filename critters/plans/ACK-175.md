# ACK-175: Thread Slack notifications under initial message

## Summary

Currently, every lifecycle notification for a critter (task picked up, planning complete, PR created, etc.) is sent as a separate top-level Slack message. This floods the channel when multiple critters run concurrently.

This plan threads all updates for a given issue under the initial "task picked up" message by:
1. Switching from Slack incoming webhooks to the Slack Web API (`chat.postMessage`) when a bot token is available
2. Capturing the message `ts` from the initial notification
3. Storing `ts` per issue in an in-memory map
4. Passing `thread_ts` for subsequent notifications about the same issue
5. Falling back to the existing webhook behavior (no threading) when only `SLACK_WEBHOOK_URL` is configured

## Files to modify

### 1. `src/slack.ts` — Core notification logic

**Current state**: A single `sendSlackNotification(webhookUrl, message)` function that POSTs to a webhook URL. Format helpers for each notification type.

**Changes**:

- Add a new `SlackNotifier` class that encapsulates notification state:
  ```typescript
  export class SlackNotifier {
    private botToken: string | undefined;
    private channel: string | undefined;
    private webhookUrl: string | undefined;
    private threadMap = new Map<string, string>(); // issueId -> message ts
  }
  ```

- Constructor takes `{ webhookUrl?, botToken?, channel? }`. If `botToken` and `channel` are provided, use the Web API; otherwise fall back to webhook.

- Add a `notify(issueId: string, message: string)` method:
  - **Fire-and-forget pattern**: The entire method body is wrapped in a try/catch that logs errors via `logError` and never throws. This matches the existing `sendSlackNotification` behavior and is critical because all call sites `await notify()` without try/catch.
  - If neither `botToken`+`channel` nor `webhookUrl` is configured, return immediately (same as current `if (!webhookUrl) return`).
  - If using **Web API** (`botToken` + `channel`):
    - POST to `https://slack.com/api/chat.postMessage` with `Authorization: Bearer ${botToken}`
    - Payload: `{ channel, text: message, thread_ts?: string }`
    - If no `thread_ts` exists in `threadMap` for this `issueId`, send without `thread_ts` — this creates a new top-level message. Capture the response `ts` into `threadMap`.
    - If a `thread_ts` exists for this `issueId`, include it in the payload to thread the reply.
    - Parse the JSON response. Slack Web API returns HTTP 200 even on errors, with `ok: false` in the JSON body. Check `response.ok` (the JSON field) and throw on failure to trigger retry.
  - If using **webhook** (backward compat):
    - Same behavior as current `sendSlackNotification` — POST `{ text: message }` to the webhook URL
    - No threading (webhooks return a bare `ok` string, not JSON with `ts`)
  - Retry logic: Reuse the existing `withRetry` wrapper for both paths.

- Add a `clearThread(issueId: string)` method to remove entries from `threadMap` when an issue reaches a terminal state.

- Add a `get isConfigured(): boolean` getter for easy checking (returns true if either webhook or bot token is configured).

- Keep the existing `sendSlackNotification` function as-is for backward compatibility (it's simple enough and may be used elsewhere), but it will no longer be called from `unified-spawner.ts`.

- Keep all existing `format*` functions unchanged.

## Design decisions

1. **Class vs functions**: Using a `SlackNotifier` class instead of bare functions because we need to hold state (the `threadMap` and configuration). This is cleaner than module-level globals.

2. **No `initial` option**: The `notify` method auto-detects whether this is the first message for an issue by checking if `threadMap` has an entry. The first call for any `issueId` creates a top-level message and captures the `ts`; subsequent calls thread under it. This is simpler than an explicit `initial` flag and equally reliable since the map starts empty.

3. **Channel from env, not config YAML**: Slack channel is tightly coupled to the bot token credential, so it makes sense alongside the token in `.env` rather than in `critters.config.yaml`. This keeps secrets together.

4. **No `thread_ts` for webhook**: Slack incoming webhooks return a bare `ok` string, not JSON with `ts`. There's no way to get the message timestamp, so threading is only available with bot tokens.

5. **Cleanup in `finally`**: The `threadMap` cleanup happens in the `finally` block of `runTask`, which runs regardless of success or failure. This ensures no memory leaks. If the same issue is retried later, it gets a fresh top-level thread.

6. **Fire-and-forget error handling**: `notify()` catches all errors internally and logs them via `logError`, never throwing. This matches the existing `sendSlackNotification` behavior and is essential because all call sites await without try/catch — a thrown error would break task execution.

## Testing approach

- **Unit tests for `SlackNotifier`** (in `src/__tests__/slack.test.ts`):
  - Mock `fetch` to simulate Web API responses (`{ ok: true, ts: "1234.5678" }`)
  - Verify first call sends without `thread_ts`, captures `ts`
  - Verify subsequent calls include `thread_ts`
  - Verify webhook fallback sends without `thread_ts` and works unchanged
  - Verify `clearThread` removes entries so next call creates a new top-level message
  - Verify retry behavior on transient failures
  - Verify error handling when Slack API returns `ok: false` (logs error, doesn't throw)
  - Verify `notify` doesn't throw even when fetch itself rejects

- **Config tests** (in `src/__tests__/config.test.ts`):
  - Verify `slackBotToken` and `slackChannel` are loaded from env
  - Verify validation error when `SLACK_BOT_TOKEN` is set without `SLACK_CHANNEL`

- **Integration testing**:
  - Manual test with a real Slack bot token against a test channel
  - Verify messages thread correctly under the initial notification
  - Verify webhook-only mode still works (backward compat)

## Dependencies / setup

- No new npm dependencies needed — uses native `fetch` (available in Bun)
- Users who want threading need to:
  1. Create a Slack app with `chat:write` scope
  2. Install it to their workspace
  3. Get the bot token (`xoxb-...`)
  4. Add the bot to the target channel
  5. Set `SLACK_BOT_TOKEN` and `SLACK_CHANNEL` in `.env`
