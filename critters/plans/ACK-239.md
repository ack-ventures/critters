# ACK-239: Generate systemd service template from `critters init`

## Summary

Add optional systemd service file generation to `critters init` on Linux. After the existing setup flow completes, detect Linux and prompt the user to generate a systemd unit file at `~/.critters/critters.service`. Print copy/enable/start instructions afterward.

Also update `docs/self-hosting.md` to document the automated generation (replacing the current manual "create the file yourself" approach with a note about `critters init`).

## Files to modify

### 1. `src/init.ts`

**Changes:**

- Add a new constant `SERVICE_PATH = join(CRITTERS_DIR, "critters.service")` near the top with the other path constants.

- Add a `generateSystemdService()` function that:
  - Returns the unit file content as a string using a template literal
  - Uses `process.execPath` for `ExecStart` (the actual binary path)
  - Adds `--no-tmux --json-logs --config ~/.critters/config.yaml` flags to `ExecStart`
  - Sets `Restart=on-failure`, `RestartSec=10`
  - Sets `Environment=HOME=<homedir()>` so `.env` resolution works
  - Sets `Environment=PATH=/usr/local/bin:/usr/bin:/bin:<homedir()>/.local/bin` so tools are found
  - Sets `StandardOutput=journal`, `StandardError=journal`
  - Sets `WorkingDirectory=<homedir()>`
  - Sets `Type=simple`, `After=network.target`, `WantedBy=multi-user.target`

- Modify `runInit()`: after the `.env` handling (just before `printSummary()`), add a block that:
  1. Checks `process.platform === "linux"` — skip entirely on non-Linux
  2. Prompts: `"Generate a systemd service file? [y/N] "`
  3. If yes, calls `generateSystemdService()`, writes to `SERVICE_PATH`
  4. Prints the setup instructions:
     ```
     sudo cp ~/.critters/critters.service /etc/systemd/system/
     sudo systemctl daemon-reload
     sudo systemctl enable --now critters
     journalctl -u critters -f
     ```

- Modify `printSummary()`: add `Service: ~/.critters/critters.service` to the file listing if the service file exists (check with `existsSync(SERVICE_PATH)`).

**Important details:**
- The systemd prompt must appear in both code paths that call `printSummary()` — there are two: one early return (when user declines to overwrite `.env`) and one at the end. Extract the systemd logic into a helper called before `printSummary()` in both paths, or restructure so both paths converge. Looking at the code, the simplest approach is to add the systemd prompt inside `printSummary()` itself (before printing the summary), or create a `maybeGenerateSystemdService()` async helper and call it before each `printSummary()` call.

  Actually, the cleanest approach: make `printSummary` async, and add the systemd prompt at the beginning of `printSummary()`. This way both code paths get it. Rename to `finalize()` or keep as `printSummary` but make it async.

- The `readLine()` function already exists and can be reused.

## Template

The generated systemd unit file:

```ini
[Unit]
Description=Critters daemon
After=network.target

[Service]
Type=simple
ExecStart=<process.execPath> --no-tmux --json-logs --config <home>/.critters/config.yaml
Restart=on-failure
RestartSec=10
Environment=HOME=<home>
Environment=PATH=/usr/local/bin:/usr/bin:/bin:<home>/.local/bin
StandardOutput=journal
StandardError=journal
WorkingDirectory=<home>

[Install]
WantedBy=multi-user.target
```

## Edge cases

- **Non-Linux platforms**: Skip the prompt entirely (no message, no file). macOS doesn't use systemd.
- **Service file already exists**: Ask before overwriting (same pattern as `.env` handling).
- **`process.execPath` when running via `bun run`**: Will point to `bun` binary rather than `critters`. This is fine — the CLAUDE.md notes that auto-update only works with compiled binaries, and the user can edit the path. Could add a warning if `process.execPath` doesn't contain "critters", but this is a CONSIDER-level enhancement, not required.
- **User running as root**: The template uses the current user's home directory. If running `critters init` as root, `homedir()` returns `/root` which is correct for that case.

## Testing approach

- **Manual testing**: Run `critters init` on Linux, verify the prompt appears and the file is generated correctly. Run on macOS, verify no prompt appears.
- **Unit test for `generateSystemdService()`**: Could add a test that verifies the template output contains expected fields. However, the codebase doesn't appear to have tests for `init.ts` currently, so this matches existing patterns (no test file for init).
- **Dry-run verification**: Inspect the generated `.service` file to confirm paths are correct.

## Dependencies

None — this is purely additive. Uses only `node:fs`, `node:os`, and `node:path` which are already imported in `init.ts`.
