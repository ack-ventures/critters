# ACK-254: Add Configurable Auto-Update Timer

## Summary

Add an auto-update feature that periodically checks for updates and applies them when no critters are actively running. The feature introduces a new `autoUpdate` config section with `enabled` (default: true) and `intervalMinutes` (default: 1440 / 24h) fields. The auto-updater reuses existing update logic from `src/updater.ts` and restart logic from `src/index.ts`.

## Files to Create

### `src/auto-updater.ts`

New file containing the auto-update loop logic.

**Exports:**
- `startAutoUpdater(config, spawner, slackNotifier, restartFn): AutoUpdaterHandle`
- `AutoUpdaterHandle` interface with `stop()` and `updateConfig(config)` methods

**Logic:**
1. Guard: only activate when running as a compiled binary (same check as `checkForUpdate` — `process.execPath` basename is not `bun`/`bun.exe`) AND `VERSION !== "dev"`
2. Set up `setInterval` with `config.autoUpdate.intervalMinutes * 60 * 1000` ms
3. On each tick:
   a. Call `checkForUpdateAvailable(VERSION)` — a new helper that just checks if an update is available without downloading (returns `{ available: boolean, currentVersion: string, latestVersion: string } | null`)
   b. If no update available → return silently
   c. If update available → check `spawner.getActiveCount() === 0`
   d. If critters are active → `log("Auto-update: v{current} → v{latest} available but deferred — {N} critter(s) active")` and return
   e. If idle → `log("Auto-update: applying update v{current} → v{latest}...")`, send Slack notification, call `checkForUpdate(VERSION)` to download+apply, then call `restartFn()` to restart the daemon
4. `.unref()` the interval timer (following the cleanup interval pattern)

**Why a separate check function:** `checkForUpdate()` does both checking and downloading/applying in one call. We need to check availability first (to decide whether to proceed based on idle state) without downloading. We'll add a lightweight `checkForUpdateAvailable()` to `src/updater.ts`.

### `src/updater.ts`

Add a new exported function `checkForUpdateAvailable()` that performs only the version check (no download):

```typescript
export async function checkForUpdateAvailable(currentVersion: string): Promise<{
  available: boolean;
  currentVersion: string;
  latestVersion: string;
} | null> {
  // Same binary guard as checkForUpdate
  const execName = process.execPath.split("/").pop() ?? "";
  if (execName === "bun" || execName === "bun.exe") return null;
  if (currentVersion === "dev") return null;

  // Reset cached version to get fresh data
  _resetCachedLatestVersion();

  const latestVersion = await fetchLatestVersion();
  if (!latestVersion) return null;

  const cleanLatest = latestVersion.replace(/-.*$/, "");
  return {
    available: compareSemver(cleanLatest, currentVersion) > 0,
    currentVersion,
    latestVersion: cleanLatest,
  };
}
```

### `src/index.ts`

Wire up the auto-updater in the `main()` function, after the spawner and watcher are created but before `watcher.start()`:

1. Import `startAutoUpdater` from `./auto-updater.js`
2. Create `SlackNotifier` instance (already exists as `slackNotifier`)
3. Start the auto-updater:
   ```typescript
   const autoUpdater = startAutoUpdater(config, spawner, slackNotifier, restartDaemon);
   ```
4. Stop the auto-updater in the `shutdown()` handler:
   ```typescript
   autoUpdater?.stop();
   ```
5. In the config hot-reload handler, update the auto-updater:
   ```typescript
   autoUpdater?.updateConfig(newConfig);
   ```

The `restartDaemon` function is already defined in `index.ts` and handles re-exec logic.

**Placement:** After the `spawner.startPeriodicCleanup()` call and near the other interval-based setup, before `watcher.start()`.

## Config Example

```yaml
autoUpdate:
  enabled: true
  intervalMinutes: 1440  # check every 24 hours (default)
```

When `autoUpdate` is omitted from config, defaults apply: `enabled: true`, `intervalMinutes: 1440`.

## Edge Cases & Design Decisions

1. **Not a compiled binary / dev build**: Auto-updater silently does nothing (no interval created). Logged at startup as info.
2. **Critters active when update available**: Deferred with a log message. Will retry next interval tick.
3. **Update download fails**: `checkForUpdate()` already handles errors gracefully with logging. The auto-updater does not retry immediately — waits for next interval.
4. **Restart after update**: Uses the existing `restartDaemon()` function which handles both tmux and non-tmux cases.
5. **Config hot-reload**: Auto-updater supports `updateConfig()` to pick up changed interval/enabled settings. If disabled via hot-reload, the interval is cleared. If re-enabled, a new interval is started.
6. **Slack notification**: Sends a notification like "🔄 Auto-updating critters from v{old} to v{new}..." before applying the update.
7. **Cache invalidation**: `_resetCachedLatestVersion()` is called before each check so the auto-updater always gets fresh version info from GitHub (the cache is designed for single-session startup checks, not periodic polling).
8. **`autoUpdate` field omitted vs explicit**: When omitted, the auto-updater still runs with defaults (enabled=true, 1440min). To disable, set `autoUpdate.enabled: false` explicitly.

## Testing Approach

1. **Unit tests for `checkForUpdateAvailable()`**: Mock `fetch` to return various GitHub API responses, verify correct `available` flag and version parsing.
2. **Unit tests for `auto-updater.ts`**: Mock `checkForUpdateAvailable`, `checkForUpdate`, `spawner.getActiveCount`, and `restartFn`. Test scenarios:
   - No update available → no action
   - Update available, critters active → deferred (log message, no restart)
   - Update available, idle → update applied and restart called
   - Not a compiled binary → no interval created
   - `enabled: false` → no interval created
3. **Config validation**: Test that `intervalMinutes < 1` throws.
4. **Integration**: Manual test with `--dry-run` won't cover this, but the auto-updater can be tested by setting a short interval and running the compiled binary.
