# ACK-251: Dashboard — Show PR CI and Review Status in Recent Activity

## Summary

Add CI check status and PR review state inline in the dashboard's recent activity table and active critters table. For each entry with a `prUrl`, fetch the PR's CI status and review decision from GitHub, cache results with a short TTL, and display status icons next to the existing "PR" link.

## Design

### Data Flow

1. **New module `src/pr-status.ts`** — encapsulates GitHub PR status fetching and caching
2. **`src/dashboard.ts`** — consumes cached PR status data to render icons next to PR links
3. **`src/health.ts`** — calls the PR status fetcher before rendering the dashboard

### PR Status Fetching (`src/pr-status.ts`)

New file with:

```typescript
export interface PrStatus {
  ciStatus: "success" | "failure" | "pending" | "none";
  reviewStatus: "approved" | "changes_requested" | "pending" | "none";
}

// In-memory cache: prUrl → { status, fetchedAt }
const cache = new Map<string, { status: PrStatus; fetchedAt: number }>();
const CACHE_TTL_MS = 60_000; // 60 seconds

export async function getPrStatuses(prUrls: string[]): Promise<Map<string, PrStatus>> { ... }
```

**Implementation details:**
- Uses `Bun.spawn` to call `gh pr view <url> --json statusCheckRollup,reviewDecision` for each PR
- Deduplicates URLs before fetching
- Skips URLs already in cache and not expired
- Limits concurrent fetches: process at most 10 PRs per dashboard render to avoid hammering GitHub API
- Returns cached values for URLs that weren't refreshed
- On `gh` failure (e.g., repo not accessible), returns `{ ciStatus: "none", reviewStatus: "none" }` and caches the failure for the TTL to avoid retrying immediately

**Mapping `gh` output to status:**
- `statusCheckRollup`: Array of check objects with `status` and `conclusion` fields
  - All checks `conclusion === "SUCCESS"` → `"success"`
  - Any check `conclusion === "FAILURE"` or `"ERROR"` → `"failure"`
  - Any check `status !== "COMPLETED"` (i.e., still running) → `"pending"`
  - Empty array or null → `"none"`
- `reviewDecision`: String field
  - `"APPROVED"` → `"approved"`
  - `"CHANGES_REQUESTED"` → `"changes_requested"`
  - `""` or `null` → `"pending"` (if PR is open) or `"none"`

**New helper function `renderPrStatusIcons`:**
```typescript
function renderPrStatusIcons(prUrl: string, prStatuses?: Map<string, PrStatus>): string {
  if (!prStatuses) return "";
  const s = prStatuses.get(prUrl);
  if (!s) return "";
  const ciIcon = s.ciStatus === "success" ? "✅"
    : s.ciStatus === "failure" ? "❌"
    : s.ciStatus === "pending" ? "⏳"
    : "";
  const reviewIcon = s.reviewStatus === "approved" ? "👍"
    : s.reviewStatus === "changes_requested" ? "🔄"
    : s.reviewStatus === "pending" ? "⏳"
    : "";
  if (!ciIcon && !reviewIcon) return "";
  return ` <span class="pr-status" title="CI: ${s.ciStatus}, Review: ${s.reviewStatus}">${ciIcon}${reviewIcon}</span>`;
}
```

## Edge Cases

1. **No `gh` CLI available** — `getPrStatuses` catches spawn errors and returns `"none"` for both statuses, cached for TTL. Dashboard degrades gracefully (no icons shown, just the PR link as before).
2. **PR from inaccessible repo** — Same as above: `gh` returns an error, cached as `"none"`.
3. **Merged/closed PRs** — `gh pr view` works on merged/closed PRs. CI status and review decision are preserved and displayed correctly.
4. **No PR URL** — Existing behavior (em-dash) unchanged.
5. **Many PRs in recent activity** — Limited to 10 concurrent GitHub API calls. Remaining PRs use cached values or show no icons until next refresh.
6. **Dashboard auto-refresh (30s)** — Cache TTL is 60s, so roughly every other refresh will reuse cached values, cutting API calls in half.
7. **Rate limiting** — GitHub API rate limits are generous (5000/hr authenticated via `gh`). With max 10 PRs per render and 30s refresh interval, worst case is ~1200 calls/hr — well within limits.

## Testing Approach

1. **Manual testing with `gh` CLI:**
   - Create a test PR with passing/failing CI
   - Verify `gh pr view <url> --json statusCheckRollup,reviewDecision` returns expected data
   - Verify the parsing logic handles all states

2. **Unit tests for `src/pr-status.ts`:**
   - Mock `Bun.spawn` to return various `gh` outputs
   - Test cache hit/miss behavior
   - Test TTL expiration
   - Test error handling (gh not found, network error, invalid JSON)
   - Test deduplication of URLs
   - Test max concurrent limit (11 URLs → only 10 fetched)

3. **Dashboard rendering tests:**
   - Pass mock `prStatuses` map to `renderDashboard` and verify HTML contains status icons
   - Test `renderPrStatusIcons` with all status combinations
   - Test with empty/undefined `prStatuses` (graceful degradation)

4. **Integration test:**
   - Start health server, create metrics with `prUrl` values
   - Verify `/dashboard` response includes status icons for PRs that `gh` can resolve
