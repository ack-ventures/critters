# ACK-114: Structured incremental reviewer feedback

## Summary

Update the planning phase's reviewer subagent prompt within `buildPlanningPrompt()` in `src/prompt.ts` to produce structured, categorized feedback with severity levels (`MUST_FIX`, `SHOULD_FIX`, `CONSIDER`). Update the revision loop instructions so the planning Claude tracks which items were addressed across rounds, and the reviewer verifies resolution of prior `MUST_FIX` items.

This is purely prompt engineering — no new TypeScript functions, types, or modules are needed.

Replace the current step 4 (lines 86–87):

With a new step 4 that instructs the reviewer to use a structured output format:

```
4. Spawn a reviewer subagent using the Task tool with this prompt:
   "Review the implementation plan in critters/plans/${task.identifier}.md for the task: ${task.title}. Read the plan and the relevant source files it references. Check for: completeness, correctness, potential issues, missing edge cases, and whether it aligns with the codebase's patterns.

   Output your review in this exact format:

   REVIEW_STATUS: APPROVED

   OR:

   REVIEW_STATUS: NEEDS_REVISION

   ## Issues Found
   - [MUST_FIX] <description>
   - [SHOULD_FIX] <description>
   - [CONSIDER] <description>

   Severity levels:
   - MUST_FIX: Blocks approval. Correctness issues, missing requirements, security problems, or architectural mistakes that must be addressed.
   - SHOULD_FIX: Should be addressed but won't block approval alone. Code quality, pattern consistency, or minor gaps.
   - CONSIDER: Suggestions for improvement. Won't block approval.

   Approval requires zero MUST_FIX items. SHOULD_FIX items alone do not block approval but should be noted.

   If this is a re-review (round 2+), you will see a '## Previous Review Items' section in the plan. Verify that all prior MUST_FIX items have been adequately addressed. If a prior MUST_FIX was not addressed, re-list it as MUST_FIX with a note that it is unresolved from a prior round."
```

Key points:
- The `REVIEW_STATUS: APPROVED` sentinel still starts with `APPROVED` — the existing parsing in the spawner just checks for the plan file's existence, not the reviewer output directly. The reviewer output is consumed by the planning Claude itself.
- The reviewer is instructed to check for prior `MUST_FIX` resolution on re-review rounds.

#### Change B: Update the revision loop instructions (steps 5–6)

Replace the current steps 5–6 (lines 88–90):
```
5. If the reviewer provides feedback (not APPROVED), revise the plan file and spawn another reviewer
6. Repeat until the reviewer responds with APPROVED (max 3 review rounds — if not approved after 3, stop and exit with an error)
```

With expanded revision loop instructions:

```
5. If the reviewer output contains REVIEW_STATUS: NEEDS_REVISION, revise your plan:
   a. Add a "## Previous Review Items" section at the end of the plan file
   b. For each MUST_FIX and SHOULD_FIX item from the reviewer, quote the item and explain how you addressed it (or why you chose not to address a SHOULD_FIX). Format:
      > [MUST_FIX] <original item>
      Addressed: <explanation of what changed>
   c. Update the relevant sections of the plan to incorporate the fixes
   d. Spawn another reviewer subagent with the same prompt
6. Repeat until the reviewer responds with REVIEW_STATUS: APPROVED (max 3 review rounds — if not approved after 3, stop and exit with an error)
```

## Design decisions

1. **Keep `APPROVED` compatibility**: The structured format uses `REVIEW_STATUS: APPROVED` which still contains the word "APPROVED" that the planning Claude looks for. The spawner itself only checks for the plan file's existence and exit code.

2. **Tracking via plan file, not separate state**: Rather than introducing a separate tracking mechanism, the plan file itself carries the "## Previous Review Items" section. This is simple, visible in the committed plan, and requires no new code.

3. **Reviewer checks prior items**: Instead of the planning Claude self-certifying that it addressed items, the reviewer is instructed to verify prior `MUST_FIX` resolution. This creates a real feedback loop.

4. **Three severity levels match PR review patterns**: The `MUST_FIX`/`SHOULD_FIX`/`CONSIDER` pattern is consistent with how code reviews typically categorize issues, making it intuitive for the LLM.

5. **SHOULD_FIX alone doesn't block**: This prevents the reviewer from getting stuck in a loop over minor suggestions while still surfacing them.
