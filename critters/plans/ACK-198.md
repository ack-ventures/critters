# ACK-198: Add Live Log Viewing to Dashboard

## Summary

Add log viewing capabilities to the web dashboard: inline log previews for active critters, a dedicated full-page log viewer with SSE streaming, and API endpoints to serve log content. This involves changes to `src/health.ts` (new routes), `src/dashboard.ts` (inline expansion + log page rendering), and a new `src/log-resolver.ts` helper for shared log file resolution logic.

### 1. `src/log-resolver.ts` (NEW)

Extract shared log file resolution logic used by both `src/logs.ts` (CLI) and the new HTTP endpoints.

**Exports:**
- `resolveLogFile(workDir: string, identifier: string, phase?: string): string | null` — finds the log file path for a given identifier and optional phase. Reuses the pattern from `src/logs.ts`: scans `<workDir>` for dirs matching `<identifier>-<timestamp>` and `review-<identifier>-<timestamp>`, picks the newest, and maps phase names to file names (`.critter-output-plan.json`, `.critter-output-exec.json`, `.critter-output-review.json`). For custom phases, uses `.critter-output-<phaseName>.json`.
- `resolveAllPhases(workDir: string, identifier: string): Array<{ phase: string; logFile: string }>` — returns all available phases with their log file paths (for the phase tabs on the dedicated page).
- `resolveWorkDirForIdentifier(workDir: string, identifier: string): string | null` — finds the most recent work directory for an identifier.
- `stripAnsi(text: string): string` — strips ANSI escape codes using `/\x1b\[[0-9;]*m/g`.
- `readLogTail(logFile: string, lines: number): string` — reads the last N lines from a log file, strips ANSI codes.

**Phase-to-file mapping** (matching `src/logs.ts` and `src/claude.ts`):
```typescript
const PHASE_FILE_MAP: Record<string, string> = {
  planning: "plan",
  execution: "exec",
  review: "review",
};
// For custom phases, the tag IS the phase name
function phaseFileTag(phase: string): string {
  return PHASE_FILE_MAP[phase] ?? phase;
}
// Log file: `${workDir}/.critter-output-${tag}.json`
```

**Work directory resolution** (from `src/logs.ts:findWorkDir`):
- Scan `workDir` for entries matching `^<identifier>-\d+$` (critter dirs) and `^review-<identifier>-\d+$` (review dirs).
- Pick the newest by timestamp suffix.
- For active critters, also accept the `workDir` from `ActiveCritterDetail` directly (passed via the health status).

**Route: `GET /api/logs/<identifier>`**
- Query params: `phase` (optional), `tail` (optional, default 50)
- Logic:
  1. Check `getStatus().activeCritterDetails` for a matching identifier to get `workDir` directly.
  2. If not found in active critters, use `resolveWorkDirForIdentifier(config.workDir, identifier)` to find historical work dirs.

**Route: `GET /api/logs/<identifier>/stream`**
- Query params: `phase` (optional)
- SSE endpoint that streams new log lines in real-time.
- Logic:
  1. Resolve the log file path (same as above).
  2. Read current file size, seek to end.
  3. Poll the file every 500ms for new content (using `fs.statSync` to check size, then `fs.readFileSync` with appropriate offset for new bytes).
  4. For each new line, strip ANSI codes and send as `data: <line>\n\n`.
  5. Send a `data: {"event":"heartbeat"}\n\n` every 15s to keep the connection alive.
  6. Check if the critter is still active (via `getStatus()`) — if it's no longer in `activeCritterDetails`, send `event: done\ndata: {}\n\n` and close.
  7. Set headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`.
- Implementation: Use Bun's streaming response with a `ReadableStream` that pushes SSE events.

**Route: `GET /logs/<identifier>`**
- Serves the dedicated log page HTML.
- Logic:
  1. Get current `HealthStatus` via `getStatus()`.
  2. Call `renderLogPage(identifier, status, config.workDir)` from `src/dashboard.ts`.
  3. Return as `text/html`.

**Route matching:**

## Implementation Details

### Log file format
Log files are stream-json format (`.critter-output-<tag>.json`): one JSON object per line. Each line has a `type` field (`system`, `assistant`, `tool_use`, `tool_result`, `result`). For the web viewer, we send raw lines and let the client extract readable text from `assistant` messages (the `content` field).

Alternatively, the `/api/logs` endpoint can do server-side extraction — parse each JSON line, extract text content from assistant messages and tool names from tool_use events, and return a plain-text representation. This avoids sending large JSON payloads to the client and is simpler for the inline preview. The SSE stream sends raw JSON lines so the client can render them richly.

**Decision:** The `/api/logs` endpoint (used for inline preview) returns **pre-processed plain text** — extracts readable content from JSON lines. The SSE stream sends **raw JSON lines** so the dedicated page can render them with syntax highlighting / structure.

### ANSI stripping
Both endpoints strip ANSI codes using the regex `/\x1b\[[0-9;]*m/g` before sending to the client.
