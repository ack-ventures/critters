# ACK-112: Add Pagination to Linear Issue Queries

## Summary

Both `findCritterIssues()` and `findReviewIssues()` in `src/linear.ts` currently query Linear with `first: 20` and no pagination. If a team has more than 20 matching issues, the excess are silently dropped. This plan adds cursor-based pagination using the Linear SDK's built-in `fetchNext()` method on `Connection` objects, with a safety cap to prevent runaway loops.

## Files to Modify

### 1. `src/linear.ts`

**Extract a shared pagination helper**, then update both functions to use it.

#### Add `MAX_PAGINATED_ISSUES` constant

```ts
const MAX_PAGINATED_ISSUES = 200;
```

Place near the top of the file, after imports.

#### Add a generic `fetchAllNodes` helper

```ts
async function fetchAllNodes<T>(connection: { nodes: T[]; pageInfo: { hasNextPage: boolean }; fetchNext(): Promise<{ nodes: T[]; pageInfo: { hasNextPage: boolean }; fetchNext(): Promise<unknown> }> }): Promise<T[]> {
  while (connection.pageInfo.hasNextPage && connection.nodes.length < MAX_PAGINATED_ISSUES) {
    await connection.fetchNext();
  }
  if (connection.nodes.length >= MAX_PAGINATED_ISSUES) {
    log(`Warning: hit pagination cap of ${MAX_PAGINATED_ISSUES} issues — some issues may be skipped`);
  }
  return connection.nodes;
}
```

This is a private (non-exported) helper. The Linear SDK's `Connection.fetchNext()` mutates the connection in place — it appends fetched nodes to `connection.nodes` and updates `connection.pageInfo`. So after the loop, `connection.nodes` contains all accumulated results.

The type signature uses a structural interface rather than importing `Connection<T>` directly, keeping the dependency lightweight.

### 2. `src/__tests__/linear.test.ts` (new file)

#### Test cases

1. **Single page (no pagination needed)**: Mock `client.issues()` returning a connection where `pageInfo.hasNextPage` is `false`. Verify all nodes are returned.

2. **Multiple pages**: Mock a connection that returns `hasNextPage: true` on the first call, then `hasNextPage: false` after `fetchNext()`. Verify nodes from both pages are accumulated.

3. **Safety cap hit**: Mock a connection that always returns `hasNextPage: true` and accumulates nodes. Verify it stops at `MAX_PAGINATED_ISSUES` and logs a warning.

4. **Empty result set**: Mock returning zero nodes with `hasNextPage: false`. Verify an empty array is returned.

#### Mocking strategy

The test needs to mock the `client` module-level variable. The simplest approach is to use `bun:test`'s `mock.module()` or directly mock the `getClient()` function. The mock `client.issues()` should return an object that mimics the Linear SDK `Connection`:

```ts
function createMockConnection(pages: MockIssue[][]) {
  let pageIndex = 0;
  const allNodes: MockIssue[] = [...pages[0]];

  const connection = {
    nodes: allNodes,
    pageInfo: {
      hasNextPage: pages.length > 1,
      endCursor: pages.length > 1 ? "cursor-1" : null,
    },
    fetchNext: async () => {
      pageIndex++;
      if (pageIndex < pages.length) {
        allNodes.push(...pages[pageIndex]);
        connection.pageInfo.hasNextPage = pageIndex < pages.length - 1;
        connection.pageInfo.endCursor = pageIndex < pages.length - 1 ? `cursor-${pageIndex + 1}` : null;
      }
      return connection;
    },
  };

  return connection;
}
```

Each `MockIssue` needs `.id`, `.identifier`, `.title`, `.description`, and `.team` / `.project` properties (as the function resolves these). Use async getters or functions returning promises to match the SDK's lazy-loading pattern:

  title: string;
  description: string;

  project: Promise<{ id: string } | null>;

For `findReviewIssues` tests, `inverseRelations` is not called so it can be omitted from those mocks.

## Dependencies / Setup

- No new dependencies needed
- The Linear SDK's `Connection` class already has `fetchNext()` — no external pagination library needed

## Testing Approach

- Run via `bun test`
- Test both `findCritterIssues` and `findReviewIssues` pagination
- Test the safety cap (200 issues)
- Test edge cases: empty results, single page

## Risk / Edge Cases

- **`fetchNext()` mutates in place**: The Linear SDK's `Connection.fetchNext()` appends nodes to `connection.nodes` and updates `pageInfo` in place. The helper relies on this behavior — if the SDK changes this contract, the helper would break. This is a documented SDK behavior though.
- **API rate limits**: Paginating through many pages makes multiple API calls. With the 200-issue cap and default page size of 50, that's at most 4 API calls per query function. This is well within Linear's rate limits.
- **Concurrent modifications**: Issues could change between pages. This is inherent to any pagination approach and acceptable — the watcher already deduplicates by issue ID.
