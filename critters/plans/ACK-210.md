## Files to Create

### 1. `docs/self-hosting.md` — Deployment Guide

A comprehensive, step-by-step guide for deploying critters in production. Structured as follows:

#### Prerequisites
- **API keys:** Linear API key (`LINEAR_API_KEY`) and/or Jira credentials (`JIRA_HOST`, `JIRA_EMAIL`, `JIRA_API_TOKEN`)
- **Claude Code CLI:** Must be installed and authenticated. Link to https://docs.anthropic.com/en/docs/claude-code
- **GitHub CLI:** Must be installed and authenticated (`gh auth login`). Link to https://cli.github.com
- **Git:** Required for repo cloning
- **tmux:** Required unless running with `--no-tmux`
- **jq:** Required for stream output formatting

Note: The daemon checks prerequisites on startup (`src/prerequisites.ts`) — it verifies `claude --version` and `gh auth status`. Missing tools produce clear error messages.

#### Binary installation (bare metal)
- One-liner install from GitHub releases:
  ```
  curl -fsSL https://raw.githubusercontent.com/ack-ventures/critters/main/install.sh | bash
  ```
- The install script (`install.sh`):
  - Detects platform (darwin/linux) and architecture (arm64/x64)
  - Checks for prerequisites (curl, claude, gh, tmux, jq)
  - Downloads the latest release binary from GitHub
  - Installs to `/usr/local/bin` (or `~/.local/bin` if no sudo)
  - On fresh install, runs interactive config setup (`~/.critters/config.yaml` + `~/.critters/.env`)
- Manual download alternative: go to GitHub releases page, download `critters-darwin-arm64` or `critters-linux-x64`, `chmod +x`, move to PATH
- Initial setup: `critters init` (interactive — creates `~/.critters/` directory with config.yaml, .env, and prompt template files; source: `src/init.ts`)
- Config file resolution order (from `src/config.ts:resolveConfigPath`):
  1. `--config PATH` flag
  2. `./critters.config.yaml` (current working directory)
  3. `~/.critters/config.yaml`

#### Running as a service

**Option A: tmux (interactive)**
```bash
tmux new -s critters
critters
```
The daemon auto-launches inside tmux if not already in a tmux session (source: `src/index.ts:189-198`). The tmux session name defaults to "critters" (configurable via `tmuxSession`).

**Option B: systemd (headless)**
- Provide a sample `critters.service` unit file:
  - `ExecStart=/usr/local/bin/critters --no-tmux`
  - `Restart=always`, `RestartSec=10`
  - `Environment=HOME=/home/critters` (or appropriate user home)
  - Notes about ensuring `claude`, `gh`, `git`, `jq` are on the PATH for the service user
  - Must set `--no-tmux` flag — this logs to `~/.critters/critters.log` instead of tmux panes
- Note: `--no-tmux` mode (`src/index.ts:201-204`):
  - Ignores SIGHUP and SIGPIPE
  - Enables file-based logging via `initFileLogging()` with log rotation at `maxLogSizeMb` (default 10 MB)

**Option C: Docker** (note: no Dockerfile exists yet)
- Explain that there is no official Docker image currently
- Provide guidance on what a Dockerfile would need:
  - Base image with Bun runtime
  - Install claude CLI, gh CLI, git, jq
  - No tmux needed (use `--no-tmux`)
  - Volume mounts: `~/.critters/` (config, env, metrics), Claude auth directory, gh auth directory
- This is aspirational/community-contributed — the project ships as a binary, not a container

#### Updating
- `critters update` — checks GitHub releases, downloads and replaces binary in-place with checksum verification (SHA-256). Creates a backup (`critters-vX.Y.Z.bak`) before overwriting.
- Or re-run the install script: `curl -fsSL ... | bash` — detects existing install, updates in place
- Auto-update check runs on daemon startup (skip with `--skip-update`). Only works when running as a compiled binary (not `bun run`).

#### Log management
- **tmux mode:** Output goes to tmux panes (one per active critter phase)
- **`--no-tmux` mode:** Logs to `~/.critters/critters.log`, rotated at `maxLogSizeMb` (default 10 MB). Log rotation keeps up to 3 rotated files (`.1`, `.2`, `.3`).
- **`--json-logs` flag:** Structured JSON output (one object per line with `timestamp`, `level`, `message`, optional `identifier`)
- CLI log commands:
  - `critters logs <ID>` — view logs for a specific critter
  - `critters tail` — live-stream output from all active critters
  - `critters logs <ID> --follow` — tail a specific critter's log

#### Remote dashboard access

**Option 1: ngrok tunnel (built-in)**
- Configure in `critters.config.yaml`:
  ```yaml
  tunnel:
    enabled: true
    auth: "user:password"     # basic auth (recommended)
    domain: your-domain.ngrok-free.app  # static domain (optional, free tier gives one)
  ```
- Requires `ngrok` CLI installed (`src/tunnel.ts` checks for `ngrok version`)
- Daemon starts tunnel automatically, logs the public URL on startup
- Source: `src/tunnel.ts` — spawns `ngrok http <port>`, polls ngrok API at `127.0.0.1:4040` for public URL

**Option 2: Reverse proxy**
- Nginx example config: proxy_pass to `http://localhost:3847` with HTTPS via Let's Encrypt
- Caddy example config (simpler — automatic HTTPS)
- Note: the dashboard has no built-in authentication — protect it behind the reverse proxy or use the ngrok `auth` option

#### Monitoring & observability
- **Health endpoint:** `GET /healthz` returns JSON with uptime, version, active/queued counts per type, active critter details, metrics summary
  - Use for uptime monitoring (e.g., UptimeRobot, Datadog HTTP check)
- **Dashboard:** `GET /` or `/dashboard` — HTML dashboard with summary stats, 14-day charts, recent activity table. Auto-refreshes every 30s.
  - Port configurable via `healthPort` (default 3847, set to 0 to disable)
- **Metrics endpoint:** `GET /metrics` — JSON array of recent metric events (last 100)
- **Poll triggers:** `POST /poll` and `POST /review-poll` — trigger an immediate poll cycle without waiting for the next interval
- **Log viewer:** `GET /logs/<identifier>` — HTML page showing critter logs
- **Log API:** `GET /api/logs/<identifier>` — plain-text log tail (supports `?phase=planning|execution|review` and `?tail=N` query params)
- **Log streaming:** `GET /api/logs/<identifier>/stream` — SSE endpoint for live-streaming critter output (auto-closes when critter finishes)
- **Metrics storage:** Stored in `~/.critters/metrics.jsonl`. Events: task_started, task_completed, task_failed, review_started, review_completed, review_failed, poll_completed. Retained for `metricsRetentionDays` (default 90).
- **Slack notifications:** Set `SLACK_WEBHOOK_URL` for basic notifications, or `SLACK_BOT_TOKEN` + `SLACK_CHANNEL` for threaded notifications (all updates for an issue grouped under one message)
- **Cost alerts:** Set `costAlertThreshold` (USD) to get a Slack alert when a task exceeds the threshold
- **CLI monitoring:** `critters status` queries the health endpoint and displays a quick summary

Full HTTP endpoints table to include in docs:

| Endpoint | Method | Description |
|---|---|---|
| `/` or `/dashboard` | GET | HTML dashboard with summary stats, charts, and recent activity |
| `/healthz` | GET | JSON health check (uptime, version, per-type counts, active details, metrics) |
| `/metrics` | GET | JSON array of recent metric events (last 100) |
| `/poll` | POST | Trigger an immediate poll cycle |
| `/review-poll` | POST | Trigger an immediate review poll cycle |
| `/logs/<identifier>` | GET | HTML log viewer page for a specific critter |
| `/api/logs/<identifier>` | GET | Plain-text log tail (`?phase=...`, `?tail=N`) |
| `/api/logs/<identifier>/stream` | GET | SSE stream of live critter output |

#### Validating configuration
- `critters validate` — validates config file without starting the daemon. Checks: YAML parsing, field constraints, repo URL format, provider credential availability, critter type definitions.
- `critters --dry-run` — polls once, shows what would be picked up, exits without running anything. Use `--type NAME` to filter to a specific critter type.

### 2. `docs/configuration.md` — Configuration Reference

- Default search order: `./critters.config.yaml` → `~/.critters/config.yaml`
- Override with `--config PATH`
- Hot-reload: the daemon watches the config file and applies changes without restart (except `workDir`, `healthPort`, `tmuxSession`, and `tunnel.enabled` which are immutable at runtime — from `src/index.ts:368-386`)

- `~/.critters/planning-prompt.md`, `execution-prompt.md`, `review-prompt.md`

#### Hooks
- All hook names: `onTaskStarted`, `onPrCreated`, `onTaskFailed`, `onReviewStarted`, `onMerged`, `onNeedsChanges`, `onPlanningCompleted`, `onExecutionStarted`
- Environment variables available to hooks
- 30-second timeout, failures are warnings only (from `src/hooks.ts:17`)

#### Multi-provider setup (Linear + Jira)

#### Model guidance
