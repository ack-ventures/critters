# ACK-218: Add release-notes CLI command with build-time bundling

## Summary

Add a `critters release-notes` CLI subcommand that displays release notes for recent versions. Notes are fetched from GitHub at build time via a script and bundled into the compiled binary as a TypeScript constant. In dev mode (no build step), an empty array is shown.

## Files to Create

### 1. `src/release-notes.ts` (new — committed default)

Default file for local dev where the bundle script hasn't run:

```typescript
export const RELEASE_NOTES: Array<{ tag: string; date: string; name: string; body: string }> = [];
```

This file is committed to the repo. CI overwrites it before compilation.

### 2. `scripts/bundle-release-notes.js` (new)

Node script that uses `gh` CLI to fetch the last 10 releases and writes `src/release-notes.ts`. Uses `execFileSync` (not `execSync`) to avoid shell injection via tag names:

```javascript
const { execFileSync } = require("child_process");
const fs = require("fs");

try {
  const listJson = execFileSync(
    "gh",
    ["release", "list", "--limit", "10", "--json", "tagName,publishedAt,name"],
    { encoding: "utf8" }
  );
  const releases = JSON.parse(listJson);
  const notes = releases.map((r) => {
    try {
      const body = execFileSync(
        "gh",
        ["release", "view", r.tagName, "--json", "body", "-q", ".body"],
        { encoding: "utf8" }
      ).trim();
      return {
        tag: r.tagName,
        date: r.publishedAt.split("T")[0],
        name: r.name || r.tagName,
        body,
      };
    } catch {
      return {
        tag: r.tagName,
        date: r.publishedAt.split("T")[0],
        name: r.name || r.tagName,
        body: "",
      };
    }
  });
  fs.writeFileSync(
    "src/release-notes.ts",
    "export const RELEASE_NOTES: Array<{ tag: string; date: string; name: string; body: string }> = " +
      JSON.stringify(notes, null, 2) +
      ";\n"
  );
  console.log(`Bundled ${notes.length} release notes into src/release-notes.ts`);
} catch {
  // If gh is not available or fails, write empty notes
  fs.writeFileSync(
    "src/release-notes.ts",
    "export const RELEASE_NOTES: Array<{ tag: string; date: string; name: string; body: string }> = [];\n"
  );
  console.log("gh not available — wrote empty release notes");
}
```

Key safety detail: uses `execFileSync` instead of `execSync` to bypass shell interpretation, preventing any injection via tag names.

### 3. `src/cli-release-notes.ts` (new)

CLI command handler following the existing pattern (simple function, no config/tracker needed):

```typescript
import { RELEASE_NOTES } from "./release-notes.js";
import { VERSION } from "./version.js";

export function runReleaseNotes(): void {
  if (RELEASE_NOTES.length === 0) {
    console.log("No release notes available (dev build).");
    return;
  }

  for (const release of RELEASE_NOTES) {
    const current = release.tag === `v${VERSION}` ? " (current)" : "";
    console.log(`\x1b[1m${release.tag}${current}\x1b[0m — ${release.date}`);
    if (release.body) {
      console.log(release.body.split("\n").map((l) => `  ${l}`).join("\n"));
    }
    console.log();
  }
}
```

Note: This is a synchronous function (no async needed since data is a bundled constant). Uses bold ANSI escape for version tags and indents release body by 2 spaces, matching the codebase style of using raw ANSI codes (see `src/index.ts` line 269).

### 7. `Dockerfile` — Build stage

Add a step to copy the scripts directory and run the bundle script. Since `gh` CLI is not available in the build stage (`oven/bun:1`), and installing it there would bloat the build image, use a build arg to pass pre-generated release notes content instead. Add between the version embed and compile steps:

```dockerfile
COPY scripts/ scripts/

ARG RELEASE_NOTES_JSON=[]
RUN echo "export const RELEASE_NOTES: Array<{ tag: string; date: string; name: string; body: string }> = ${RELEASE_NOTES_JSON};" > src/release-notes.ts
```

The `docker` job in release.yml would pass the notes via `--build-arg RELEASE_NOTES_JSON='...'`. However, since the Docker job runs after the release job (which already has the artifacts built), and the release notes are a nice-to-have for the Docker image, the simpler approach is to just accept that Docker builds get empty release notes by default. The `RELEASE_NOTES_JSON` arg defaults to `[]`, so no change to the Docker workflow job is needed unless we want to populate it.

**Simplest Docker approach**: Just copy `scripts/` and run the script. It will gracefully fall back to empty notes since `gh` isn't in the build image. This requires no build-arg plumbing:

```dockerfile
COPY scripts/ scripts/
RUN node scripts/bundle-release-notes.js
```

Add after `COPY src/ src/` and before the version embed step. The script's catch-all fallback writes an empty array when `gh` fails.

### 8. `package.json` — Build script (optional improvement)

Update the `build` script to also bundle release notes before compilation:

```json
"build": "node scripts/bundle-release-notes.js && bun build --compile src/index.ts --outfile dist/critters"
```

This ensures local `bun run build` also attempts to bundle notes (will fall back to empty if `gh` is not available/authed).

## Design Decisions

1. **No .gitignore entry for `src/release-notes.ts`**: The default empty-array version is committed. CI overwrites it before compilation. This means the file always exists for dev/typecheck.

2. **scripts/ directory**: New directory. Using plain Node.js (not Bun-specific TypeScript) since the CI build environment has Node via `oven-sh/setup-bun` and it keeps the build script simple without needing TS compilation.

3. **Synchronous `runReleaseNotes()`**: Unlike most CLI commands that need async for config/tracker/network, this just reads a bundled constant. The dynamic `import()` in `index.ts` handles the async boundary.

4. **`execFileSync` over `execSync`**: Prevents shell injection. Tag names are passed as array arguments rather than interpolated into a shell command string.

5. **Docker builds get empty notes**: The bundle script gracefully falls back to empty notes when `gh` is unavailable. This is acceptable since Docker users can also run `critters release-notes` from a binary build, and the Docker image is primarily for the daemon, not CLI tools.

## Testing Approach

1. **`src/cli-release-notes.ts`**: Can be tested by importing `runReleaseNotes` and capturing stdout. Verify:
   - Empty array prints "No release notes available" message
   - Non-empty array prints formatted output with bold tags and dates
   - Current version tag gets "(current)" suffix

2. **`scripts/bundle-release-notes.js`**: Can be tested manually by running `node scripts/bundle-release-notes.js` in a repo with `gh` auth. Verify it writes valid TypeScript to `src/release-notes.ts`.

3. **Integration**: After CI builds, verify `critters release-notes` shows the bundled notes. Run `critters help` and verify the new command appears.

4. **Typecheck**: Run `bun run typecheck` to verify `src/release-notes.ts` is properly typed and imported.

## Dependencies

- No new runtime dependencies
- Build-time dependency on `gh` CLI (already available in GitHub Actions runners)
- New `scripts/` directory (first file in this directory)
