# ACK-237: Add Webhook Triggers for Linear and Jira

## Summary

Add optional `POST /webhook/linear` and `POST /webhook/jira` endpoints to the health server so Linear/Jira can push issue updates for near-instant pickup instead of waiting for the next poll cycle (up to 120s). Webhooks are additive — polling continues as the fallback.

## Design Overview

When a webhook fires, the daemon validates the signature, extracts the issue identifier from the payload, and triggers a targeted poll for just that issue. This reuses the existing polling infrastructure (dedup, blocker checks, enrichment, repo resolution) rather than building a parallel dispatch path.

### 3. `src/webhook.ts` — New file: webhook signature verification + payload parsing

This file contains:

#### Linear signature verification

Linear signs webhooks using HMAC-SHA256. The `Linear-Signature` header contains the hex-encoded signature of the raw request body.

```typescript
import { createHmac, timingSafeEqual } from "node:crypto";

export function verifyLinearSignature(body: string, signature: string, secret: string): boolean {
  const expected = createHmac("sha256", secret).update(body).digest("hex");
  // Use timing-safe comparison to prevent timing attacks
  if (expected.length !== signature.length) return false;
  return timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
}
```

#### Linear payload parsing

Linear webhooks send JSON with `action`, `type`, `data` fields. We care about:
- `type === "Issue"` with label or status changes
- Both `action === "create"` (issue created with trigger label) and `action === "update"` (label/status changed)
- Extract `data.identifier` (e.g., "ACK-123"), `data.labels` (array of label objects with `name`), `data.state.name` (status name)

```typescript
export interface LinearWebhookPayload {
  action: string;        // "create" | "update" | "remove"
  type: string;          // "Issue" | "Comment" | etc.
  data: {
    id: string;
    identifier: string;
    labels?: { id: string; name: string }[];
    state?: { name: string; type: string };
    team?: { key: string };
  };
  updatedFrom?: {
    labelIds?: string[];
    stateId?: string;
  };
}
```

Filter function: return the issue identifier if the webhook indicates a relevant issue event. Otherwise return `null`.

```typescript
export function extractLinearWebhookTrigger(
  payload: LinearWebhookPayload,
  critterTypes: CritterTypeConfig[],
): string | null
```

Logic:
1. If `type !== "Issue"`, return null
2. If `action === "remove"`, return null
3. If `action === "create"`: check if any current label name matches any critter type's `trigger.label`. If match, return `data.identifier`
4. If `action === "update"`: check if `updatedFrom` contains `labelIds` or `stateId` (indicates labels or status changed). If so, check if any current label name matches a trigger. If match, return `data.identifier`
5. Otherwise return null

#### Jira signature verification

Jira Cloud webhooks can be configured with a secret. When a secret is set, Jira includes an `X-Hub-Signature` header containing `sha256=<hex>` — an HMAC-SHA256 of the request body using the secret.

```typescript
export function verifyJiraSignature(body: string, signatureHeader: string, secret: string): boolean {
  const expected = createHmac("sha256", secret).update(body).digest("hex");
  const provided = signatureHeader.replace(/^sha256=/, "");
  if (expected.length !== provided.length) return false;
  return timingSafeEqual(Buffer.from(expected), Buffer.from(provided));
}
```

#### Jira payload parsing

Jira webhooks send `webhookEvent` and `issue` fields. We care about:
- `webhookEvent === "jira:issue_updated"` with label/status changes in the changelog
- `webhookEvent === "jira:issue_created"` for new issues created with a trigger label
- Extract issue key from `issue.key` (e.g., "PROJ-123")

```typescript
export interface JiraWebhookPayload {
  webhookEvent: string;
  issue: {
    id: string;
    key: string;
    fields: {
      labels: string[];
      status: { name: string };
    };
  };
  changelog?: {
    items: Array<{
      field: string;
      fieldtype: string;
      from: string | null;
      fromString: string | null;
      to: string | null;
      toString: string | null;
    }>;
  };
}
```

Filter function:

```typescript
export function extractJiraWebhookTrigger(
  payload: JiraWebhookPayload,
  critterTypes: CritterTypeConfig[],
): string | null
```

Logic:
1. If `webhookEvent === "jira:issue_created"`: check if any current label matches any critter type's `trigger.label`. If match, return `issue.key`
2. If `webhookEvent === "jira:issue_updated"`: check changelog items for `field === "labels"` or `field === "status"` changes. If changelog shows a relevant change and any current label matches a trigger, return `issue.key`
3. Otherwise return null

### 4. `src/unified-watcher.ts` — Add `pollForIssue(identifier)` method

Add a new public method to `UnifiedWatcher`:

```typescript
async pollForIssue(identifier: string): Promise<number> {
  // Don't acquire the polling lock — targeted polls are lightweight and
  // independent of the full poll cycle. The dedup mechanism (activeIssueIds)
  // prevents double-dispatch regardless of concurrent polls.
  return await this.pollSingleIssue(identifier);
}
```

Add private `pollSingleIssue(identifier)`:

The key challenge: `findIssueByIdentifier()` returns `IssueTrackerIssue` (minimal: id, identifier, statusName, labels, groupId), but dispatch needs a full `TrackerTask` (includes title, description, repoUrl, group, projectId, blockedBy, etc.).

**Solution**: Use `findIssues(trigger)` for each matching critter type and filter by identifier. This reuses the exact same code path as the regular poll and returns full `TrackerTask` objects.

```typescript
private async pollSingleIssue(identifier: string): Promise<number> {
  let dispatched = 0;

  for (const critterType of this.config.critterTypes) {
    const tracker = this.getTracker(critterType);

    // Use the same findIssues() as the regular poll, which returns full TrackerTask objects
    const issues = await tracker.findIssues(critterType.trigger);
    const matchingTask = issues.find((t) => t.identifier === identifier);
    if (!matchingTask) continue;

    // Reuse the exact dispatch logic from poll() — dedup, blockers, repo, enrichment
    // (extract the per-issue handling from poll() into a shared helper, or inline it)
    // ... same logic as the for-loop body in poll() ...

    dispatched++;
  }

  return dispatched;
}
```

This approach calls `findIssues()` which may return multiple issues, but we only act on the one matching the identifier. While slightly less efficient than a single-issue lookup, it:
- Returns full `TrackerTask` objects with all fields needed for dispatch
- Reuses the exact same tracker query logic (label + status filtering happens server-side)
- Avoids needing to add a new method to the `IssueTracker` interface

To avoid duplicating the dispatch logic, extract the per-issue handling from `poll()`'s inner loop into a private helper method `tryDispatch(task, critterType, tracker): Promise<boolean>` and call it from both `poll()` and `pollSingleIssue()`.

#### Per-identifier debounce

Add a simple debounce map to prevent rapid-fire polls for the same identifier:

```typescript
private webhookDebounce = new Map<string, number>(); // identifier → timestamp
private static WEBHOOK_DEBOUNCE_MS = 5_000; // 5 seconds
```

In `pollForIssue()`, check if the identifier was polled recently:

```typescript
const now = Date.now();
const lastPoll = this.webhookDebounce.get(identifier) ?? 0;
if (now - lastPoll < UnifiedWatcher.WEBHOOK_DEBOUNCE_MS) {
  return 0; // debounced
}
this.webhookDebounce.set(identifier, now);
```

### 5. `src/health.ts` — Add webhook endpoints

Add two new routes before the 404 fallback, following the existing POST route pattern:

#### `POST /webhook/linear`

```typescript
if (url.pathname === "/webhook/linear") {
  if (req.method !== "POST") {
    return new Response("Method Not Allowed", { status: 405 });
  }
  if (!webhookConfig?.linearWebhookSecret) {
    return Response.json({ error: "Linear webhooks not configured" }, { status: 404 });
  }

  const rawBody = await req.text();
  const signature = req.headers.get("Linear-Signature") ?? "";

  if (!verifyLinearSignature(rawBody, signature, webhookConfig.linearWebhookSecret)) {
    log("Webhook: Linear signature verification failed");
    return Response.json({ error: "Invalid signature" }, { status: 401 });
  }

  let payload: LinearWebhookPayload;
  try {
    payload = JSON.parse(rawBody);
  } catch {
    return Response.json({ error: "Invalid JSON" }, { status: 400 });
  }

  log(`Webhook: Linear event received — ${payload.type}/${payload.action}`);

  const identifier = extractLinearWebhookTrigger(payload, webhookConfig.critterTypes);
  if (identifier) {
    log(`Webhook: Triggering poll for ${identifier}`);
    // Fire-and-forget — don't block the webhook response
    triggers?.triggerPollForIssue?.(identifier).catch((err) => {
      logError(`Webhook poll failed for ${identifier}: ${err}`);
    });
    return Response.json({ ok: true, triggered: true, identifier });
  }

  return Response.json({ ok: true, triggered: false });
}
```

## Architecture Decisions

### Why targeted poll instead of direct dispatch?

The webhook handler doesn't dispatch directly to the spawner. Instead, it triggers a targeted poll via `pollForIssue()` which:
- Reuses all existing validation (dedup, blockers, repo resolution, enrichment)
- Doesn't duplicate any of the complex dispatch logic
- Prevents double-pickup via the existing `activeIssueIds` dedup mechanism
- Keeps the webhook handler thin — just signature verification and payload parsing

### Why `findIssues()` + filter instead of `findIssueByIdentifier()`?

`findIssueByIdentifier()` returns `IssueTrackerIssue` (minimal fields: id, identifier, statusName, labels, groupId), but dispatch requires a full `TrackerTask` (title, description, repoUrl, group, projectId, blockedBy, etc.). Rather than adding a new tracker interface method or changing the return type, we reuse `findIssues(trigger)` which already returns full `TrackerTask` objects and filter by identifier. This is slightly less efficient but maintains interface stability and reuses battle-tested code.

### Why fire-and-forget for the poll?

Webhook endpoints should respond quickly (Linear/Jira have timeout limits). The actual poll is kicked off asynchronously and the webhook returns immediately with `{ ok: true, triggered: true }`. Errors are logged but don't affect the webhook response.

### Why separate webhook secrets from dashboardToken?

The `dashboardToken` is for human/CI access to dashboard endpoints. Webhook secrets are provider-specific cryptographic signing secrets used for HMAC verification. They serve different purposes and should be configured independently.

### Why no polling lock in `pollForIssue()`?

Unlike `triggerPoll()` which acquires `this.polling`, `pollForIssue()` does not. This is intentional:
- A full poll takes time and uses the lock to prevent overlapping full scans
- `pollForIssue()` calls `findIssues()` for specific types and only acts on one issue — it's lightweight
- The `activeIssueIds` dedup mechanism is the true guard against double-dispatch
- If we locked on `this.polling`, webhook triggers during a regular poll would be silently dropped with no retry

### Why debounce per identifier?

A single label change can trigger multiple webhook events (Linear sends separate events for label add and status change). The 5-second debounce prevents redundant `findIssues()` calls for the same identifier in rapid succession.

## Testing Approach

1. **Unit tests for signature verification**: Test `verifyLinearSignature` and `verifyJiraSignature` with known payloads/secrets/signatures. Test timing-safe comparison. Test invalid signatures are rejected.

2. **Unit tests for payload parsing**: Test `extractLinearWebhookTrigger` and `extractJiraWebhookTrigger` with:
   - Issue created with trigger label → returns identifier
   - Label added (update) matching a trigger → returns identifier
   - Status changed (update) matching a trigger → returns identifier
   - Irrelevant event type (e.g., Comment) → returns null
   - Label added but not matching any trigger → returns null
   - Issue removed (`action === "remove"`) → returns null
   - Missing/malformed fields → returns null (no crash)
   - Jira `jira:issue_created` with trigger label → returns identifier

3. **Unit tests for `pollForIssue`**: Mock the tracker's `findIssues` and verify:
   - Issue matching trigger → dispatched
   - Issue not matching any trigger → not dispatched
   - Already active (dedup) → not dispatched
   - Blocked issue → not dispatched
   - Debounced (called twice within 5s for same identifier) → second call returns 0

4. **Integration test for webhook endpoints**: Use Bun's test server utilities to send POST requests to `/webhook/linear` and `/webhook/jira` with valid/invalid signatures and verify responses (200/401/400/404).

5. **Manual testing**: Configure a test Linear workspace with a webhook pointing at an ngrok tunnel, create/label an issue, verify near-instant pickup.

## Edge Cases

- **Webhook fires during active poll**: `pollForIssue` runs independently (no polling lock), but `activeIssueIds` dedup prevents double-dispatch
- **Rapid-fire webhooks**: Per-identifier debounce (5s) prevents redundant polls
- **Duplicate webhooks**: Dedup via `activeIssueIds` prevents double-dispatch
- **Webhook for non-existent issue**: `findIssues` won't return it → no action
- **Webhook for already-in-progress issue**: Dedup catches it
- **Malformed payload**: JSON parse wrapped in try/catch, returns 400
- **Invalid signature**: Returns 401, logged as warning
- **Webhook secret not configured**: Returns 404 (endpoint effectively doesn't exist)
- **Config hot-reload**: Webhook config object is mutated in-place during reload, so the health server always sees current values
- **Issue created with trigger label**: Both `action === "create"` (Linear) and `jira:issue_created` (Jira) are handled
