# ACK-241: Fix SIGTERM not releasing port during graceful shutdown

## Summary

When the daemon receives SIGTERM, it can fail to exit because:
1. `healthServer.stop()` (which calls `server.stop()`) doesn't forcibly close keep-alive connections, so the event loop stays alive
2. The 6-second fallback `setTimeout` is a regular timer that won't fire if the event loop is blocked by open handles
3. The shutdown handler can be called twice (once from SIGINT, once from SIGTERM) causing duplicate cleanup

The fix addresses all three issues: force-close connections, use an unref'd hard fallback timeout, and add an idempotency guard.

## Files to Modify

### 1. `src/health.ts` — Expose force-close capability

**Current** (line 546-548):
```ts
return {
  stop: () => server.stop(),
};
```

**Change**: Update the `stop()` method to also force-close idle connections. In Bun, `server.stop(true)` closes the server and immediately terminates all pending connections (including keep-alive). Update the return type accordingly.

```ts
return {
  stop: () => server.stop(true),
};
```

Also update the return type annotation from `{ stop: () => void }` to match (it's already `void`, so no change needed there — just the call argument).

### 2. `src/index.ts` — Fix shutdown handler (lines 668-683)

**Current**:
```ts
const shutdown = () => {
  log("Shutting down...");
  tunnelHandle?.stop();
  configWatcher?.stop();
  if (titleInterval) clearInterval(titleInterval);
  healthServer?.stop();
  watcher.stop();
  // Give running tasks a moment to clean up
  setTimeout(() => {
    log("Exiting");
    process.exit(0);
  }, 6000);
};

process.on("SIGINT", shutdown);
process.on("SIGTERM", shutdown);
```

**Change to**:
```ts
let shuttingDown = false;

const shutdown = () => {
  if (shuttingDown) return;
  shuttingDown = true;

  log("Shutting down...");
  tunnelHandle?.stop();
  configWatcher?.stop();
  if (titleInterval) clearInterval(titleInterval);
  healthServer?.stop();
  watcher.stop();

  // Graceful exit: give running tasks a moment to clean up
  setTimeout(() => {
    log("Exiting");
    process.exit(0);
  }, 6000);

  // Hard fallback: if the event loop is stuck (open handles, blocked I/O),
  // force exit after 10s. unref() ensures this timer alone won't keep the
  // process alive, but if other handles do, it will still fire and kill us.
  setTimeout(() => {
    log("Forced exit (shutdown timeout)");
    process.exit(1);
  }, 10_000).unref();
};

process.on("SIGINT", shutdown);
process.on("SIGTERM", shutdown);
```

Key changes:
- **Idempotency guard**: `shuttingDown` boolean prevents the handler from running twice when both SIGINT and SIGTERM arrive
- **`server.stop(true)`** (via health.ts change): Immediately drops all connections including keep-alive, so the server socket is released and the port is freed
- **Hard fallback with `.unref()`**: A 10-second `setTimeout(...).unref()` ensures the process exits even if open handles prevent the 6-second graceful timer from firing. `unref()` means this timer won't keep the event loop alive on its own, but if something else is keeping it alive, the timer will fire and force `process.exit(1)`
- **Exit code 1** for forced exit: Distinguishes between clean shutdown (exit 0) and forced shutdown (exit 1) for monitoring/debugging

## Dependencies

None. Both changes are self-contained within existing files.

## Testing Approach

1. **Manual testing**: Start the daemon, make a request to the health server (to establish a connection), then send SIGTERM. Verify the process exits within ~6 seconds and the port is released.

2. **Verify idempotency**: Send both SIGINT and SIGTERM in quick succession. Verify "Shutting down..." is logged only once.

3. **Verify forced exit**: If feasible, create a scenario where the event loop is blocked (e.g., a long-running SSE connection to `/api/logs/<id>/stream`) and send SIGTERM. Verify the process exits within 10 seconds via the hard fallback.

4. **Existing tests**: Run `bun test` to ensure no regressions. The health server tests in `src/__tests__/health.test.ts` should continue to pass since the `stop()` interface remains the same (just the internal behavior changes).
