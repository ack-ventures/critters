#### b. Implement `listTeams()`

Replace the stub at line 206-208 with:

```typescript
async listTeams(): Promise<TrackerTeam[]> {
  const resp = await this.request("/project/search?maxResults=100");
  const data = (await resp.json()) as { values: Array<{ id: string; name: string; key: string }> };
  return (data.values ?? []).map((p) => ({ id: p.key, name: p.name, key: p.key }));
}
```

**Key design decisions:**
- Uses `/project/search` (Jira REST API v3) which supports pagination and permissions filtering (unlike the older `/project` endpoint).
- Maps Jira projects to `TrackerTeam`, since Jira projects are the equivalent of Linear teams in this codebase — `groupId` throughout `JiraTracker` is already `project.key` (see `findIssues` line 73, `findIssueByIdentifier` line 100).
- Sets `id` to `key` (not numeric `id`) for consistency with how the codebase already uses `project.key` as the group identifier. This means `teamId` in `CreateIssueInput` will be a project key like `"PROJ"`, which is what `createIssue` needs for the `project: { key: ... }` field.
- `maxResults=100` matches the task description. This is sufficient for most Jira instances; pagination can be added later if needed.

**Imports:** `TrackerTeam` is already imported at line 4.

#### c. Implement `createIssue()`

Replace the stub at line 202-204 with:

```typescript
async createIssue(input: CreateIssueInput): Promise<CreatedIssue> {
  const resp = await this.request("/issue", {
    method: "POST",
    body: JSON.stringify({
      fields: {
        project: { key: input.teamId },
        summary: input.title,
        description: {
          type: "doc",
          version: 1,
          content: [{
            type: "paragraph",
            content: [{ type: "text", text: input.description }],
          }],
        },
        labels: input.labelNames,
        issuetype: { name: "Task" },
      },
    }),
  });
  const data = (await resp.json()) as { id: string; key: string; self: string };
  return {
    id: data.id,
    identifier: data.key,
    url: `https://${this.host}/browse/${data.key}`,
  };
}
```

**Key design decisions:**
- Description uses ADF (Atlassian Document Format) — consistent with the existing `comment()` method (line 131-147) which already constructs ADF in the same way.
- `labels` is passed as a string array — Jira auto-creates labels when applied (as noted by the existing `ensureLabel` no-op at line 198-200).
- `issuetype: { name: "Task" }` is a safe default — Task exists in all standard Jira workflows.
- The browse URL is constructed using `this.host` (the new stored field): `https://${this.host}/browse/${data.key}`.
- Uses the existing `this.request()` helper which handles auth headers, content-type, and error checking.

**Imports:** `CreateIssueInput` and `CreatedIssue` are already imported at line 4.

## Risks / Considerations

- **Issue type assumption:** Using `{ name: "Task" }` assumes a "Task" issue type exists. This is true for all standard Jira project templates (Scrum, Kanban, basic). Custom workflows with only non-standard issue types would fail. This matches the task spec and is an acceptable default.
- **Pagination:** `listTeams` fetches at most 100 projects. Organizations with 100+ Jira projects may need pagination, but this is rare and can be addressed separately.
- **No `maxResults` on `/project/search`:** The `values` field could theoretically be undefined if Jira returns an unexpected response shape — the `?? []` fallback handles this safely.
