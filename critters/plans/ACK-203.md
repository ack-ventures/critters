# ACK-203: Add MCP Server Support to Spawned Claude Instances

## Summary

Add support for passing `--mcp-config` (and optionally `--strict-mcp-config`) flags to the `claude` CLI when spawning critter instances. This allows critters to access external tools via MCP servers (databases, Slack, custom APIs, etc).

### 5. `src/claude.ts` — Add `resolveMcpConfig()` helper

Add a helper function in `src/claude.ts` (co-located with the spawn functions that consume it):

```typescript
import { homedir } from "node:os";
import { join } from "node:path";
import type { CritterTypeConfig } from "./critter-type.js";
import type { Config } from "./types.js";

export function resolveMcpConfig(
  critterType: CritterTypeConfig,
  config: Config,
): { mcpConfig: string[]; strictMcpConfig: boolean } {
  // Per-type mcpConfig fully replaces global (not merged)
  const raw = critterType.mcpConfig ?? config.mcpConfig;
  const strict = critterType.strictMcpConfig ?? config.strictMcpConfig ?? false;

  if (!raw) return { mcpConfig: [], strictMcpConfig: strict };

  const paths = Array.isArray(raw) ? raw : [raw];

  // Expand ~ to homedir (matches existing pattern in prompt-template.ts)
  const resolved = paths.map(p =>
    p.startsWith("~") ? join(homedir(), p.slice(1)) : p
  );

  return { mcpConfig: resolved, strictMcpConfig: strict };
}
```

Note: The `~` expansion uses `p.startsWith("~")` which is consistent with the existing pattern in `prompt-template.ts` (line 28) and `validate.ts` (line 211). This means `~otheruser/foo` would be incorrectly expanded, but this is an existing codebase convention and not something to diverge from in this change.

### 9. `src/validate.ts` — Validate MCP config paths

Add MCP config file validation after the existing skill file validation block (~line 220). Pattern follows the skill validation:

```typescript
// Validate MCP config paths
const globalMcp = yaml.mcpConfig;
if (globalMcp !== undefined) {
  if (typeof globalMcp !== "string" && !Array.isArray(globalMcp)) {
    errors.push("mcpConfig must be a string or array of strings");
  }
}
if (yaml.strictMcpConfig !== undefined && typeof yaml.strictMcpConfig !== "boolean") {
  errors.push("strictMcpConfig must be a boolean");
}

// Check file existence (warnings, not errors)
const mcpPaths: string[] = [];
if (typeof globalMcp === "string") mcpPaths.push(globalMcp);
else if (Array.isArray(globalMcp)) mcpPaths.push(...globalMcp as string[]);

for (const ct of critterTypes) {
  if (ct.mcpConfig) {
    const paths = Array.isArray(ct.mcpConfig) ? ct.mcpConfig : [ct.mcpConfig];
    mcpPaths.push(...paths);
  }
}

for (const mcpPath of mcpPaths) {
  const filePath = mcpPath.startsWith("~")
    ? join(homedir(), mcpPath.slice(1))
    : mcpPath;
  if (!existsSync(filePath)) {
    warnings.push(`MCP config file not found: ${filePath} (may exist at runtime)`);
  }
}
```

Note: MCP config missing files are **warnings** (not errors), unlike skill files which are errors. This is because MCP configs may exist on the runtime host but not the config validation host.

## Implementation Details

### Per-type vs global resolution

Per-type `mcpConfig` **fully replaces** global (not merged). This matches the task spec and is consistent with how `provider` works per-type. The resolution logic:

1. If `critterType.mcpConfig` is set, use it
2. Otherwise, fall back to `config.mcpConfig`
3. If neither is set, no `--mcp-config` flag is passed

Same for `strictMcpConfig`: per-type overrides global, defaulting to `false`.

### synthesizeDefaultTypes behavior

`synthesizeDefaultTypes()` constructs `CritterTypeConfig` objects for the built-in "create" and "review" types. Since `mcpConfig` and `strictMcpConfig` are optional fields on `CritterTypeConfig`, the synthesized types simply don't set them (they remain `undefined`). When `resolveMcpConfig()` runs, `critterType.mcpConfig` is `undefined`, so it falls back to `config.mcpConfig` — which is the correct behavior (global config applies to default types).

### --mcp-config flag syntax

The `--mcp-config` flag is repeated for each config file path. Multiple paths use `--mcp-config path1 --mcp-config path2`, not space-separated after a single flag. This is the standard CLI pattern for variadic arguments in the Claude CLI.

## Testing Approach

1. **Manual testing with `--dry-run`**: Verify config parsing works by adding `mcpConfig` to a test config and running `bun run src/index.ts --dry-run`
2. **Validate command**: Use `critters validate` with the new config fields to confirm parsing and warnings
3. **Unit-level verification**: Read the generated bash scripts (`.critter-run-*.sh` files in work dirs) to confirm `--mcp-config` flags appear correctly (one per path)
4. **Edge cases to verify**:
   - Global mcpConfig with no per-type override
   - Per-type override replacing global
   - Multiple paths in array form — each gets its own `--mcp-config` flag
   - `~` expansion in paths
   - `strictMcpConfig: true` at global level
   - Per-type `strictMcpConfig: false` overriding global `true`
   - Missing MCP config file (should warn, not error)
   - No mcpConfig set at all (no flags added — backward compatible)
   - `critters validate` shows warnings for missing MCP config files
   - `critters validate` shows errors for invalid mcpConfig types
