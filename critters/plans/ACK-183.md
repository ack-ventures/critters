# ACK-183: Add Config Hot-Reload Without Daemon Restart

## Summary

Add file watching on the config file (`critters.config.yaml` or `--config` path) so that changes are detected, validated, and applied to the running daemon without requiring a restart. In-flight critters are not interrupted — changes take effect on the next poll cycle.

## Design

### New file: `src/config-watcher.ts`

A `ConfigWatcher` class that:

1. Uses `fs.watch()` to monitor the resolved config file path for changes
2. Debounces change events (500ms) since editors often trigger multiple writes
3. On change, calls `loadConfig(this.configPath)` to re-parse and validate the config (must pass stored path to support `--config PATH`)
4. If validation fails, logs a warning and keeps the current config
5. If valid, computes a diff of what changed and calls a callback with the new config
6. Provides a `stop()` method to clean up the watcher

```typescript
export class ConfigWatcher {
  private watcher: fs.FSWatcher | null = null;
  private debounceTimer: Timer | null = null;
  private configPath: string;
  private onReload: (newConfig: Config) => void;

  constructor(configPath: string, onReload: (newConfig: Config) => void);
  start(): void;
  stop(): void;
}
```

The debounce works by clearing and resetting a timer on each `fs.watch` event. Only after 500ms of no events does it attempt a reload.

### Diff logging

A `diffConfigs(oldConfig, newConfig)` function in `src/config-watcher.ts` that compares the two configs and returns a human-readable summary of changes. It checks:

- Added/removed critter types (by name)
- Changed concurrency per type
- Changed poll interval
- Changed models, tools, timeout settings
- Changed provider
- Changed `repos`, `teamRepos`, `hooks`, `defaultAllowedTools`

Example output: `"Config reloaded: added type 'audit', updated concurrency for 'create' (2 → 5), poll interval 120s → 60s"`

### Modifications to `src/index.ts`

In the `main()` function, after creating the watcher/spawner:

1. Import and instantiate `ConfigWatcher` with the resolved config path
2. Pass a reload callback that:
   a. Preserves `noTmux` from the original config (runtime flag, not from file)
   b. Overrides immutable fields (`workDir`, `healthPort`, `tmuxSession`) with the current config's values, logging a warning for any that changed
   c. Determines if new trackers are needed (provider set changed)
   d. If new providers are needed, creates and initializes new trackers
   e. Calls `watcher.updateConfig(newConfig, newTrackers)` and `spawner.updateConfig(newConfig, newTrackers)`
   f. Ensures labels/statuses for any new types via `ensureLabelsAndStatuses()`
   g. Logs the diff summary
3. Add `configWatcher.stop()` to the `shutdown()` handler

### Modifications to `src/unified-watcher.ts`

Add an `updateConfig()` method to `UnifiedWatcher`:

```typescript
updateConfig(config: Config, trackers: Map<string, IssueTracker>): void {
  this.config = config;
  this.trackers = trackers;
}
```

This is safe because the `for...of` loop in `poll()` captures the `this.config.critterTypes` array reference once at iteration start. Even if `this.config` is swapped mid-poll (between awaits), the current poll completes with the old critter types array. The new config takes effect on the next poll cycle. Note: `getTracker()` reads `this.config.provider` as a fallback, so a mid-poll swap could theoretically use the new default provider — but since critter types almost always specify their own provider, and the new tracker map contains all needed providers, this is benign.

### Modifications to `src/unified-spawner.ts`

Add an `updateConfig()` method to `UnifiedSpawner`:

```typescript
updateConfig(config: Config, trackers: Map<string, IssueTracker>): void {
  this.config = config;
  this.trackers = trackers;
  // Drain queues for removed types
  this.drainRemovedTypeQueues(config);
}

private drainRemovedTypeQueues(config: Config): void {
  const activeTypeNames = new Set(config.critterTypes.map(ct => ct.name));
  for (const [typeName, queue] of this.queues.entries()) {
    if (!activeTypeNames.has(typeName) && queue.length > 0) {
      log(`Draining ${queue.length} queued tasks for removed type "${typeName}"`);
      for (const item of queue) {
        item.resolve({ success: false, error: `Critter type "${typeName}" was removed from config` });
      }
      this.queues.delete(typeName);
    }
  }
}
```

In-flight tasks retain their original `critterType` and `tracker` references (captured at dispatch time in `runTask()`), so they are unaffected. New dispatches will use the updated config. The `processQueue()` method reads `this.config.critterTypes` to find the type config, so updated concurrency limits take effect immediately for queue processing.

When a critter type is removed from the config, queued tasks for that type are drained with an error result. This resolves the dispatch Promise so the task ID is removed from `UnifiedWatcher.activeIssueIds`, allowing re-pickup if the type is later re-added.

### Modifications to `src/config.ts`

1. Export `resolveConfigPath()` so the watcher in `index.ts` can resolve the config file path and pass it to `ConfigWatcher`. Currently it's a private function.
2. Note: `loadConfig()` calls `mkdirSync(workDir)` as a side effect. When `workDir` changes in a reloaded config, this creates the new directory on disk even though we ignore the value. This is harmless (an empty directory in `/tmp` or similar) and the reload callback overwrites `newConfig.workDir` with the old value before applying.

### What does NOT change on reload

- `workDir` — changing this mid-run would break in-flight tasks. The reload callback overrides with the old value and logs a warning.
- `healthPort` — the HTTP server is already bound. Override with old value, log a warning.
- `tmuxSession` — already attached. Override with old value, log a warning.
- `noTmux` — runtime flag from CLI args, not config file.
- In-flight critters — they keep their original config/tracker references.
- Environment variables (API keys) — these come from `process.env`, not the config file. A provider change that needs different credentials will fail at validation time if the env vars aren't set.

### Tracker handling on provider change

When the set of needed providers changes (e.g., a new type uses Jira but no existing type did):

1. Compute needed providers from new config's `critterTypes`
2. Reuse existing tracker instances for providers that haven't changed
3. Create and `init()` new tracker instances for newly needed providers
4. Pass the merged tracker map to `updateConfig()` on watcher and spawner

Tracker instances for providers no longer needed are simply dropped (they hold no persistent connections — Linear SDK and Jira REST are stateless HTTP clients).

## Edge Cases

1. **Config file deleted** — `fs.watch` may fire an event. The `loadConfig()` call will throw, which we catch and log a warning.
2. **Rapid successive edits** — debounce (500ms) ensures we only reload once after edits settle.
3. **Invalid config** — caught by `validateConfig()`. Log warning, keep current config.
4. **Provider credentials missing** — `validateProviderCredentials()` inside `validateConfig()` catches this.
5. **workDir/healthPort/tmuxSession changed** — override with old values, log warning.
6. **Type removed while tasks are queued** — queued tasks are drained with an error, resolving their dispatch Promises. This clears them from `activeIssueIds` in the watcher.
7. **Type removed while tasks are in-flight** — in-flight tasks continue with their captured config. They'll complete normally. The running count decrements when done, and `processQueue()` for the removed type is a no-op since the queue was drained.
8. **fs.watch platform differences** — `fs.watch` is well-supported on macOS (kqueue) and Linux (inotube). Bun supports it. The `'change'` event is sufficient.
9. **loadConfig side effect** — `loadConfig()` creates `workDir` via `mkdirSync`. If `workDir` changed, the new directory is created on disk but the value is overridden back to the old one in the reload callback. The empty directory is harmless.

## Testing Approach

1. **Unit test for `diffConfigs()`** — verify it correctly identifies added/removed types, changed concurrency, changed poll interval, changed repos/hooks/tools, etc.
2. **Unit test for `ConfigWatcher`** — mock `fs.watch`, verify debouncing behavior, verify callback is called with new config, verify errors are caught and logged.
3. **Unit test for `drainRemovedTypeQueues()`** — verify queued tasks are resolved with error when their type is removed.
4. **Integration test** — manual testing:
   - Start daemon
   - Edit `critters.config.yaml` to change concurrency
   - Verify log message shows the change
   - Edit to add a new critter type
   - Verify log message shows the addition
   - Edit to make config invalid (e.g., `concurrency: -1`)
   - Verify warning is logged and daemon continues with old config
5. **Existing tests** — run `bun test` to ensure no regressions.
