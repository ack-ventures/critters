# ACK-115: Execution plan checkpointing

## Summary

Add checkpointing to the execution phase so that if it times out or fails, a retry can resume from where it left off instead of starting over. This involves four coordinated changes:

1. **Prompt instrumentation**: Tell Claude to maintain a `critters/plans/<ID>.checkpoint.md` file during execution, updating it after each major plan section is completed.
2. **Failure reporting**: Before cleanup on failure, read the checkpoint file and include progress info in the Linear failure comment.
3. **Resume-aware prompts**: When resuming, instruct Claude to read the checkpoint file and skip completed steps.
4. **Branch reuse on retry**: Detect an existing remote branch and check it out instead of creating a new one, enabling resume.

## Files to modify

- Add optional parameter: `options?: { resuming?: boolean }`

**Add checkpoint instructions (always, not just when resuming):**

After the existing editing guidance section, append a new `## Checkpointing` section to the prompt:

```
## Checkpointing
After completing each major section/step of the plan, update a checkpoint file at `critters/plans/${task.identifier}.checkpoint.md`.
The file should be a checklist mirroring the plan's sections, e.g.:
\`\`\`
- [x] Step 1: Set up the retry utility
- [x] Step 2: Migrate git.ts
- [ ] Step 3: Migrate spawner.ts
- [ ] Step 4: Add tests
\`\`\`
Commit the checkpoint file alongside your code changes (include it in the same commit, not separately).
```

**Add resume instructions (only when `options?.resuming` is true):**

Prepend to the prompt (before the plan reading instruction):

```
## Resuming from checkpoint
This is a RETRY of a previously failed attempt. A checkpoint file exists at `critters/plans/${task.identifier}.checkpoint.md`.
Read it first to see which steps were already completed. Skip completed steps and continue from where the previous attempt left off.
Review the existing code changes on this branch to confirm the completed steps are actually done before skipping them.
```

Also change the plan reading instruction when resuming — instead of "Execute the plan completely", say "Continue executing the plan from where the previous attempt stopped."

### 2. `src/spawner.ts` — Checkpoint reading on failure + branch reuse on retry

**A. Read checkpoint on failure (in the `catch` block, before cleanup):**

After `uploadFailureLogs` and before posting the failure comment (around line 273), add:

```typescript
// Read checkpoint file if it exists
let checkpointStatus = "";
const checkpointFile = `${workDir}/critters/plans/${task.identifier}.checkpoint.md`;
if (existsSync(checkpointFile)) {
  try {
    const checkpointContent = readFileSync(checkpointFile, "utf-8");
    const completed = (checkpointContent.match(/- \[x\]/gi) || []).length;
    const total = (checkpointContent.match(/- \[[ x]\]/gi) || []).length;
    if (total > 0) {
      checkpointStatus = `\n\nCheckpoint: completed ${completed}/${total} steps before failure.`;
    }
  } catch {
    // Best effort — don't fail the failure handler
  }
}
```

Then append `checkpointStatus` to `failComment`.

Also add the checkpoint file to the `logFiles` array in `uploadFailureLogs` so it gets uploaded as an attachment:

```typescript
{ path: `${workDir}/critters/plans/${task.identifier}.checkpoint.md`, name: `${task.identifier}-checkpoint.md` },
```

**B. Branch reuse logic (in `runTask`, before `createBranch`):**

After the `shallowClone` call (line 121) and before `createBranch` (line 124), add logic to detect and reuse an existing remote branch:

```typescript
// Check if branch already exists remotely (indicates a retry)
let resuming = false;
const lsRemote = await runCommand("git", ["ls-remote", "--heads", "origin", branch], { cwd: workDir });
if (lsRemote.code === 0 && lsRemote.stdout.trim().length > 0) {
  // Branch exists — check it out for resume
  logTask(task.identifier, `Branch ${branch} exists remotely, checking out for resume`);
  const fetchResult = await runCommand("git", ["fetch", "origin", branch], { cwd: workDir });
  if (fetchResult.code !== 0) {
    throw new Error(`Failed to fetch existing branch: ${fetchResult.stderr}`);
  }
  const checkoutResult = await runCommand("git", ["checkout", "-b", branch, `origin/${branch}`], { cwd: workDir });
  if (checkoutResult.code !== 0) {
    throw new Error(`Failed to checkout existing branch: ${checkoutResult.stderr}`);
  }
  resuming = true;
} else {
  // No existing branch — create a new one
  await createBranch(workDir, branch, task.identifier);
}
```

Note: Since the clone is `--depth 1`, we need the explicit `fetch` to get the branch. The `git checkout -b branch origin/branch` creates a local tracking branch from the fetched remote.

**C. Pass `resuming` to execution prompt:**

Change the `buildExecutionPrompt` call (around line 194) to pass the `resuming` flag:

buildExecutionPrompt(task, execAllowedTools, { resuming })

**D. Update Linear comment when resuming:**

After the branch reuse check, if `resuming` is true, update the Linear comment:

## Edge cases

1. **First run (no checkpoint exists)**: Claude creates the checkpoint file from scratch during execution. The `resuming` flag is `false`, so no resume instructions are added.

2. **Retry with checkpoint**: Branch exists remotely → checked out → `resuming: true` → Claude reads checkpoint and skips completed steps.

3. **Retry without checkpoint (failed before any checkpoint)**: Branch may exist but checkpoint file doesn't. Claude gets resume instructions but finds no checkpoint file, so it starts from the beginning (plan is still there from the planning phase commit).

4. **Checkpoint file with no completed steps**: `completed` count is 0, so the failure comment says "completed 0/N steps" — accurate.

5. **Shallow clone limitations**: `git clone --depth 1` only gets the default branch. We need `git fetch origin <branch>` to get the critter branch before checkout. This is handled explicitly.

6. **Race condition on branch name**: The `branchName()` function is deterministic (based on identifier + title), so retries always target the same branch. The `activeIssueIds` set in `Watcher` prevents duplicate dispatches for the same issue.

7. **Multiple retries**: Each retry checks out the latest state of the remote branch, which includes all previous progress. Checkpoint file accumulates completed steps.

8. **Planning phase on retry**: The planning phase still runs, but the plan file already exists from the previous attempt's commit. The planning Claude will see the existing plan and may just approve it again, or the plan file exists in the branch from the first run. This is acceptable — the planning phase is relatively cheap and ensures the plan is still valid.

   **Optimization**: If the plan file already exists in the checked-out branch, we could skip planning entirely. However, this adds complexity and the planning phase acts as a validation step. The current design keeps it simple.

9. **Work directory naming**: Work directories use `${task.identifier}-${Date.now()}`, so retries get fresh directories. The branch is what carries state across retries, not the work directory.

## Testing approach

- **Unit tests for prompt changes** (`src/__tests__/prompt.test.ts`):
  - `buildExecutionPrompt()` without `resuming` includes checkpoint section but NOT resume section
  - `buildExecutionPrompt()` with `{ resuming: true }` includes both checkpoint and resume sections
  - Verify the checkpoint file path uses the correct task identifier

- **Unit tests for checkpoint parsing** (new test in `src/__tests__/spawner.test.ts` or inline):
  - Parse a checkpoint file with mixed `[x]` and `[ ]` entries → correct counts
  - Parse an empty/missing checkpoint → graceful fallback (no crash)

- **Integration testing** (manual):
  - Run a critter, let it succeed → verify checkpoint file is committed alongside code
  - Run a critter, kill it mid-execution → verify checkpoint status appears in failure comment
  - Re-trigger the same critter → verify it detects existing branch and resumes
