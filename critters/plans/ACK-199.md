# ACK-199: Expand README with general-purpose use cases and examples

## Summary

Add a "Use Cases" section to both `CLAUDE.md` and `README.md` that positions critters as a general-purpose agent orchestrator, not just a code PR bot. The section showcases five example use cases with config snippets.

## Files to modify

### 1. `CLAUDE.md`

**Location:** Insert a new `## Use Cases` section immediately after the existing `## Custom Critter Types` section (after line 184, before `## Multi-Provider Support` on line 186).

**Content to add:**

#### Intro paragraph
A brief paragraph explaining that critters is a general-purpose agent orchestrator. The built-in `create` and `review` types are just defaults. Any workflow matching "watch for trigger -> run Claude with a prompt -> produce an outcome" can be built with custom critter types, no code changes needed.

#### Five use cases, each with:
- 2-3 sentence description
- Minimal `critterTypes` YAML config snippet (just the type entry, not full config)
- A note on model choice

**Use case 1: Issue triage bot**
- Reads new issues, adds labels, sets priority, posts a triage summary comment
- Read-only tools, sonnet model (fast, cheap, good for analysis)
- Config: single phase, custom prompt, read-only tools, short timeout

**Use case 2: Documentation writer**
- Watches for "Docs Needed" label, reads relevant code, generates/updates markdown docs
- Can write files and create PRs (needs `repo.branch: true`)
- Opus model for multi-step reasoning and writing quality

**Use case 3: Security auditor**
- Scans repo for OWASP top 10 vulnerabilities, dependency issues, secrets
- Read-only, produces `.critter-report.md` with findings
- Sonnet model (good cost/quality tradeoff for analysis)

**Use case 4: Test generator**
- Picks up issues labeled "Needs Tests", reads implementation, writes missing tests
- Creates a PR with new tests (needs `repo.branch: true`, write tools)
- Opus model for code generation quality

**Use case 5: Multi-step workflow**
- Shows how to chain critter types using Linear/Jira blocking relationships
- Example: a "plan" critter creates a plan and spawns sub-tickets, then "implement" critters pick up each sub-ticket
- Mention that `blocks`/`blockedBy` fields on Linear issues enforce ordering automatically
- This one is more of a pattern description with two config snippets (plan type + implement type)

**Style notes:**
