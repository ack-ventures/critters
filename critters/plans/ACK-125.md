# ACK-125: Add `critters init-repo` command for per-repo config

## Summary

Add a `critters init-repo` CLI subcommand that scaffolds a `.critters.yaml` file in the current directory (must be a git repo), and teach the daemon to read this per-repo config after cloning. The per-repo config is **additive only** — it can add tools and custom prompts but cannot remove daemon defaults.

## Files to Create

### 1. `src/init-repo.ts` — CLI scaffolding logic

New file with a single named export `runInitRepo()`:

- Run `git rev-parse --git-dir` via `Bun.spawnSync` (or import `runCommand` from `utils.ts`) to verify the current directory is a git repo. If it fails, print an error and exit with code 1.
- Check if `.critters.yaml` already exists using `Bun.file(".critters.yaml").exists()` (async) or `existsSync`.
  - If it exists: print `.critters.yaml already exists` and `process.exit(0)`.
- Write the default template to `.critters.yaml` using `Bun.write()` or `writeFileSync`. Template content (commented-out defaults):

```yaml
# Critters per-repo configuration
# This file is read by the critters daemon after cloning this repo.
# All fields are optional — omit or leave empty to use daemon defaults.

# Extra tools the critter is allowed to use (merged with daemon defaults)
# extraAllowedTools:
#   - "Bash(python:*)"
#   - "Bash(pip:*)"

# Custom prompt appended to the planning phase
# planningPrompt: |
#   Follow the patterns in src/utils/ for new utilities.
#   Always add tests in __tests__/.

# Custom prompt appended to the execution phase
# executionPrompt: |
#   Run `npm test` before committing.

# Custom prompt appended to the review phase
# reviewPrompt: |
#   Pay extra attention to SQL injection risks.
```

- Print `Created .critters.yaml — edit it to customize critter behavior for this repo`

### 2. `src/repo-config.ts` — Per-repo config loader

New file with:

**Type** (named export):
```typescript
export type PerRepoConfig = {
  extraAllowedTools?: string[];
  planningPrompt?: string;
  executionPrompt?: string;
  reviewPrompt?: string;
};
```

Note: Named `PerRepoConfig` to avoid collision with the existing `RepoConfig` type in `types.ts` (which represents the daemon's per-project config from `critters.config.yaml`).

**Function** (named export):
```typescript
export function loadRepoConfig(workDir: string): PerRepoConfig | null
```

- Check for `.critters.yaml` at `path.join(workDir, ".critters.yaml")`
- If the file doesn't exist, return `null`
- Read and parse with `yaml` package (already a dependency): `parse(readFileSync(filePath, "utf-8"))`
- If the parsed result is null/undefined (empty file), return `null`
- Wrap the parse in a try/catch — if YAML parsing fails, log a warning and return `null`. This way a malformed `.critters.yaml` doesn't crash the entire task; the critter proceeds without repo-specific config.
- Return the parsed object cast to `PerRepoConfig`

## Design Decisions

1. **`PerRepoConfig` vs `RepoConfig` naming**: The existing `RepoConfig` in `types.ts` represents daemon-level per-project config (project UUID → repo URL + extra tools). The new type is named `PerRepoConfig` to clearly distinguish it as the in-repo `.critters.yaml` config.

2. **Ordering of prompt sections**: Repo-specific instructions are appended **after** both the base prompt and the global `~/.critters/` custom prompts. This means the section ordering is:
   - Base prompt (hardcoded)
   - `## Additional Context` (from `~/.critters/*.md`)
   - `## Repo-Specific Instructions` (from `.critters.yaml`)

   This ordering makes sense because repo-specific instructions are more targeted and should take precedence (appearing later = more salient to the model).

3. **Additive-only merging**: Per-repo config can only add tools and prompts. It cannot remove daemon defaults or override the daemon's `defaultAllowedTools`. This is enforced structurally — the code only pushes to the tools array, never filters.

4. **`loadRepoConfig` returns `null` not `{}`**: Following the pattern of `readCustomPrompt` which returns `null` when no content exists, allowing callers to easily skip processing with a null check.

5. **No validation of tool patterns in per-repo config**: Following the existing pattern where `extraAllowedTools` in daemon config is not validated for format — it's just passed through.

6. **`extraAllowedTools` only applies to execution phase**: The planning phase uses a hardcoded restricted tool set via `getPlanningAllowedTools()`. Per-repo `extraAllowedTools` are intentionally not merged into planning tools, since the planning phase should remain sandboxed. Custom prompts (`planningPrompt`) *are* applied to the planning phase to provide guidance without expanding tool access.

7. **Graceful YAML parse error handling**: `loadRepoConfig` wraps parsing in try/catch and returns `null` on failure, logging a warning. A malformed `.critters.yaml` in a target repo should not crash the task — the critter proceeds without repo-specific config.

8. **File naming — `.critters.yaml`**: Uses the dotfile convention (`.critters.yaml`) matching common patterns like `.eslintrc.yaml`, `.prettierrc.yaml`. Distinguished from the daemon config (`critters.config.yaml`) by the dot prefix and shorter name.
