# ACK-132: Add SHA-256 checksum verification to updater

## Summary

The updater (`src/updater.ts`) downloads binaries from GitHub releases with no integrity verification. This change adds SHA-256 checksum verification to protect against compromised releases or MITM attacks, and updates the release workflow to generate and upload a checksum file.

## Files to modify

### 1. `.github/workflows/release.yml`

Add a step in the `release` job (after downloading artifacts, before creating the release) to generate `checksums-sha256.txt` and include it as a release asset.

**Changes:**

Add a new step between the `download-artifact` step and the `Create GitHub Release` step:

```yaml
- name: Generate checksums
  run: |
    cd artifacts
    shasum -a 256 critters-darwin-arm64 critters-linux-x64 > checksums-sha256.txt
```

Update the `gh release create` command to include the checksum file:

```yaml
- name: Create GitHub Release
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  run: |
    gh release create "$GITHUB_REF_NAME" \
      artifacts/critters-darwin-arm64 \
      artifacts/critters-linux-x64 \
      artifacts/checksums-sha256.txt \
      --generate-notes
```

### 2. `src/updater.ts`

Extract checksum verification into a testable helper function and integrate it into `checkForUpdate`.

**New exported functions:**

#### `parseChecksumFile(content: string): Map<string, string>`

Parses the `checksums-sha256.txt` format (`<sha256-hex>  <filename>\n`) and returns a Map of filename → hash. Each line is split on whitespace (the standard `shasum` format uses two spaces between hash and filename).

#### `verifyChecksum(buffer: Buffer, expectedHash: string): boolean`

Computes SHA-256 of the buffer using `crypto.createHash('sha256')` from Node's `crypto` module and compares it (case-insensitive) to the expected hash. Returns `true` if they match.

**Changes to `checkForUpdate`:**

After downloading the binary buffer (line 146) and before writing to disk (line 147), add checksum verification:

1. Find `checksums-sha256.txt` in the `assets` array (same pattern as finding the binary asset).
2. If the checksum asset is found:
   - Download it (simple `fetch` with a timeout).
   - Parse with `parseChecksumFile`.
   - Look up the expected hash using `expectedName` (the binary asset name, e.g. `critters-darwin-arm64`).
   - If the asset name is not found in the checksum file, treat it as a verification failure and abort.
   - Call `verifyChecksum(buffer, expectedHash)`. If it returns `false`, abort the update with an error message and return (do not write to disk).
   - If it passes, log a success message (e.g., `"Checksum verified (SHA-256)"`).
3. If the checksum asset is not found (backwards compat with older releases):
   - Log a warning: `"Update: checksums-sha256.txt not found in release, skipping verification"`.
   - Proceed with the update as before.

**Import addition:**

Add `import { createHash } from "node:crypto";` at the top of the file.

### 3. `src/__tests__/updater.test.ts` (new file)

Create a dedicated test file for the checksum verification logic. Tests use `bun:test` (matching existing test patterns).

**Test cases:**

#### `parseChecksumFile`

- Parses standard two-entry format correctly (returns Map with correct hash → filename mappings)
- Handles single entry
- Handles empty string (returns empty Map)
- Handles lines with extra whitespace
- Ignores blank lines
- Handles both `shasum -a 256` format (two spaces) and single-space separation

#### `verifyChecksum`

- Returns `true` for matching hash
- Returns `false` for non-matching hash
- Case-insensitive comparison (uppercase vs lowercase hex)
- Works with known test vector (e.g., SHA-256 of empty buffer = `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`)

#### Integration-style tests (optional, if mocking `fetch` is straightforward)

- Existing `compareSemver` tests remain in `src/__tests__/utils.test.ts` (no move needed)

## Dependencies

- `node:crypto` — already available in Bun's Node.js compat layer; no new packages needed.

## Testing approach

- Unit tests for `parseChecksumFile` and `verifyChecksum` are pure functions that need no mocking.
- The integration into `checkForUpdate` is tested indirectly via the pure functions. Full integration testing of `checkForUpdate` would require mocking `fetch` (GitHub API + download URLs), which is complex and out of scope — the critical logic is in the extracted functions.
- Run tests with `bun test` to verify.

## Edge cases

- **Backwards compatibility**: Older releases won't have `checksums-sha256.txt`. The updater logs a warning and proceeds. This is explicitly required by the task spec.
- **Checksum file present but missing entry for this platform**: Treated as a verification failure (abort update). This could indicate a corrupted or tampered release.
- **Download failure for checksum file**: Treated as an error, abort the update (not silently skipped — if the asset exists but can't be downloaded, something is wrong).
- **Hash comparison**: Done case-insensitively since hex encoding case can vary between tools.
