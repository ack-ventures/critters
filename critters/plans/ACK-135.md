# ACK-135: Add `critters kickoff` command to trigger immediate poll

## Summary

Add a `critters kickoff` CLI command that POSTs to the running daemon's health server to trigger an immediate poll cycle (both critter and review polls), without waiting for the next scheduled interval.

## Files to modify

### 1. `src/watcher.ts` — Add `triggerPoll()` public method

Add a public method to the `Watcher` class that calls the existing private `poll()` method, with a guard against concurrent polls:

```ts
private polling = false;

async triggerPoll(): Promise<number> {
  if (this.polling) {
    return 0;
  }
  this.polling = true;
  try {
    return await this.poll();
  } finally {
    this.polling = false;
  }
}
```

Also wrap the existing `poll()` call in `start()` with the same guard:

```ts
// In start(), replace `const issuesFound = await this.poll();` with:
if (this.polling) {
  await sleep(this.config.pollIntervalSeconds * 1000);
  continue;
}
this.polling = true;
let issuesFound: number;
try {
  issuesFound = await this.poll();
} finally {
  this.polling = false;
}
```

- Insert `polling` flag and `triggerPoll()` after the `stop()` method (after line 41)
- Returns the number of issues found (same as `poll()`)
- The `polling` flag prevents overlapping execution. Since JS is single-threaded, the flag check + set is atomic within a microtask. If a trigger arrives while a scheduled poll's `await findCritterIssues()` is in flight, the trigger will return 0 immediately, avoiding any risk of duplicate dispatch.

### 5. `src/cli-kickoff.ts` — New CLI command file

Create a new file following the pattern of `src/status.ts`:

```ts
import { existsSync, readFileSync } from "node:fs";
import { homedir } from "node:os";
import { parse as parseYaml } from "yaml";

function getKickoffConfig(): { healthPort: number } {
  const candidates = [
    "./critters.config.yaml",
    `${homedir()}/.critters/config.yaml`,
  ];

  for (const candidate of candidates) {
    if (existsSync(candidate)) {
      try {
        const raw = readFileSync(candidate, "utf-8");
        const yaml = parseYaml(raw) as Record<string, unknown>;
        return {
          healthPort: (yaml.healthPort as number) ?? 3847,
        };
      } catch {
        // Fall through to defaults
      }
    }
  }

  return { healthPort: 3847 };
}

export async function runKickoff(): Promise<void> {
  const config = getKickoffConfig();
  const baseUrl = `http://localhost:${config.healthPort}`;

  // Trigger both polls concurrently
  const [pollResult, reviewResult] = await Promise.allSettled([
    fetch(`${baseUrl}/poll`, { method: "POST" }).then(async (resp) => {
      if (!resp.ok) {
        throw new Error(`${resp.status} ${await resp.text()}`);
      }
      return resp.json() as Promise<{ triggered: boolean; issuesFound: number }>;
    }),
    fetch(`${baseUrl}/review-poll`, { method: "POST" }).then(async (resp) => {
      if (!resp.ok) {
        throw new Error(`${resp.status} ${await resp.text()}`);
      }
      return resp.json() as Promise<{ triggered: boolean; issuesFound: number }>;
    }),
  ]);

  // If both failed, daemon is likely not running
  if (pollResult.status === "rejected" && reviewResult.status === "rejected") {
    console.error("Critters daemon is not running (or health endpoint is disabled)");
    process.exit(1);
  }

  // Report results, showing partial results if one failed
  const critterIssues = pollResult.status === "fulfilled" ? pollResult.value.issuesFound : null;
  const reviewIssues = reviewResult.status === "fulfilled" ? reviewResult.value.issuesFound : null;

  const parts: string[] = [];
  if (critterIssues !== null) {
    parts.push(`${critterIssues} critter issues`);
  } else {
    parts.push("critter poll failed");
  }
  if (reviewIssues !== null) {
    parts.push(`${reviewIssues} review issues`);
  } else {
    parts.push("review poll failed");
  }

  console.log(`Poll triggered. Found ${parts.join(", ")}.`);
}
```

## Design decisions

1. **Separate endpoints (`/poll` and `/review-poll`)** rather than a single combined endpoint — matches the task spec and allows triggering each independently if needed in the future.

2. **`triggers` as fourth parameter (after `metricsPath`)** — preserves backward compatibility with all existing callsites. Both `index.ts` and the 11+ test callsites in `health.test.ts` pass `metricsPath` as the third argument (or omit it). Adding `triggers` after `metricsPath` means zero existing callsite changes are needed.

3. **Move health server start after watcher creation** — simplest way to resolve the ordering dependency where trigger callbacks need watcher references. No functional impact since the health server just needs to be running before the `Promise.all` that starts the poll loops.

4. **`polling` mutex flag to prevent concurrent polls** — Although JS is single-threaded synchronously, `poll()` contains `await` calls (e.g., `findCritterIssues()`) that yield to the event loop. A `triggerPoll()` arriving during a scheduled poll's async gap could cause both to see the same new issue before either adds it to `activeIssueIds`. The `polling` flag prevents this by making `triggerPoll()` return 0 immediately if a poll is already in flight, and by skipping the scheduled poll iteration if a triggered poll is running.

5. **`Promise.allSettled` in CLI** — Fires both poll requests concurrently and reports partial results if one fails. This is more resilient than sequential calls where a first-call failure would hide the second call's success.

6. **CLI uses same config-reading pattern as `status.ts`** — only reads `healthPort` from config, communicates with daemon via HTTP. This keeps the CLI command lightweight and decoupled from daemon internals.

## Testing approach

- **Existing health tests**: No changes needed — the new `triggers` parameter is appended as an optional fourth parameter, so all 11+ existing callsites remain valid.
- **New health route tests** (in `src/__tests__/health.test.ts`): Tests for `POST /poll` and `POST /review-poll` covering success, 405 for GET, and 503 when triggers are not configured.
- **Unit tests for `triggerPoll()`**: Verify that calling `triggerPoll()` on both `Watcher` and `ReviewWatcher` invokes the underlying poll logic and returns the issue count.
- **Concurrency guard test**: Verify that calling `triggerPoll()` while a poll is in progress returns 0 immediately.
- **CLI test**: Verify `runKickoff()` handles success, daemon-not-running, and partial failure cases.
