# ACK-229: Hot-reload config without daemon restart

## Summary

The hot-reload infrastructure is **already implemented** in the codebase. The following components exist and are fully wired:

- `src/config-watcher.ts`: `ConfigWatcher` class using `fs.watch()` with 500ms debounce, `diffConfigs()` for change logging
- `src/unified-watcher.ts`: `updateConfig()` method that atomically swaps config + trackers
- `src/unified-spawner.ts`: `updateConfig()` method with `drainRemovedTypeQueues()` for removed types
- `src/index.ts` (lines 456-520): Full wiring — immutable field enforcement, new provider/tracker creation, async apply flow with diff logging
- `src/__tests__/config-watcher.test.ts`: Tests for diffConfigs and ConfigWatcher (reload on change, rejection of invalid config, cleanup)

**What's missing** per the requirements:

1. **`--no-watch` CLI flag** — no way to disable config watching
2. **`metricsRetentionDays` not in immutable fields list** — requirement says it should warn on change
3. **`provider` not treated as unsafe** — requirement says it should warn, but current code hot-reloads it by creating new trackers (this is arguably better behavior, see notes below)

### 3. `src/index.ts` — Add `provider` change warning

**Location**: After the immutable fields check (line 469), before the provider tracker creation

The current implementation hot-reloads the provider by creating new trackers. Per the requirement, changing the top-level `provider` should log a warning. However, I recommend keeping the current behavior (creating new trackers on provider change) since it's more useful and already works correctly. Instead, add a warning log noting that the provider change was applied but a restart is recommended for full effect:

```typescript
if (newConfig.provider !== config.provider) {
  log(`Warning: default 'provider' changed (${config.provider} → ${newConfig.provider}) — new trackers created, but restart recommended for clean state`);
}
```

**Alternative**: If strict adherence to the requirement is preferred, add `provider` to the immutable fields list and revert changes. But this would regress functionality.

## Testing approach

1. **Existing tests pass**: Run `bun test src/__tests__/config-watcher.test.ts` to verify existing hot-reload tests still pass
2. **Manual testing**: Start daemon, edit config file, verify reload log message; start with `--no-watch`, edit config, verify no reload
3. **Invalid config**: Edit config with invalid values (e.g., `pollIntervalSeconds: 1`), verify warning logged and old config retained (already tested)
4. **Immutable field warning**: Change `metricsRetentionDays` in config, verify warning logged and value reverted

## Design decisions

- **`provider` as hot-reloadable vs unsafe**: The current implementation correctly handles provider changes by creating new trackers. Making it fully immutable would be a regression. The plan adds a warning log but keeps the hot-reload behavior.
- **`--no-watch` only affects config watching**: The flag doesn't affect any other daemon behavior. Dry-run mode already implicitly disables watching.
- **No new files**: All changes are modifications to `src/index.ts`. The existing `ConfigWatcher` class and tests are sufficient.
