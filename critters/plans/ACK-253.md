# ACK-253: Add `critters stop` CLI command

## Summary

Add a `critters stop` CLI command that gracefully stops the running daemon by hitting a new `/stop` endpoint on the health server. The `/stop` endpoint triggers the existing `shutdown()` function (the same one used by SIGTERM/SIGINT handlers).

## Files to Create

### `src/cli-stop.ts`

New file following the exact pattern of `src/cli-restart.ts`:

- Export `async function runStop(): Promise<void>`
- Reuse the same `getStopConfig()` pattern (read `healthPort` and `dashboardToken` from config YAML, same candidates list)
- Send `POST /stop` to `http://localhost:{healthPort}`
- Include `Authorization: Bearer {token}` header if `dashboardToken` is configured
- On success: print `"Stopping critters daemon..."`
- On HTTP error: print `"Stop failed: {status} {body}"` and exit 1
- On connection error (daemon not running): print `"Critters daemon is not running (or health endpoint is disabled)"` and exit 1

Actually, to avoid duplicating the config-reading logic, we can extract the shared helper or just duplicate it (it's only ~20 lines). Following the existing pattern in `cli-restart.ts`, we'll duplicate the small helper since that's what the codebase does — each CLI file is self-contained.

## Files to Modify

### `src/health.ts`

Add a `/stop` endpoint right after the `/restart` endpoint (around line 201). Pattern:

```typescript
if (url.pathname === "/stop") {
  if (req.method !== "POST") {
    return new Response("Method Not Allowed", { status: 405 });
  }
  const authResp = checkAuth(req, dashboardToken);
  if (authResp) return authResp;
  if (!triggers?.triggerStop) {
    return Response.json({ error: "Stop not available" }, { status: 503 });
  }

  setTimeout(() => {
    triggers.triggerStop!();
  }, 250);

  return Response.json({ ok: true, message: "Stopping..." });
}
```

Add `triggerStop?: () => void` to the `triggers` parameter type (alongside `triggerRestart`).

Since `triggerStop` is a closure that's only *called* later (not at definition time), and `const` declarations in the same function scope are accessible from closures as long as they're assigned before the closure executes, this works fine. The health server won't call `triggerStop` until an HTTP request comes in, by which time `shutdown` is defined. So we can simply add `triggerStop: () => shutdown()` — same pattern as `triggerRestart: () => restartDaemon()`.

The closure `() => shutdown()` captures `shutdown` by reference, but `shutdown` is a `const` defined later in the same block scope. In JavaScript, this would be a TDZ (temporal dead zone) issue if accessed before initialization — but since the closure is only *invoked* later (when an HTTP request arrives), not at definition time, and by that time `shutdown` has been assigned, this is safe. ## Testing Approach

- **Manual**: Start daemon, run `critters stop`, verify daemon shuts down gracefully
- **Type check**: `bun run typecheck` to verify no type errors

## Edge Cases

- **Daemon not running**: CLI prints error message and exits 1 (same as `restart`)
- **Health port disabled (0)**: Same behavior — connection refused, CLI prints error
- **Auth required**: Token is read from config and sent in header (same as `restart`)
- **Multiple stop requests**: The `shuttingDown` guard in `shutdown()` prevents double-shutdown
- **Active critters**: The existing shutdown logic handles this — waits 6s for cleanup, then exits
