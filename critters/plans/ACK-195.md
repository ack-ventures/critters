# ACK-195: Add automatic retry with backoff for transient failures

## Summary

When a critter fails due to a transient issue (git clone failure, API timeout, network error), automatically retry the entire task with exponential backoff before marking it as "Critter Failed". This is opt-in via a new `autoRetry` config section.

## Files to modify

### 1. `src/types.ts` — Add `AutoRetryConfig` type and optional field to `Config`

Add a new interface:

```typescript
export interface AutoRetryConfig {
  maxRetries: number;
  baseDelaySeconds: number;
  maxDelaySeconds: number;
}
```

Add optional field to `Config`:
```typescript
autoRetry?: AutoRetryConfig;
```

When `autoRetry` is absent/undefined, no retry happens. When present, retry is enabled. This follows the codebase pattern used by `costAlertThreshold`, `hooks`, `slackWebhookUrl`, etc. — optional presence indicates opt-in.

### 4. `src/unified-spawner.ts` — Core retry logic

#### 4a. Add retry tracking state

Add a new private field to `UnifiedSpawner`:
```typescript
private retryCounts = new Map<string, number>();
```

Key is `task.id`. In-memory only.

#### 4b. Add `isTransientError(error: string)` private method

Returns `true` if the error message matches known transient patterns. Uses a single compiled regex for efficiency, following the `GIT_URL_RE` pattern in `src/config.ts`:

```typescript
private static TRANSIENT_ERROR_RE = /Could not resolve host|Connection refused|Connection timed out|Connection reset|fatal: unable to access|fatal: Could not read from remote|SSL_ERROR|TLS handshake|rate limit|429|500 Internal Server Error|502 Bad Gateway|503 Service|504 Gateway|ETIMEDOUT|ECONNREFUSED|ECONNRESET|ENOTFOUND|shallow file has changed/i;

private isTransientError(error: string): boolean {
  return UnifiedSpawner.TRANSIENT_ERROR_RE.test(error);
}
```

#### 4c. Add `shouldAutoRetry` private method

Centralizes the retry decision:

```typescript
private shouldAutoRetry(taskId: string, error: string, timedOut: boolean): boolean {
  const autoRetry = this.config.autoRetry;
  if (!autoRetry) return false;
  if (timedOut) return false;
  if (this.stopped) return false;
  const retryCount = this.retryCounts.get(taskId) ?? 0;
  if (retryCount >= autoRetry.maxRetries) return false;
  return this.isTransientError(error);
}
```

#### 4d. Modify `runTask` catch block to skip heavy failure handling on intermediate attempts

In the `catch` block of `runTask`, right after determining `error` and `timedOut`, add an early return:

```typescript
// Auto-retry: skip heavy failure handling if this will be retried
if (this.shouldAutoRetry(task.id, error, timedOut)) {
  logTask(task.identifier, `Transient failure detected (will auto-retry): ${error}`);
  try {
    await tracker.comment(task.id, `Transient failure detected (will auto-retry): ${error}`);
  } catch { /* best effort */ }
  return { success: false, error };
}
```

This early return skips:
- Status update to "Critter Failed"
- Salvage/draft PR creation
- Failure Slack notification
- `task_failed` metric recording
- `onTaskFailed` hook firing
- Log upload

The `finally` block still runs, cleaning up workdir, abort controller, etc.

#### 4e. Add `runTaskWithRetry` wrapper

Uses a loop with exponential backoff + jitter matching the formula from `src/retry.ts` (`baseDelay * 2^attempt` capped at `maxDelay`, plus 25% jitter):

```typescript
private async runTaskWithRetry(task: TrackerTask, critterType: CritterTypeConfig): Promise<TaskResult> {
  const autoRetry = this.config.autoRetry;
  if (!autoRetry) {
    return this.runTask(task, critterType);
  }

  let lastResult: TaskResult;
  for (let attempt = 0; attempt <= autoRetry.maxRetries; attempt++) {
    lastResult = await this.runTask(task, critterType);

    // Success or non-retryable — done
    if (lastResult.success || !lastResult.error) break;
    if (lastResult.error.startsWith("Timed out after")) break;
    if (!this.isTransientError(lastResult.error)) break;
    if (attempt >= autoRetry.maxRetries) break;
    if (this.stopped) break;

    // Retryable transient failure — compute exponential backoff delay
    const baseMs = autoRetry.baseDelaySeconds * 1000;
    const maxMs = autoRetry.maxDelaySeconds * 1000;
    let delayMs = Math.min(baseMs * (2 ** attempt), maxMs);
    delayMs += Math.random() * 0.25 * delayMs; // jitter

    this.retryCounts.set(task.id, attempt + 1);
    const nextAttempt = attempt + 2;
    const maxAttempts = autoRetry.maxRetries + 1;

    logTask(task.identifier, `Auto-retrying (attempt ${nextAttempt}/${maxAttempts}) in ${Math.round(delayMs / 1000)}s after transient failure: ${lastResult.error}`);
    const tracker = this.getTracker(critterType);
    await tracker.comment(task.id, `Auto-retrying (attempt ${nextAttempt}/${maxAttempts}) in ${Math.round(delayMs / 1000)}s...\nError: ${lastResult.error}`).catch(() => {});

    await new Promise(resolve => setTimeout(resolve, delayMs));
  }

  this.retryCounts.delete(task.id);
  return lastResult!;
}
```

The `shouldAutoRetry` check in step 4d ensures that intermediate attempts return early from `runTask`'s catch block (skipping heavy failure handling). The final attempt, when `retryCounts.get(task.id) >= autoRetry.maxRetries`, causes `shouldAutoRetry` to return false, so `runTask` runs its full failure path (status update, salvage, Slack, hooks, metrics).

Note: We don't reuse `withRetry` from `src/retry.ts` directly because it expects the function to throw on retriable failures, whereas `runTask` returns a `TaskResult`. The backoff formula is the same though (`baseDelay * 2^attempt` + jitter).

Change line ~204 from:

to:

#### 4g. Include retry info in failure metrics

In the `runTask` catch block where `recordMetric` is called for `task_failed`/`review_failed`, add:
```typescript
retryAttempt: this.retryCounts.get(task.id) ?? undefined,
```

The `retryAttempt` value is the number of retries that preceded this final failure. `0` or `undefined` means first (and only) attempt. `1` means one retry was attempted before this final failure. This only appears on the final failure metric since intermediate attempts skip metric recording via the early return in step 4d.

No changes needed to `src/slack.ts`. Intermediate attempts skip Slack (via the early return in step 4d). The final failure goes through the normal `runTask` failure path which posts the Slack notification. The retry comments on the issue tracker provide the full audit trail.

## Edge cases

- **Stopped spawner**: Both `shouldAutoRetry()` and the `runTaskWithRetry` loop check `this.stopped` before retrying. Clean shutdown is preserved.
- **Config reload**: The wrapper reads `this.config.autoRetry` each call, picking up live config changes.
- **Concurrent retries**: Each task has its own retry count keyed by `task.id`. No shared state issues.
- **Memory leak**: `retryCounts` entries are deleted in `runTaskWithRetry` after loop exits. No leak.
- **`critters retry` CLI**: Still works — it resets issue status to Todo for re-pickup. Orthogonal to auto-retry.
- **Intermediate failure handling**: `shouldAutoRetry` causes the catch block to early-return, skipping salvage, status update, Slack, hooks, and metrics. Only a lightweight comment is posted. The `finally` block still cleans up workdir/abort controller.
- **Final failure after retries**: Goes through the full failure path since `shouldAutoRetry` returns false when retries are exhausted.

## Testing approach

1. **Unit test `isTransientError`**: Test with various error strings — transient ones (git clone failures, connection errors, rate limits) should return true; non-transient ones (compilation errors, test failures, permission errors) should return false.
2. **Unit test `shouldAutoRetry`**: Test with autoRetry undefined (disabled), autoRetry present + transient error, autoRetry + non-transient error, autoRetry + timeout, autoRetry + retries exhausted, autoRetry + stopped.
3. **Unit test config parsing**: Verify `autoRetry` defaults when section present, absent section means undefined, validation errors for invalid values.
4. **Unit test validate.ts**: Verify `autoRetry` validation in the validate CLI.
5. **Integration test retry flow**: Mock `runTask` to return transient failure first, success second. Verify retry comment posted, final result is success, only one failure metric (from last attempt if it fails).
6. **Integration test non-transient**: Verify compilation errors go straight to full failure (no retry).
7. **Integration test timeout**: Verify timeouts are NOT retried.
8. **Integration test max retries**: Verify retries stop after `maxRetries` and full failure handling runs on the last attempt.
