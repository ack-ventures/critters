# ACK-233: Per-issue dashboard drill-down page

## Summary

Add a per-issue detail page at `/dashboard/<identifier>` that shows issue metadata, phase timeline, cost breakdown, embedded streaming logs, and links to the PR. The existing recent activity table and active critters table will link to this new page instead of `/logs/<identifier>`.

## Files to modify

### 1. `src/dashboard.ts`

**Add `renderIssuePage()` function** — a new exported function following the same pattern as `renderDashboard()` and `renderLogPage()`. It receives:
- `identifier: string`
- `status: HealthStatus`
- `workDir: string`

**Page sections:**

1. **Header** — Back link to `/dashboard`, identifier as `<h1>`, status badge (Live/Completed/Failed), critter type badge
2. **Issue metadata card** — Title (from active detail or "N/A"), identifier, type, current status, link to PR if available, repo and branch info
3. **Phase timeline** — Table of phases that ran: phase name, cost, token counts (input/output/cache), turns, success/failure badge. Data source: parse the `result` event from each phase's stream-json log file (`.critter-output-*.json`). For the currently running phase (active critter), show "Running" with elapsed time. **Note:** Per-phase duration is not available from the stream-json result event, so duration is omitted from the per-phase breakdown.
4. **Cost breakdown card** — Total cost, input/output/cache tokens. Aggregate from: (a) per-phase log file result events if available, (b) fall back to metrics `task_completed`/`task_failed` event for this identifier. Overall task duration comes from the metrics event's `duration` field (available for completed tasks) or elapsed time for active critters.
5. **Embedded log viewer** — Reuse the same log viewer pattern from `renderLogPage()`: phase tabs, `<pre>` log content area, SSE streaming for active critters, static fetch for completed ones. The existing `/api/logs/<identifier>` and `/api/logs/<identifier>/stream` endpoints are reused as-is.

**Update recent activity table links** — Change the identifier column `<a href="/logs/...">` to `<a href="/dashboard/...">` in the `recentActivity` table rendering (around line 811).

**Update active critters table links** — Change the identifier column and log preview links from `/logs/...` to `/dashboard/...` in the active critters table (around lines 612, 622).

### 3. `src/log-resolver.ts`

**Add `extractPhaseResult()` helper** — New exported function that reads the last few lines of a phase log file and extracts the `result` event JSON object. Uses the correct field names matching the actual stream-json output format (as parsed in `src/claude.ts:228-247`):

```typescript
export function extractPhaseResult(logFile: string): {
  costUsd?: number;
  numTurns?: number;
  inputTokens?: number;
  outputTokens?: number;
  cacheReadTokens?: number;
} | null
```

The `result` event has this actual schema:
- `type: "result"` — identifies the event
- `total_cost_usd: number` — total cost (NOT `cost_usd`)
- `num_turns: number` — turn count
- `modelUsage: Record<string, { inputTokens, outputTokens, cacheCreationInputTokens, cacheReadInputTokens }>` — per-model token breakdown (needs aggregation across models)

The function aggregates `modelUsage` the same way as `src/claude.ts:238-246`:
- `inputTokens = sum(model.inputTokens + model.cacheCreationInputTokens)` per model
- `outputTokens = sum(model.outputTokens)` per model
- `cacheReadTokens = sum(model.cacheReadInputTokens)` per model

Implementation: read the file, scan last ~10 lines for a line with `"type":"result"`, parse it. Uses synchronous file reads (`readFileSync`), consistent with the existing pattern in `resolveAllPhases()` and `readLogTail()`.

### 4. No changes to `src/metrics.ts`

`getRecentMetrics()` is used only for aggregate cost fallback (when log files are unavailable due to cleanup) and for identifying the task's critterType, prUrl, etc. No per-phase data is extracted from metrics.

## Design details

### Per-phase data extraction from log files

Each phase writes a `.critter-output-<tag>.json` file with stream-json output. The last meaningful line is a `result` event:
```json
{"type":"result","subtype":"success","total_cost_usd":0.45,"num_turns":12,"modelUsage":{"claude-opus-4-20250514":{"inputTokens":45000,"outputTokens":12000,"cacheCreationInputTokens":5000,"cacheReadInputTokens":8000}}}
```

The `extractPhaseResult()` function reads the file, scans the last ~10 lines for the `result` event, and parses it using the correct field names. This is efficient and doesn't require changes to the metrics system.

### Issue metadata resolution

For active critters, metadata comes from `status.activeCritterDetails` (has identifier, title, phase, repo, branch, prUrl, critterType, workDir, startedAt, timeoutMinutes).

For completed critters, metadata comes from metrics events filtered by identifier:
- `task_started` event has `identifier`, `repoUrl`, `critterType`
- `task_completed`/`task_failed` have `identifier`, `duration`, `costUsd`, `prUrl`

Note: Issue tracker URLs are not available from metrics or active critter details (`issueUrl` exists on `CritterTask` but isn't propagated). The drill-down page will not include a direct link to the issue tracker — this can be added in a future PR by propagating `issueUrl` to `ActiveCritterDetail` and `MetricEvent`.

### Auto-refresh for active critters

Re-fetch the full page HTML every 10s while the critter is active (same pattern as the main dashboard's 30s refresh). When the critter completes, the re-rendered page will show "Completed" status and stop refreshing. The log viewer uses SSE independently so it streams in real-time without being affected by the page refresh (the SSE connection is re-established after each refresh, which is acceptable since it sends existing content first).

### Routing order in health.ts

1. `/healthz` (existing)
2. `/metrics` (existing)
3. `/dashboard/<identifier>` (NEW — must come before the main dashboard route)
4. `/` or `/dashboard` (existing — main dashboard)
5. `/poll`, `/review-poll`, `/restart` (existing)
6. `/api/logs/<identifier>` (existing — API endpoint, unchanged)
7. `/logs/<identifier>` (existing — changed to 302 redirect to `/dashboard/<identifier>`)
8. `/api/v1/*` (existing)

### Edge cases

1. **Unknown identifier** — If no metrics and no active critter match, show a "not found" page with a link back to the dashboard.
2. **Cleaned-up work directory** — Phases/logs won't be available, but metrics still are. Show metrics-only view (aggregate cost, duration) with a note that logs are no longer available.
3. **Multiple runs of same identifier** — `resolveWorkDirForIdentifier` picks the newest directory. Metrics may contain events from retries; show aggregate data from the latest run (filter by most recent `task_started` timestamp). Note in the UI if multiple runs exist.
4. **Identifier with special characters** — Use `encodeURIComponent`/`decodeURIComponent` consistently.
5. **Old `/logs/<identifier>` links** — 302 redirect to `/dashboard/<identifier>`. Only the HTML page route redirects; the `/api/logs/` API endpoint is unaffected (it's matched earlier in the routing chain).
