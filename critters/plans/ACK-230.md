# ACK-230: Add `critters retry --all-failed` for bulk retry

## Summary

Add bulk retry support to `critters retry`. Currently it only retries a single issue by identifier. This adds `--all-failed` to find all failed issues across configured critter types and reset them to their trigger status, with optional `--since`, `--type`, and `--dry-run` filters.

Add an optional `updatedAt?: Date` field to the `TrackerTask` interface. This is needed for `--since` filtering.

}

### 4. `src/cli-retry.ts` — Add `runRetryAllFailed()` function

Add a new exported function alongside the existing `runRetry()`:

```typescript
export async function runRetryAllFailed(options: {
  dryRun: boolean;
  since?: string;      // e.g., "24h", "3d", "1w"
  typeName?: string;   // filter to a specific critter type
}): Promise<void>
```

**Implementation:**

1. Call `loadEnv()` and `loadConfig()` (same pattern as `runRetry`)
2. Determine which providers are needed:
   - Collect unique providers from `config.critterTypes` (each type has `type.provider ?? config.provider`)
   - Create a tracker for each unique provider via `createTracker()`
3. Determine which critter types to query:
   - If `--type` is specified, filter `config.critterTypes` to matching name
   - Error if no type matches
4. For each critter type, query its provider's tracker:
   - Look up the type's failure status from `type.outcomes.failure?.status` (default to `"Critter Failed"` if not configured)
   - Build a `TriggerConfig` with `label: type.trigger.label` and the resolved failure status
   - Call `tracker.findIssues(trigger)` to get failed issues
   - Track which critter type each issue came from (needed to know the correct trigger status to reset to)
   - Deduplicate across types by `provider + identifier` (same issue might match multiple type labels, and multi-provider setups could theoretically have collisions)
5. Apply `--since` filter if specified:
   - Parse duration string: regex match `^(\d+)(h|d|w)$`
   - Convert to milliseconds: h=3600000, d=86400000, w=604800000
   - Filter out issues where `updatedAt` is before `now - duration`
   - If `updatedAt` is unavailable on an issue, include it (don't silently drop)
6. If no failed issues found, print message and return
7. Print summary:
   ```
   Found N failed critters:
     - ACK-123: title
     - ACK-456: title
   ```
8. If `--dry-run`, print "Dry run — no changes made." and return
9. Print "Retrying..." then for each issue:
   - Determine the target status from the critter type's `trigger.status` (e.g., "Todo" for create types, "In Review" for review types) rather than hardcoding "Todo"
   - Call `tracker.updateStatus(issue.id, targetStatus, issue.groupId)`
   - Call `tracker.comment(issue.id, "Bulk retry triggered via CLI")`
   - Print `  Retried ACK-123`
   - If update fails, log the error and continue (don't stop batch)
10. Print summary: "Retried N/M critters."

**Duration parsing** — add a helper `parseDuration(s: string): number | null`:
- Match `^(\d+)(h|d|w)$`
- Return milliseconds or null if invalid format

**Provider-to-tracker mapping** — reuse the pattern from `getTracker()` in `src/utils.ts`:
- Build `Map<string, IssueTracker>` keyed by provider name
- For each critter type, look up tracker by `type.provider ?? config.provider`

**Issue-to-type association** — each found issue needs to remember:
- Which tracker (provider) it came from (for calling updateStatus/comment)
- Which critter type it matched (for determining target status via `type.trigger.status`)

Use a collected results type like:
```typescript
interface FailedIssue {
  task: TrackerTask;
  tracker: IssueTracker;
  targetStatus: string;  // from type.trigger.status
}
```

## Dependencies

None — all APIs needed already exist (`findIssues`, `updateStatus`, `comment`). The only interface change is adding `updatedAt` to `TrackerTask`.

## Edge Cases

- **Duplicate issues across types**: Two critter types may share the same trigger label (e.g., both "Critter"). Dedup by `provider + identifier` so each issue is only retried once, and multi-provider setups with same identifiers don't collide.
- **Multi-provider**: If critter types span both Linear and Jira, create trackers for each and query both. Track which tracker owns each issue for the retry calls.
- **Custom failure statuses**: Custom critter types may use different failure status names (e.g., "Error" instead of "Critter Failed"). Use `type.outcomes.failure?.status ?? "Critter Failed"` when querying.
- **Custom trigger statuses**: When resetting, use `type.trigger.status` (e.g., "In Review" for review types) instead of hardcoding "Todo".
- **Jira status mapping**: When querying Jira for failure status, the status name must go through `jiraStatusMap`. This is already handled by `findIssues()` in JiraTracker — the trigger config uses critter-internal names and the tracker maps them.
- **Missing updatedAt**: If a tracker doesn't return `updatedAt` (shouldn't happen after our changes, but defensive), include the issue in results rather than silently dropping it.
- **Partial failures**: If updating one issue fails, log the error and continue with remaining issues. Print a summary of successes/failures at the end.
