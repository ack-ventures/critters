# ACK-240: Add cost budget to kill expensive critters

## Summary

Add a hard `costBudget` config field (global and per-type) that kills a critter mid-execution if its accumulated cost exceeds the budget. Unlike `costAlertThreshold` (which only sends a Slack alert after each phase), `costBudget` actively monitors cost every 30 seconds during phase execution and aborts the critter immediately when the budget is exceeded.

### 4. `src/claude.ts` — Add new `readPartialCost()` function

Add a new exported function `readPartialCost(filePath: string): number` that:
- Reads the `.critter-output-<phaseTag>.json` file (may be partially written)
- Parses line by line, wrapping each `JSON.parse()` in try/catch to handle truncated lines
- Looks for `total_cost_usd` in `result` events (the authoritative source — same field used by `parseClaudeJsonLog`)
- Returns the `total_cost_usd` from the last `result` event found, or 0 if no result events exist yet
- Returns 0 if the file doesn't exist

**Important**: This function does NOT attempt to estimate cost from token counts. The `total_cost_usd` field in `result` events is the only reliable cost source. During a running phase, this function will return 0 until the phase completes and a `result` event is written. The primary value of periodic monitoring is catching cost overruns **between phases** (where prior phases have completed and written `result` events) and providing a final check when the current phase produces its result. For truly mid-phase enforcement, the 30-second interval serves as a best-effort check — if Claude CLI adds intermediate cost reporting in the future, this function will automatically pick it up.

**Leave `parseClaudeJsonLog()` unchanged** — it extracts multiple fields (numTurns, tokens, cost) and serves a different purpose. No refactoring needed.

## Design decisions

### Why abort mid-phase rather than between phases?
The requirements say "kill it immediately" and "check every 30 seconds". A single phase can run for 30+ minutes and consume significant cost. Between-phase checks (like `costAlertThreshold`) would only catch cost after the expensive phase finishes — too late. The 30-second interval provides best-effort mid-phase enforcement when cost data is available, and the between-phase check guarantees enforcement at phase boundaries.

### Why reuse `abortController.abort()` instead of a new mechanism?
The abort signal flow is already battle-tested for timeout handling. Cost budget exceeded is semantically similar to timeout — both kill the critter mid-execution. Reusing the abort signal avoids duplicating tmux pane cleanup, salvage logic, and error handling. A `costBudgetExceeded` flag differentiates the two cases for error messages and metrics.

### Why not use the existing `timedOut` flag directly?
While the abort mechanism is reused, the error message, comment, metric, and Slack notification must be different from timeout. A separate boolean `costBudgetExceeded` (checked before `timedOut` in the catch block) provides clean differentiation.

### Per-type override resolution
`critterType.costBudget ?? this.config.costBudget` — per-type takes precedence, falling back to global. If neither is set, no limit is enforced. This matches the existing pattern for `timeoutMinutes` and `concurrency`.

### Cost accumulation across phases
Cost from completed phases is summed (`phaseResults.reduce(...)`) and added to the current phase's partial cost. This ensures multi-phase critters don't circumvent the budget by spreading cost across phases.

### Mid-phase vs between-phase monitoring
`readPartialCost()` reads `total_cost_usd` from `result` events. Since `result` events are written at the end of a Claude run, mid-phase reads will typically return 0 for the current phase. The practical enforcement path is: (1) between phases, where completed phase costs are reliably available, and (2) mid-phase if/when Claude CLI adds intermediate cost reporting. The 30-second interval is cheap (just a file read + JSON parse) and future-proof.

### `--no-tmux` support
The abort mechanism works for both `spawnClaude()` (tmux — kills pane via `signal.aborted` check in poll loop) and `spawnClaudeSubprocess()` (`--no-tmux` — kills process via abort event listener calling `proc.kill()`). No additional code needed for `--no-tmux`.

## Hot-reload support

The `costBudget` field is read from `this.config` which is already hot-reloadable (ACK-229). Since the effective budget is resolved at the start of each task (`const effectiveCostBudget = critterType.costBudget ?? this.config.costBudget`), hot-reloaded values will apply to newly started critters. Already-running critters will use the budget resolved when they started, which is the correct behavior (changing budget mid-task would be confusing).

## Testing approach

1. **Unit test for `readPartialCost()`**: Create partial output files with various states (empty, partial JSON, complete result events, truncated lines) and verify correct cost extraction.
2. **Unit test for config validation**: Verify `costBudget` is validated (must be > 0 if set, undefined/null is OK).
3. **Unit test for `validateCritterType()`**: Verify per-type `costBudget` validation.
4. **Integration test for cost monitoring**: Mock a phase runner that writes cost data to the output file, verify the interval triggers abort when budget is exceeded.
5. **Manual test with `--dry-run`**: Verify config loading with `costBudget` set at global and per-type levels.
6. **Slack formatter test**: Verify `formatCostBudgetExceeded()` output format.

## Edge cases

- **Budget set to a very small value**: The critter will be killed at the first phase boundary or during the first 30-second check (if cost data is available). Minimum runtime is ~30 seconds.
- **No cost data available yet**: `readPartialCost()` returns 0. The critter continues running. The between-phase check catches it once the first phase completes.
- **Multiple phases**: Cost accumulates. A critter that uses $2 in planning and has a $3 budget will only have $1 left for execution.
- **Cost budget + cost alert threshold**: Both can be set. Alert fires at the threshold (notification only), budget kills at the limit. If budget < threshold, the alert never fires (critter is killed first). This is fine — the user set a budget lower than their alert threshold.
- **Race condition between interval and phase completion**: The interval is cleared after `runner.run()` returns. If the phase completes naturally at the same time the interval fires, the abort is harmless — the phase already finished. The `costBudgetExceeded` flag prevents incorrect error handling.
- **Partial output file reads**: The output file is written via `tee` (tmux) or `>` (`--no-tmux`). Reads may see partial lines. `readPartialCost()` wraps each `JSON.parse` in try/catch (same pattern as `parseClaudeJsonLog()`).
- **Interval cleanup on error**: The `setInterval` must be cleared in a `finally` block (or before the throw) to prevent leaked timers when the phase throws.
