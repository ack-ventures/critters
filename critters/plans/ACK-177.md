# ACK-177: Smarter CI polling with backoff in review critter

## Summary

The review critter currently tells Claude to run `gh pr checks <number> --watch --fail-fast` in a single blocking call (Step 3 of the review prompt). If CI is slow (5-10+ minutes), this burns an entire Claude turn waiting, and can hit the review timeout.

The fix is a **prompt-only change** in `src/review-prompt.ts` that instructs Claude to poll CI checks with a smarter, multi-step approach instead of a single blocking `--watch` call.

## Files to modify

### `src/review-prompt.ts` (lines 42-48)

Replace the current Step 3 CI-waiting instructions with a smarter CI polling strategy:

**Current behavior (line 44):**
```
2. Run: `gh pr checks ${task.prNumber} --watch --fail-fast`
```

**New behavior — replace the CI section of Step 3 with:**

```markdown
### Step 3: Wait for CI and merge (if approved)

**If the PR looks good** (no significant issues):
1. Run: `gh pr review <number> --approve -b "LGTM. Automated review by Critters."`
2. Check CI status: `gh pr checks <number>`
   - If all checks have already passed → skip to merge
   - If any check has failed → skip to the CI-failed path below
   - If checks are pending or no checks exist yet → continue to step 3
3. Wait for CI using: `gh pr checks <number> --watch --fail-fast`
   - This command blocks until checks complete. It may take several minutes — this is expected.
   - If the command exits 0 → checks passed, proceed to merge
   - If the command exits non-zero → checks failed, go to CI-failed path
   - If the command appears to hang or you get a timeout error → run `gh pr checks <number>` one final time to snapshot the current state, then output: REVIEW_RESULT:NEEDS_CHANGES:CI timed out — checks still pending after extended wait
4. Merge: `gh pr merge <number> --squash --delete-branch`
   - If merge fails → output: REVIEW_RESULT:NEEDS_CHANGES:Merge failed
5. After successful merge → output: REVIEW_RESULT:MERGED

**CI-failed path:**
1. Run `gh pr checks <number>` to capture which checks failed
2. Run: `gh pr review <number> --request-changes -b "CI checks failed: <list failed check names>"`
3. Output: REVIEW_RESULT:NEEDS_CHANGES:CI checks failed

**If the PR needs changes** (real issues, not just style nits):
1. Write clear, actionable feedback explaining what needs to change and why
2. Run: `gh pr review <number> --request-changes -b "<your feedback>"`
3. Output: REVIEW_RESULT:NEEDS_CHANGES:<one-line summary>
```

### Key improvements over current prompt

1. **Check before watching**: First runs `gh pr checks` (non-blocking) to see if CI already passed or failed, avoiding an unnecessary blocking wait.
2. **Handles "no checks yet"**: If no checks exist, proceeds to the watch step rather than hanging on a check-less PR.
3. **Clear timeout handling**: Tells Claude what to do if the watch command times out or hangs — snapshot state and report, rather than burning turns retrying.
4. **Better failure reporting**: On CI failure, captures which specific checks failed and includes them in the review comment.
5. **Single blocking call preserved**: Still uses `--watch --fail-fast` as the primary waiting mechanism (it's the right tool), but only after confirming checks are actually pending.

## What does NOT change

- `src/runner/review.ts` — no code changes needed. The runner already handles timeouts and parses REVIEW_RESULT correctly.
- `getReviewAllowedTools()` — no new tools needed; `Bash(gh:*)` already covers all `gh` commands.
- The REVIEW_RESULT sentinel format — unchanged, backward compatible.
- The review rules section — unchanged.

## Dependencies

None. This is a self-contained prompt change.

## Testing approach

1. **Manual review**: Read the updated prompt to verify the instructions are clear, unambiguous, and cover all edge cases.
2. **Dry-run with a real PR**: Use `--dry-run` with a review-type critter pointing at a PR with slow CI to observe the behavior difference.
3. **Existing tests**: Run `bun test` to verify no regressions (the review prompt builder is tested if tests exist for it).
4. **Edge cases to verify**:
   - PR with no CI checks configured → should still merge after approval
   - PR with already-passed checks → should skip watch and merge immediately
   - PR with already-failed checks → should report failure without waiting
   - PR with slow pending checks → should wait via `--watch` then merge/report
   - Watch timeout → should report clearly rather than retrying
