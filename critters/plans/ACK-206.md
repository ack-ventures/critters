# ACK-206: Add ngrok tunnel support to the daemon

## Summary

Add optional ngrok tunnel integration so the health/dashboard server can be accessed remotely. When `tunnel.enabled` is true in config, the daemon spawns an `ngrok http` process after the health server starts, logs the public URL, and tears it down on shutdown.

## Files to Create

### `src/tunnel.ts` (new)

Export `startTunnel(port: number, config: TunnelConfig): Promise<TunnelHandle | null>`.

**Implementation:**
1. Check if `ngrok` binary is available using `runCommand("ngrok", ["version"])`. If not found (exit code !== 0), log a warning via `log()` and return `null`.
2. Build args array: `["http", String(port), "--log", "stderr"]`
   - If `config.auth` is set, append `"--basic-auth", config.auth`
   - If `config.domain` is set, append `"--domain", config.domain`
3. Spawn `ngrok` as a long-running child process using `spawn()` from `node:child_process` (same import pattern as `utils.ts`).
4. Obtain the public URL by polling the ngrok local API at `http://127.0.0.1:4040/api/tunnels` with retries (up to 10 attempts, 1s apart). Parse the JSON response to extract `tunnels[0].public_url`.
5. If the URL can't be obtained after retries, log a warning and kill the process, return `null`.
6. Return `{ url: string, stop: () => void }` where `stop()` kills the child process.
7. Attach handlers: on process `exit` or `error`, log a warning that the tunnel has disconnected.

**Type definition:**
```typescript
export interface TunnelHandle {
  url: string;
  stop: () => void;
}
```

**Key patterns followed:**
- Uses `log()` and `logError()` from `src/logger.ts` (no `console.log` directly)
- Uses `spawn` from `node:child_process` (same as `utils.ts`)
- Named exports only (no default exports)
- Graceful degradation: missing ngrok binary = warning, not crash

## Dependencies / Setup

- No new npm/bun dependencies required (ngrok is a system binary, API is polled via `fetch`)
- `ngrok` CLI must be installed and authenticated (`ngrok config add-authtoken <token>`)

## Testing Approach

- **Manual testing**: Start daemon with `tunnel.enabled: true` in config, verify:
  - Tunnel URL is logged
  - Dashboard is accessible at the tunnel URL
  - Basic auth works when configured
  - Daemon starts cleanly without ngrok installed (warning only)
  - Shutdown kills the ngrok process
- **Config validation**: Test that invalid `tunnel.auth` formats are rejected
- **Edge cases**:
  - `tunnel.enabled: true` with `healthPort: 0` → warning logged, no tunnel started
  - ngrok binary not found → warning, daemon continues normally
  - ngrok process dies unexpectedly → warning logged, daemon continues

## Design Decisions

1. **Poll ngrok API vs parse stdout**: The ngrok local API at `127.0.0.1:4040/api/tunnels` is the most reliable way to get the public URL. Parsing stdout is fragile and varies by ngrok version.

2. **Tunnel config is immutable at runtime**: Since ngrok is a long-running subprocess, hot-reloading tunnel config would require killing and restarting ngrok, which is complex and could cause brief downtime. Simpler to require a daemon restart.

3. **No new dependencies**: Using `fetch()` (available in Bun) to poll the ngrok API and `spawn()` for the process keeps this lightweight.

4. **Lazy import**: `tunnel.ts` is imported dynamically (`await import("./tunnel.js")`) so it's only loaded when tunnel is enabled, keeping startup fast for the common case.
