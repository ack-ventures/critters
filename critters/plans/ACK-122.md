# ACK-122: Add `critters retry` CLI Command

## Summary

Add a `critters retry <issue-identifier>` subcommand that re-triggers a failed critter by resetting its Linear status to "Todo". The command fetches the issue by identifier, validates its current state, and updates the status so the daemon's watcher picks it up on the next poll cycle.

## Files to Create

### 1. `src/retry.ts` — Retry logic

Create a module exporting `runRetry(identifier: string, force: boolean): Promise<void>`.

```typescript
import { existsSync, readFileSync } from "node:fs";
import { homedir } from "node:os";
import { loadConfig } from "./config.js";
import { commentOnIssue, getIssueByIdentifier, initLinear, updateIssueStatus } from "./linear.js";
```

Note: `getClient` is not imported — all Linear SDK interactions go through the helper functions in `linear.ts`.

The function:

1. **Loads environment** — Loads `~/.critters/.env` as fallback if CWD `.env` doesn't exist (same pattern as the daemon in `src/index.ts` lines 92–107). Bun auto-loads `.env` from CWD at startup, so this fallback is only needed for the `~/.critters/.env` case when the user runs `critters retry` from a directory without a local `.env`.
2. **Loads config** — Calls `loadConfig()` to get the config (needed for `initLinear()` and `triggerLabel`).
3. **Initializes Linear client** — Calls `initLinear(config)`.
4. **Fetches the issue by identifier** — Calls `getIssueByIdentifier(identifier)` from `linear.ts`. If `null` is returned, prints `Error: Issue ${identifier} not found.` and exits with code 1.
5. **Fetches issue state, labels, and team** — Calls `await issue.state`, `await issue.labels()`, and `await issue.team` on the returned issue node. The team is needed to resolve the "Todo" status ID.
6. **Validates the "Critter" label** — Checks that the issue has the config's `triggerLabel` (default "Critter"). If not: prints `Error: ${identifier} isn't a critter task (missing "${config.triggerLabel}" label).` and exits 1.
7. **Checks current status** and applies safety rules:

   | Current Status | Default behavior | With `--force` |
   |---|---|---|
   | "Critter Failed" | Retry (reset to "Todo") | Retry |
   | "Human Review" | Refuse: `"${identifier} was flagged for human review. Use --force to override."` | Retry |
   | "In Progress" | Refuse: `"${identifier} is currently being worked on."` | **Still refuse** (never retry active work) |
   | "In Review" | Refuse: `"${identifier} is currently being worked on."` | **Still refuse** (never retry active work) |
   | "Done" | Refuse: `"${identifier} is already completed."` | Retry |
   | "Todo" | Print: `"${identifier} is already in Todo — it will be picked up on the next poll."` and exit 0 | Same (already in desired state) |
   | Any other | Refuse: `"${identifier} is in unexpected status '${statusName}'. Use --force to override."` | Retry |

8. **Resolves "Todo" status ID** — Fetches the issue's team workflow states via `const team = await issue.team; const states = await team.states();` and finds the state named "Todo". If "Todo" doesn't exist, throws a clear error: `Error: No "Todo" status found for team ${team.name}. Available statuses: ${names.join(", ")}`. This avoids using `loadTeamStatuses()` which fetches ALL teams' statuses (wasteful for a single-issue CLI command), and avoids the issue that `TeamStatuses` doesn't store state `type` information.
9. **Updates issue status** — Calls `updateIssueStatus(issue.id, todoStatusId)`.
10. **Posts a comment** — Calls `commentOnIssue(issue.id, "Retry triggered via CLI")`.
11. **Prints confirmation** — `console.log("Retried ${identifier} — status set to Todo. The daemon will pick it up on the next poll cycle.")`.

Helper function `loadEnv()`: Extract the `~/.critters/.env` fallback loading logic into a small helper within this file (duplicating the ~15 lines from `index.ts` lines 92–107 rather than refactoring `index.ts`). This keeps the change minimal and avoids touching daemon startup code.

Add the `retry` subcommand block **before** the unknown command check (line 60). Insert after the `init` block (line 58):

```typescript
if (subcommand === "retry") {
  const identifier = Bun.argv[3];
  if (!identifier) {
    console.error("Usage: critters retry <issue-identifier> [--force]\n\nExample: critters retry ACK-101");
    process.exit(1);

  const force = Bun.argv.includes("--force");
  const { runRetry } = await import("./retry.js");
  await runRetry(identifier, force);
```

### 4. `src/linear.ts` — Add `getIssueByIdentifier()` export

Add a new exported function:

```typescript
export async function getIssueByIdentifier(identifier: string) {
  const result = await client.issues({
    filter: { identifier: { eq: identifier } },
    first: 1,
  });
  return result.nodes[0] ?? null;
}
```

This uses the existing `client` module-level variable and the Linear SDK's `issues()` filter. Returns the raw Linear SDK `Issue` object (not a `CritterTask`) since the retry command needs access to `.state`, `.labels()`, and `.team` directly.

## Edge Cases

- **Issue not found**: Print clear error with the identifier and exit 1
- **No "Todo" status in team**: Throw a clear error listing the team's available statuses, rather than silently failing. The error message includes the team name and all status names to help the user debug.
- **Multiple issues with same identifier**: Not possible in Linear — identifiers are unique
- **Network errors**: Let the error propagate — the top-level `catch` in `index.ts` will print the error
- **Missing .env / LINEAR_API_KEY**: `loadConfig()` already throws a clear error if `LINEAR_API_KEY` is missing
- **"In Progress" never overridable**: Even with `--force`, refuse to retry issues in "In Progress" or "In Review" to avoid conflicting with an actively running critter
- **Bun auto-loads CWD `.env`**: The manual `.env` loading in `retry.ts` is only the `~/.critters/.env` fallback — Bun handles CWD `.env` automatically at startup
