# ACK-109: Make `critters init` idempotent — merge new fields into existing config

## Summary

Currently `runInit()` in `src/init.ts` skips writing `config.yaml` entirely if the file already exists (line 66-70). This means users who upgrade critters never get new config fields added to their existing config. The fix: when `config.yaml` exists, parse both the existing config and the default template, add any missing top-level keys with their default values, and write the merged result back.

**Extract the merge logic into a pure, testable function:**

```typescript
export function mergeConfig(
  existingYaml: string,
  defaultYaml: string,
): { merged: string; added: string[] } {
  const existing = parseYaml(existingYaml) as Record<string, unknown> | null;
  const defaults = parseYaml(defaultYaml) as Record<string, unknown>;

  const merged = existing != null ? { ...existing } : {};
  const added: string[] = [];

  for (const [key, defaultValue] of Object.entries(defaults)) {
    if (!(key in merged)) {
      merged[key] = defaultValue;
      added.push(key);
    }
  }

  return { merged: stringifyYaml(merged), added };
}
```

**Replace the config-exists branch (lines 66-71) with merge logic:**

The `runInit()` function's else-branch becomes:

```typescript
} else {
  const existingRaw = readFileSync(CONFIG_PATH, "utf-8");
  const { merged, added } = mergeConfig(existingRaw, DEFAULT_CONFIG);

  if (added.length > 0) {
    writeFileSync(CONFIG_PATH, merged);
    const defaults = parseYaml(DEFAULT_CONFIG) as Record<string, unknown>;
    for (const field of added) {
      const value = defaults[field];
      const display = typeof value === "object" ? "(default structure)" : `(default: ${value})`;
      console.log(`Added missing field: ${field} ${display}`);
    }
    console.log("\nNote: YAML comments have been removed during merge.");
  } else {
    console.log("Config is up to date");
  }
}
```

**Key design decisions:**
- Only top-level keys are compared. For nested objects like `repos` and `teamRepos`, we only add the key if it's entirely absent — we never merge into user-populated objects.
- We use `yaml.stringify()` to write the merged result. This will lose comments from the original file. When fields are added, we print a note: "Note: YAML comments have been removed during merge." to avoid user confusion. If no fields are added, the file is not rewritten, so comments are preserved.
- An empty/null existing file is treated as having no keys — all defaults get added.
- Array values (like `defaultAllowedTools`) follow the same rule: only added if the key is entirely missing, never merged element-by-element.
- The `runInit()` function signature does not change — `mergeConfig` is called inline within the existing else-branch.

## Edge cases considered

- Empty config file → treated as no keys, all defaults added
- Config file with only comments → `parseYaml` returns null, treated as empty
- New fields added in future upgrades → automatically handled since we compare against `DEFAULT_CONFIG` keys
- User has extra keys not in defaults → preserved (we only add, never remove)
- `repos`/`teamRepos` with user data → never touched if key exists, even if value differs from default
- Comment stripping → only occurs when fields are actually added (file not rewritten if nothing to add); user is warned with a printed note
